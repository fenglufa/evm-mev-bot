# M8.1 Latency Baseline

> **一句话**：从「一个真实机会被这个进程第一次看见」到「这条生命周期走到它走不动的那一格」，
> 现在每一段都有各自的数；没测到的格子写的是 `null`（没测），不是 `0`（很快）。
> **M8.1 只做这一件事：测量。本轮一行优化代码都没写，一次多余的 RPC 都没发，一分钱没花。**

白话版结论（给不看代码的人）：

```text
本轮一共写下 7 条生命周期记录（traces.jsonl 里 7 行，每行 14 个阶段，一行不缺）：
  3 条 = 真实 GIWA 测试链上现读现算的路线 run（只做 build，不签名、不广播）
  1 条 = 一段已经录好的真实区块（replay），用来证明「同一段录制跑两次，结构一模一样」
  3 条 = M7 那 6 笔真实交易留下的历史证据，按 §30 只读不算、原样折算成 latency

第一次能量出的事实（单位：毫秒）：
  一个机会从「区块到手」到「判定成候选」：live 3 次 = 1,664 / 1,841 / 2,149；replay = 2
  一次模拟（REVM）花掉：live = 23,888 / 24,432 / 24,972；历史 = 21,449 / 21,449 / 21,686；
                        replay（读录制状态）= 25
  风险判定：0.011 / 0.014 / 0.016（live，三位小数都不够它花）
  执行前闸门 §26：6,887 / 7,483 / 8,634（live）；5,627 / 5,786 / 5,989（历史）
  构造交易：2,201 / 2,310 / 2,682
  签名 / 提交 / 入块 / 结算（只有 M7 那笔成功的 6 笔序列有）：772 / 253 / 3,367 / 27,221

最重要的一条事实不是「快不快」，而是「时间花在哪一类事上」：
  live 一条生命周期总共 34.3–38.1 秒里，
    真正在 CPU 上算的：1.8–4.0 秒
    边读节点边算的（模拟 + §26 闸门）：31.9–32.5 秒  ← 92 % 以上在这一类
    等链/等节点的：0.5–0.8 秒
  「模拟 25 毫秒 vs 24,000 毫秒」这个 1,000 倍差的来源，本轮只记录、不修（§1、§54）。
  一个直接后果也被量出来了：一条生命周期 34–38 秒 ≈ 这条 1 秒一块的链上 28 个块，
  所以 3 个 live run 里有 2 个在 §26 第 12 项（fee）被自己拒掉 —— 拒的原因是「报价已经过期 28 块」，
  不是「方向算反」（那是 M7 修掉的缺陷，本轮它在正确地工作）。
```

本轮**新增 RPC 调用：0**；**被执行语义的改变：0**；**签名/广播：0 笔**；**支出：0 ETH**；
**instrumentation 自己写坏状态的次数（`instrumentation_refusals`）：7 条 trace 全为 0**。

# 42.1 Scope

**M8.1 only measures. No optimization.**（§54：「不要优化你还没有测量的东西。」）

这一份文件里出现的每一个数字，都来自「已经在磁盘上/已经在内存里」的时间戳；M8.1 没有为任何数字
新增一次等待、一次请求、一次重算。§1 明令不做的事，本轮一个字都没碰，逐条列出以免日后怀疑：

| §1 禁止 | 本轮实际 |
| --- | --- |
| 改写热路径 / 换 RPC、WS、runtime | 没换。HTTP 轮询仍是唯一 canonical 状态源（WS head 订阅 M5 实测 BLOCKED） |
| 引入新 async runtime / 队列 / 微服务 | 没有。trace 是「一条生命周期自己的一个 map」，由跑它的代码持有并 `&mut` 传入（§39） |
| 优化任何阶段 | 没有。发现的耗时问题全部写成 §42.9 的候选，带取证，不带补丁 |
| 改套利算法 / AMM 数学 / 费用模型 / Risk 规则 / stale 规则 / nonce 策略 / 执行语义 | 全部未动。四道关卡下 M7 的 629 个测试一字不改地通过（§47） |
| **改 M7 的 ProfitVerified 逻辑** | 未动。`profit_verification` 那一行只是给「已经存在的那一步」贴了一个时长 |
| 新增策略 / V3 / flashloan / sandwich / 跨链 / 外部价格 / LLM | 一个都没加 |
| 做 M8.2–M8.8 的活 | 没做。Opportunity 存活时间、stale 加固、故障恢复、observability、回放回归、资金安全、长观测全部留给后段 |

**允许宣称的话只有一句**（§49）：latency is now measurable and baseline is established.
不宣称：bot is fast / production ready / low latency / competitive / optimized。

# 42.2 Architecture：trace 是怎么进到 pipeline 里的

三层，职责互不重复：

```text
crates/metrics/src/trace.rs      数据结构 + 不变量（14 阶段、5 种 outcome、粒度、成本类、hop、里程碑）
crates/metrics/src/baseline.rs   把多行 trace 折成分位数表（nearest-rank + 样本门槛）
crates/pipeline/src/latency.rs   记录器 TraceRecorder、证据写入 LatencyEvidence、§11 归类、README
```

接入点只有三个，且都是「读已经存在的时间戳」：

| 半侧 | 接在哪 | 读的是谁已经写下的东西 |
| --- | --- | --- |
| 发现侧（observation → risk） | `crates/pipeline/src/runner.rs`（live / replay 引擎循环） | M5 为它自己的理由已经取的 `PipelineTiming` 八个 instants 和每块已经写的 `blocks.jsonl` stamps |
| 执行侧（preflight → profit_verification） | `crates/pipeline/src/arbitrage.rs` 的 `RouteTrace` + `latency::record_ladder` | M7 阶梯 `ExecutionRecord` 的 rung stamps（`created/built/signed/submitted/included/settled/profit_verified`），一次都不新读 |
| M7 历史（§30） | `crates/pipeline/src/history.rs` | M7 自己写的 `route-run.json` 里的 `latency_ms` 对象；缺字段就写 `skipped`，绝不重建时间戳 |

开关（§40/§41）：

```text
--latency-trace              打开测量。默认关闭
--latency-output <dir>       输出根目录；只给它一个目录名本身就等于打开（§41）
```

**关闭时它不存在**：`TraceRecorder` 不持 trace，连时钟都不读，因此每一次埋点调用都是空操作，
run 走的代码路径与 M5–M7 完全一致。这条不是口头承诺，由测试钉住：
`crates/cli/tests/{arbitrage,live}_args.rs` 与 `crates/pipeline/tests/latency_traces.rs` 的
`a_run_that_measures_no_latency_writes_no_traces` —— 同一段录制，不加开关产出的证据文件**逐字节相同**，
且根本没有 `traces.jsonl` 目录。

`baseline` 子命令（§30 的入口，不联网、不跑 pipeline）：

```text
evm-mev-bot baseline --evidence-dir <M7 run 目录> [--evidence-dir ...] --output <目录>
```

写出位置永远是 `data/evidence/m8/latency/{session_id}/`，与那次 run 自己的证据目录**并列而不混在一起**
（§2.1、§44）：

```text
data/evidence/m8/latency/traces.jsonl   一行一条生命周期，14 个阶段恒定齐全
                              summary.json   按来源分桶的分位数表 + §44 元数据
                              README.md      读这张表的规则（由代码写，不靠人抄）
```

一行 trace 的字段（`trace_schema: 1`）：

```text
trace_id lat-<16 hex>        由 opportunity_id 派生（§6），不会和交易哈希/区块哈希混淆
source                       live | replay | fixture（§45，永不混算）
chain_id, opportunity_block, opportunity_tx_index, opportunity_id, session_id
started_ns, completed_ns, closed
stages[]                     14 行，每行 stage/half/outcome/started_ns/ended_ns/duration_ns/
                             granularity/domain/nominal_domain/note
totals_ns                    wall_clock_total, stage_duration_sum,
                             local_processing, mixed_reads_and_compute, network_or_chain
hops_ns                      §12 的 17 个名字，全都在，没测到的为 null
end_to_end_ns                §13 的 5 个里程碑，没测到的为 null
instrumentation_refusals[]   埋点自己没被允许写成的东西（双关一个阶段、关掉没开的阶段等）
```

`opportunity_id` 直接复用 M7/M5 早就在 `opportunities.jsonl` 里写下的稳定 id
（例：`m7-91342-37581247-0x2a3ce…-0x5b3C1…-100000000000000`），§14 要求「复用一个已存在的稳定身份」
而不是再造一个可以互相打架的第二身份。§37 的敏感数据规则：trace 里没有私钥、没有签名后的字节、
没有任何秘密字段。

# 42.3 Stage Definitions：每个时间戳各自的语义

「started = 什么时刻、ended = 什么时刻」逐条写清。`granularity` 一栏说的是这一行的两个端点
**实际是拿什么精度打的**，不是这段活真的花了那么久；`domain` 是 §11 的成本类。

| stage | started 的语义 | ended 的语义 | 计时来源 | granularity | domain |
| --- | --- | --- | --- | --- | --- |
| `observation` | 这一条生命周期所依赖的**第一个已确认区块**进入本进程的那一刻（§16：confirmed，不是 pending） | 该块的解析与投递完成 | 本次 run 新读的 `Instant`（§15 允许：这是本来就要读的块） | nanosecond（live）/ millisecond（读录制） | network |
| `state_update` | 状态引擎开始把这一块的日志折进状态 | 折完，状态版本可被引用 | M5 已写的块 stamps | millisecond | local |
| `graph_update` | 开始按新状态重建图 | 重建完成 | 同上 | millisecond | local |
| `opportunity_detection` | 开始从图上找候选 | 候选集合交出去（§17：一个 opportunity 被判定成立） | 同上 | nanosecond（live） | local |
| `simulation` | 向 REVM 提交这条 12 步计划 | **结果完整产出**（§18：`simulation_end` = 净利/ Gas/revert 全都拿到） | 引擎自己的 span | nanosecond（live）/ millisecond（历史） | **随状态源**：读录制 ⇒ local；读 `rpc:` ⇒ mixed |
| `risk` | 风险层拿到模拟结果 | 判定产出（§19 独立一格，不再和模拟混在一起） | 已有 stamps | nanosecond | local |
| `preflight` | 开始为 §26 采集事实（连接 + 采集是一段，M7 没单独记「开 lane」这一格，§15 不许补） | 十四项事实（§26 的十三项 + §34 那一项）全部采齐并判完（§20：span 实测，verdict 不新增检查） | lane 自己的 span | nanosecond（live）/ 只有 figure（历史） | mixed |
| `build` | 阶梯写下第一个字节之前的那一格（`created_at_ms` 是记录开格，不是 build 完成） | 未签名的可广播字节就绪（§21） | M7 rung stamps | millisecond | local |
| `sign` | built 那一格 | 原始签名字节产出（§21，`may_read_key` 为假时这一格是 skipped，不是 failed） | 同上 | millisecond | local |
| `submit` | signed 那一格 | **`eth_sendRawTransaction` 得到 RPC 回应**——注意收据不在这段里（§21） | 同上 | millisecond | network |
| `inclusion` | submitted 那一格 | 收据证明已入块（§22 单独一格） | 同上 | millisecond | network |
| `receipt` | —— | —— | 收据就是入块的证明，没有独立 RPC 查询可以把它单独量出来 | 无 | network，恒 `skipped` + 原因 |
| `settlement` | included 那一格 | 两侧余额/资产差核算完成（§23/§24） | 同上 | millisecond | network |
| `profit_verification` | settled 那一格 | ProfitVerified 产出；**M7 那段逻辑一个字没改** | 同上 | millisecond | network |

三种「没有数字」的写法各自的意义（§9，这是本轮最容易写坏的一处）：

```text
completed  两个端点都有 ⇒ duration = 差值
failed     有 started、没有 ended ⇒「进了这一格但没有回答」。永远不带 duration
skipped    根本没进 ⇒「没有尝试」。永远不带 duration，也永远不是 0
```

`skipped` 与 `failed` 谁都不能被均值吸收：`summary.json` 只为 `completed` 的行建分位数行，
`skipped`/`failed` 连样本都不算。

§12 的 hop（17 个名字恒定齐全）与 §13 的五个端到端里程碑都是**从同一批记录里再算一次**，
不新建第二套时间戳：

```text
detection_latency              = Observation.started → OpportunityDetection.ended
execution_preparation_latency  = OpportunityDetection.started → Submit.ended
inclusion_latency              = Submit.started → Inclusion.ended
settlement_latency             = Inclusion.started → Settlement.ended
end_to_end_latency             = Observation.started → ProfitVerification.ended
```

任何一段没跑到，对应里程碑就是 `null`（§13 明令不是 0）。本轮 7 条 trace 的
`execution_preparation / inclusion / settlement / end_to_end` 全是 `null`，
因为唯一的真实提交序列属于 M7 历史，它的 ladder 只有 run 自己的相对毫秒、没有这一 run 的
绝对端点可用（§46 不许重建）。

`totals_ns` 的两个总量按 §10 同时给、互不推导：

```text
wall_clock_total     本 run 从第一个 stamp 到最后一个 stamp 的墙（含阶段之间的排队与等待）
stage_duration_sum   所有测到的阶段之和
```

历史 trace（读 M7 文件）的 `wall_clock_total` 是 `null`：这条生命周期不是这个进程跑的，
没有「它的终点」可以盖（§46）。live/replay 的有：
`route-…37581247` 38,137 ms vs 阶段和 37,250 ms ⇒ 排队/空隙约 887 ms；
replay 那条 32.2 ms vs 28.0 ms ⇒ 4.2 ms。

# 42.4 Measurement Method

```text
时钟      单调 `Instant` 差值，纳秒落盘（`crates/metrics/src/clock.rs` 的 `stamp_ns`）。
          全仓新增生产代码里 `SystemTime::now()` 只出现在 `unix_ms()` 一个函数，
          它只给 `generated_at_unix_ms` 这个文件标签用；summary.json 里
          `generated_at_used_for_durations: false` 明写它没参与任何时长（§44）。
          §2.3 的禁令（不得拿 SystemTime 相减）由 `TraceError` 的路径保证：所有 duration
          都来自同一个 Clock 的 Instant。
单位      ns（`summary.json` 的 `unit: "ns"`）。本文的表都写成毫秒（duration_ns / 1e6）。
不为负    倒序的两个读数一律当作「没有这个数」处理，不夹到 0 之外、不做插值（§34 T8）。
          实测：7 条 trace 里 `duration_ns < 0` 的行数 = 0；
          非 completed 的行带 duration 的个数 = 0。
百分位    nearest-rank，和 M5 的 `metrics.json` 同一个算法（单测
          `nearest_rank_agrees_with_the_m5_series_over_the_same_samples` 直接对着 M5 序列比）。
          再加一条：一个 rank 只有当它的下标严格小于最后一个样本时才报，否则它只是在重印 max。
样本策略  p50 需 ≥2、p90 ≥10、p95 ≥20、p99 ≥100 个样本；不够就 `null` +
          `"reason": "insufficient_sample"`（§29）。门槛写在 summary.json 的
          `minimum_samples_for_rank` 里，机器可读。
不分桶不混算  `sources_are_never_blended: true`；分位数按 `live` / `replay` / `fixture` 各自成表。
          live 的路线 run 绝不折进 `baseline` 子命令（那个加载器把行标成 `replay`，
          §45 禁止把录制和 live 折进同一张表）。
不新增测量  §15 的门槛是硬的：任何一个「要发新请求才拿得到」的测量点都不取。
          因此本轮 `instrumentation_refusals` 数组在 7 条 trace 里全是空的：埋点从未
          被状态机拒绝过（没有二次 close、没有关掉没开过的阶段、没有写过负的 span）。
overhead  一个阶段边界做的事是「读一个时间戳 → 写一个 map 项」（§38）。开关关掉时这两步都不发生。
```

`domain` / `nominal_domain` 两个标签（§11 的归类根因，本轮第二个 commit 修的就是它）：

```text
domain           这段时间**实际是怎么花掉的**
nominal_domain   这个阶段的名字**看起来**该归哪类
两者不同 ⇒ 这个 span 里含节点（例如模拟读的是 `rpc:chain-91342` 的真状态），
           这些时间进 `mixed_reads_and_compute`，不进 `local_processing`
```

判定依据是 run 自己已经写下的字符串（`simulation.state_source`：`RpcStateProvider` 自己写
`rpc:chain-N`，录制回放路径由 `crates/pipeline/src/sim.rs:284` 写
`recorded:<dump 路径>@<块号>`，simulation 层的 dump provider 另一路拼法是 `dump:fixtures/…`），
M8.1 不第二次「判断状态是从哪来的」：只有 `rpc:` 前缀 ⇒ mixed，其余 ⇒ 保持名义类。
§11.1/§11.2 的分界在本轮数据里落成这样：

| §11.1 本地处理 | §11.2 外部/链 | 既读又算（本轮新加的一格） |
| --- | --- | --- |
| `opportunity_detection`、`risk`、`build`、`sign` | `observation`、`submit`、`inclusion`、`receipt`、`settlement`、`profit_verification` | `simulation`（读节点时）、`preflight`（本身就是节点读） |

# 42.5 Historical Baseline（§30：M7 那 6 笔真实交易能给的 latency）

M7 的三份 `route-run.json` 折算出 3 条 trace。**能给的都给了，给不出的写 N/A，没有重建任何一个时间戳。**

| 会话 | source | mode | 计时行数 | detection | simulation | preflight | build | sign | submit | inclusion | settlement | profit_verif | 本地 | 混合 | 外部 | 阶段和 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `route-91342-37563264-1790908382146`（6 笔全部上链、利润核验通过） | replay | submit | 9 | 2,087 | 21,449 | 5,786 | 2,201 | 772 | 253 | 3,367 | 27,221 | 0.000 | 5,060 | 27,235 | 30,841 | 63,136 |
| `route-91342-37563031-1790908149030`（被 §26 第 12 项 fee 闸门拒） | replay | submit | 3 | 2,394 | 21,686 | 5,627 | skipped | skipped | skipped | skipped | skipped | skipped | 2,394 | 27,313 | N/A | 29,707 |
| `route-91342-37562423-1790907541327`（build-only 演练，停在 Built） | replay | build-only | 4 | 3,059 | 21,449 | 5,989 | 2,682 | skipped | skipped | skipped | skipped | skipped | 5,741 | 27,438 | N/A | 33,179 |

单位毫秒。三行都是 14 阶段齐全，空的那 10 来格写的是 `skipped` + 各自的原因。

**这 6 笔真实交易到底能拿到哪些 latency（§53 Q8/Q9 的答复）：**

```text
拿得到：opportunity_detection、simulation、preflight、build、sign、submit、inclusion、
        settlement、profit_verification  ← 九格，全部来自 M7 已经写下的字段
拿不到，且原因逐条写明：
  observation / state_update / graph_update
      M7 的路线 run 是命令行把候选对喂给它的，它自己没做观测。三行 note =
      NO_DISCOVERY_IN_M7（§30 的 N/A），不假装同步完成。
  risk
      M7 记了判定的内容、没记判定的耗时 ⇒ note = NO_RISK_SPAN_IN_M7。
  receipt
      收据就是入块的证明，没有第二次查询可以把它单独量出来 ⇒ RECEIPT_NOT_SEPARABLE。
  wall_clock_total
      这条生命周期不是本进程跑的，没有终点可盖 ⇒ null。
必须读到的 caveat（写在对应行自己的 note 里，不是写在本文里）：
  6 步序列的 ladder 只爬一次，因此**只有 `submit` 与 `inclusion` 两行**带这句
  「this record is the whole sequence and its ladder is climbed once: this span covers
  the first bound transaction, not all 6 steps」——它们是第一笔的时长，不是六笔的总时长。
  `build` / `sign` / `settlement` 三行没有这个 caveat，因为它们量的本来就是同一段 ladder
  上的相邻两格（`settlement` 那一格从第一笔入块起，到整条序列结算完为止，是全程）。
```

上面三个大写的名字（`NO_DISCOVERY_IN_M7` / `NO_RISK_SPAN_IN_M7` / `RECEIPT_NOT_SEPARABLE`）是
`crates/pipeline/src/history.rs` 与 `crates/pipeline/src/latency.rs` 里的**常量名**；
写进 `traces.jsonl` 的是它们各自那一句原文（42.8 引的就是那些句子），JSONL 里没有这三个大写串。

# 42.8 Known Limitations

这些是本轮**已知做不到**的事，逐条给原因；后续里程碑不能假装它们已经解决。

1. **历史观测没有精确 timestamp。** M7 的路线 run 是命令行喂候选的，`observation` 那一格
   在它自己的文件里根本不存在。三行 `skipped` + 常量 `NO_DISCOVERY_IN_M7` 的整句原文（见 42.5），没有插值。
2. **样本量不足以报 p99。** 本轮最大的桶是 2 个样本（M7 的 submit 桶），p90/p95/p99 在任何一桶里
   都是 `null`。全仓 7 份 summary 里只有 6 行带得出 p50，那是 4 个不同的量（单位毫秒）：
   `simulation` 21,449（hop 行 `simulation_duration` + 阶段行 `stage_duration:simulation`）、
   `preflight` 5,627（同样两行）、`opportunity_detection` 2,087（一行）、
   `total:stage_duration_sum` 29,707（一行）。
   live 侧永远是 1 个样本/会话：一次 run 写一个目录、一行 trace。
3. **历史 trace 只有跨度、没有时刻。** `granularity: millisecond`、`started_ns/ended_ns: null`、
   `wall_clock_total: null`。§30 禁 `reconstructed_time`、§46 禁插值，所以这是上限。
4. **`receipt` 与 `inclusion` 实测不可分。** 收据本身就是入块的证明；要分它们必须再发一次
   `eth_getTransactionReceipt`，而 §15 禁止为测量新增请求。因此 `receipt` 恒为 `skipped`
   并注明 `RECEIPT_NOT_SEPARABLE`。
5. **§26 闸门拒绝在 trace 里的形状是「Preflight completed（只带 span）+ 其后每一行 skipped
   的 note 里引用闸门原话」**，没有一个 outcome 词叫 `rejected`。例（`route-…37581286` 的 build 行）：
   `the lifecycle never reached this stage: invalid intent: the transaction carries
   max_fee_per_gas 1000632 and the fee read at block 37581314 says 1000634 — …`。
   把 verdict 做成一等字段属 M8.5 observability；本轮不新增任何检查去填它（§15/§20）。
6. **同上一条的根因**：ladder 只存 `built_at_ms`，没有 `preflighted_at_ms`。所以
   「闸门清了、但第一个字节之前失败」和「闸门拒了」在 stamps 上完全同形（都只有 `created`）。
   本轮的处置是**一律记 `skipped`**（欠称，不虚称「进了这一格没回答」）。
   这轮我一度把它「修」成 `failed`，取证书 `crates/execution/src/sequence.rs:1453`
   （`preflight_cleared` 在任何构造/签名/发送之前拒）证明那个改动会把一次闸门拒绝写成
   「build 跑过但没回答」，属于 §9 禁止的那类谎，已回退（diff 留档，未进 commit）。
   要真正分开两者，需要 M8 后续给阶梯加一格 `preflighted` 的 stamp —— 那是执行语义的改动，M8.1 不碰。
7. **`git_revision` 只证明「哪个 commit 编译出的二进制」，不证明工作树 clean。** 值由构建时的
   `GIT_REVISION` 环境变量注入（`crates/pipeline/build.rs` 只让构建指纹跟着它）。本轮每条证据
   都是从 clean tree 重新构建后跑的（磁盘上 7 个 `summary.json` 全部是
   `d4f61a912bdc1d8660d145f6e745dc9cbc60a0c1`），但这不是文件能自证的事。
8. **`TraceSource::Fixture` 没有生产者。** 枚举里有这一类（§45 要求分得开），metrics 的
   单测会用；但 §33 那条确定性测试走的是真实录制，所以它正确地自称 `replay`。
   本轮没有把任何合成行情标成 `fixture` 来充数。
9. **M7 的字段名与 §12 的阶段名不完全同义。** `opportunity_detection_latency_ms` 的内容其实是
   §13 的 observation→opportunity 里程碑（M7 在问节点要 head **之前**就起了这一格）。
   历史表照 M7 的名字放进 `opportunity_detection` 行，并在该行 note 里说明它含什么（§42.3 的 caveat）。
10. **模拟里的 RPC 读次数没有被记录。** dump 记 `reads`（可比的录制 dump 记着 64 次），
    `RpcStateProvider` 不记次数。所以 §42.9 候选 1 的「可能原因」目前只有代码路径可指，
    没有实测计数。补齐它是 M8.5 的活。
11. **SequencerDirect 与 WS head 仍是 BLOCKED**（M5/M6 实测），因此 live 侧的 `observation`
    只能来自 HTTP 轮询，其 hop 成本天然带着轮询节奏；这不是本轮能改变的链侧事实。
12. **domain 归类只认 run 自己写下的字符串。** 没有 `simulation.state_source` 的 run 保留
    阶段名义类（`nominal_domain == domain`），这一条写在每份 README 里，不做猜测。
13. **同一个检查项在代码里有两个名字（本轮写文档时新发现，未修）。**
    `PreflightCheck::InputAssetBalance::name()`（`crates/execution/src/preflight.rs:93`）返回
    `"input_token_balance"`，而 `preflight.json` 里 serde 按变体名 snake_case 输出的是
    `"input_asset_balance"`。两个都是真字段，指向同一项检查；本轮没碰它（它在执行层，M8.1 §1 不许动），
    记给 M8.5 observability 一并清理。

# 附录 A. 本文的表是怎么读出来的（不是手抄）

本文所有数字都由脚本直接从 `data/evidence/m8/latency/*/traces.jsonl` 与同目录
`summary.json` 读出，字段路径写在每张表的标题或单元里。复现用的最小片段：

```python
import glob, json
MS = 1_000_000
for path in sorted(glob.glob("data/evidence/m8/latency/*/traces.jsonl")):
    for line in open(path):
        if not line.strip():
            continue
        t = json.loads(line)                       # 一条生命周期
        for s in t["stages"]:                      # 恒定 14 行
            print(t["session_id"], s["stage"], s["outcome"],
                  (s["duration_ns"] or 0) / MS if s["duration_ns"] is not None else None,
                  s["domain"], s["granularity"])
        print(t["totals_ns"], t["end_to_end_ns"])
```

自洽检查（本轮实测全部成立，7 条 trace）：

```text
每行 stages 数量 == 14                                   ✓ 7/7
local + mixed + network == stage_duration_sum            ✓ 7/7（逐条相加后精确等于）
任何 duration_ns < 0 的行                                 ✓ 0 行
skipped/failed/cancelled 却带 duration 的行               ✓ 0 行
instrumentation_refusals 非空的行                        ✓ 0 行
summary.json 里 generated_at_used_for_durations          ✓ 全部 false
sources_are_never_blended                                ✓ 全部 true
```
