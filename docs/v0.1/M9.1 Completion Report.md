## 白话结论（先看这一屏）

**结论：M9.1 = COMPLETE。** 判定 = `COMPLETE`。

一句话讲清这次做了什么：**我们从链的历史里把「有人开过池子」这件事一条一条挖出来、逐条查户口，最后只把查清楚的 80 家放进了原来那张名录里，剩下 5 家因为查不到储备而当场否决，并且每条否决都写清了是在哪一步、因为什么被否。**

打个比方：链上每开一个交易对，就会在账本里贴一张「开张告示」（`PairCreated` 事件）。我们做的是：

1. **看告示**：在 5 段历史区间（合计 50,000 个区块）里把所有告示收上来，收到 **85 张**，对应 **85 个**互不相同的池子地址，零重复、零读不懂的告示。
2. **查户口**（每条都要问合约本人，且都钉在同一个历史区块上问）：这张告示是不是真的由合约贴的、合约自报的两个代币是不是和告示一致、合约有没有真的公布过储备。85 条全部走完前两步，**80 条**走完第三步，**5 条**在第三步被否决。
3. **登名册**：80 张合格凭证写进**原有的** Registry（没有新造名册），再喂给状态快照和行情图。图上这一次只有 **48 条**报价边、**56 个**池子被跳过——原因全部是「它的最新一次报价不在快照那个区块上」，也就是**验证过 ≠ 此刻新鲜**，图自己把这个区别说清楚了。

**这次没有做的事，同样重要**：

- **发现 ≠ 信任**（§16）：告示只是「有人这么声明」。我们把 85 条全部当声明处理，一条都没有因为告示好看就直接进名册。85 − 5 = 80 这条算式的存在，就是这句话的证据。
- **已验证池 ≠ 可交易机会**（§25、`not_claimed`）：80 个池子我们逐个问过合约行为像不像池子、公布过什么储备，**但没有一个被拿去算过价差、构造过交易、签过名、广播过**。本次运行签名 0、广播 0、真实套利 0（`discovery-summary.json#/rpc`）。
- **手续费仍然全部未知**（§14）：80 张凭证的 fee 字段是 `None` × 80，我们没有把 `997/1000` 这种「行业常识」偷偷填进去当作已知数。

**改动面**：生产代码只动了 `crates/protocol/`（加解码，3 个文件）与新 crate `crates/discovery/`；`chain / simulation / pipeline / state / graph / execution / cli` 的**被跟踪文件改动数实测为 0**（§23「不新增缓存、不跨阶段复用状态」在结构上成立——我们连一行缓存代码都没碰）。RPC 全部走既有 `ChainAdapter`，两把运行各 441 / 440 次调用，方法只有 4 种且全是只读。

## 4. Discovery Source（§5、§6、§8）

- **形态**：`HistoricalPairCreatedSource`，实现发现源抽象，只问历史，不订阅、不预测。
- **提出的问题**（`discovery-summary.json#/source/question_asked`）：对该区间做一次 `eth_getLogs`，topic0 固定为 `0x0d3648bd0f6ba80134a33ba9275ac585d9d315f0ad8355cddefde31afa28d0e9`，**地址列表为空**。
- **分片**：片宽 4,999 块，节点单次日志上限 20,000 条——两个数字都是这台节点此前被实测出来的边界，遇到区间或片宽不合法直接报错，不悄悄夹窄（`error.rs`；`scanning.rs::a_window_at_the_node_s_ceiling_is_an_error_not_a_shorter_census`、`an_impossible_range_or_chunk_is_reported_not_clamped`）。
- **解码**（§6）：`PairCreated(address indexed token0, address indexed token1)`，data 是两个 `uint112` 槽位；三种真实存在的形状（indexed pair / inline pair / 只有两个 token）都被测过。畸形数据产出「一行畸形记录」而不是「一条被静默丢弃的日志」（`malformed_pair_created_data_produces_a_row_and_no_candidate`）。
- **不需要完整 DEX 名单**（§8）：地址过滤器为空即是这条要求的实现；本次 85 条候选里有 5 条最后被验证层否决，说明源本身不做准入。

## 6. Candidate Count（§4、§7）

85 条候选 = 85 条 `PairCreated` 日志 = 85 个不同池子地址。三个数相等说明两件事：这台链在这 50,000 块里没有「同一个池被重复声明」，也没有「一条日志解出两个候选」。

每条候选携带的 provenance（§7）：链 id、池地址、声明区块、日志 index、发出者地址、以及它落在哪个窗口——逐行在 `candidate-pools.json`，行身份是 `chain/pool/block/logIndex` 语义键，不是行号。

一个值得单说的实测细节：**同一个地址被声明两次会是「两条候选、一个池」**，这条规则有测试钉住（`scanning.rs::two_claims_of_one_address_are_two_candidates_and_one_pool`），只是本窗口没出现（重复日志 0）。

## 7. Verified Count（§9–§13）

**80 条**通过全部三个阶段，成为已验证池并拿到凭证（`discovery-summary.json#/verification/verified` = 80、`#/integration/attested` = 80）。

80 这个数字之后没有停在纸面：

- 80 张凭证全部写入既有 Registry，Registry 里 80 个池，重复声明 0，被存储层拒绝 0；
- 与「已提交名册」（4 个池）合并的结果是 `Ok`，合并后 84 个池；
- 状态快照落在区块 37,224,031，图上生成 48 条报价边，56 个池被跳过（原因全为 `NotAtTargetBlock`）。

**48 条边不等于 48 个池**，这是本节唯一容易被读错的地方，所以直接数表：48 条边按 `pool` 去重后是 **24 个池**，每个池恰好 2 条边（`reserve_in`/`reserve_out` 互换的两个方向，实测边的分布 `Counter({2: 24})`），`state-graph-integration.json#/graph/pool_count` 也记着 24。被跳过的 56 个池按地址去重同样是 56 个。**24 + 56 = 80**，正好等于凭证数——图的输入就是这 80 个池，一个不多一个不少；其中 24 个在快照区块上报价，56 个因为最新 `Sync` 不在那个区块而被跳过。README 第 32 行说的是同一件事。

## 8. Rejected Count（§19 的「每条为什么」）

**5 条**被否决，全部停在 `state` 阶段，原因全部是 `no_authoritative_state`（`#/verification/rejected_by_stage`、`rejected_by_reason`）。

这不是「5 条一样的批量结论」——每条都带自己的搜索区间和看到的日志条数。举一条完整记录（`rejected-pools.json` 第 1 行）：

```text
pool         0x133e57116919b80b29fcbeb6ae74b70494529b16
discovery    28,543,905
identity     91342/0x133e5711…/28543905/17/state
stage/reason state / no_authoritative_state
detail       no Sync(uint112,uint112) from this pool in 28543905..=28549999
             (0 logs of any shape were seen)
reads        calls_succeeded 4 / calls_failed 0 / sync_logs_seen 0 / sync_present false
```

门禁 `every_rejection_row_explains_itself` 要求每条否决必须有：阶段、原因、非空说明句、`reason_derives_from_stage` 为 true、指向记录的字段对象、以及搜索区间数组；并且表内原因分布必须等于汇总里的分布。**「0 条日志」与「有若干条但读不懂」在模型里是两个不同结论，不允许合并**——这是 §12 状态验证的一条硬规则，NC7a/NC7b 分别对着这两种沉默。

5 条否决的共同点：四次合约读取全部成功（代币两个、储备一次、字节码一次），但这个池在自己声明之后、区间之内从未发布过 `Sync`。没有人公布过它的储备，就没有可交易的状态——这是**判定**，不是数据缺失。

## 9. Verification Rules（§9–§13 的规则表）

阶段顺序固定为 Provenance < Identity < Tokens < State，前一个不过就不进下一个。表规则写在 `#/verification/rule`：**某阶段到达数 = 候选数 − 在该阶段或更早阶段被否决的条数**，所以 identity/token = 85、state = 80 与 rejected = 5 是同一件事的两种说法，不是两个来源。

| 阶段 | 问什么问题 | 判定材料 | 失败原因串 |
| --- | --- | --- | --- |
| Provenance（§9 来源） | 声明、代币、池三方是不是同一条链；读取是不是钉在声明区块上；读取是不是关于这个池本身 | 三个 chain id 是否相等、记录自己的区块字段、记录指向的池地址 | `chain_mismatch`、`read_not_pinned_at_discovery_block`、`read_about_another_pool` |
| Identity（§10 V2 身份） | 这个地址是不是一个真的会答 `getReserves()` 的合约 | `eth_getCode` 有没有代码、`getReserves()` 是否成功且至少三个词 | `no_bytecode`、`reserves_unreadable` |
| Tokens（§11 代币） | 告示上的两个 token 与合约自己报的是否一致；两侧是否不是同一个币 | `token0()` / `token1()` 的回答 | `tokens_unreadable`、`claimed_tokens_disagree_with_contract`、`same_token_on_both_sides` |
| State（§12 状态） | 这个池自己有没有对外公布过储备 | 从声明区块起在区间内搜该池的 `Sync(uint112,uint112)`，并读那条日志 | `no_authoritative_state` |

每条原因都被代码绑死在一个阶段上（`RejectionReason::stage()`，`crates/discovery/src/verify.rs:117`），表里出现的「阶段 × 原因」组合不可能凭空造出来，门禁 `every_rejection_row_explains_itself` 与 `reason_derives_from_stage` 字段一起钉住这一点。

**§12 里最要紧的一条设计**：合约 `getReserves()` 的回答和池自己发的 `Sync` 是两种东西，代码把它们做成两个类型——`ContractVerificationState`（证明合约行为像池子）与 `AuthoritativeMarketState`（唯一能变成 `PoolState` 进状态层的形状），后者**只有一个接受 `SyncRecord` 的构造函数**。也就是说「拿 `getReserves()` 的读数冒充市场状态」这件事在类型层面写不出来，不靠纪律靠编译。

Provenance 阶段的三条检查（尤其 `read_about_another_pool`）是 §7 的落点：`verify` 是纯函数，记录里写的地址是它与候选之间唯一的连线；没有这条检查，一条声明可以被**另一个池的健康读取**救活。

## 10. Fee Handling（§14）

**80 张凭证的手续费全部是 `None`**（`discovery-summary.json#/integration/fees_attested` = `{"None": 80}`）。

- `attest.rs` 产凭证时不查费率函数、不猜常数；下游谁需要费率，谁自己去问（M3/M7 已经证明同对不同池费率可以不同，写死会污染下游）。
- 证据目录里出现的 `997` / `1000` 只可能是储备数值或代码摘要里的十六进制片段，所以门禁不是字符串扫描而是字段级检查：`no_fee_was_substituted_and_no_write_ever_left_the_run` 直接读 attestation 的 fee 字段与整表的 `fees_attested` 分布。
- **NC9** 把「未知被填成已知」这个失效模式当负控制跑了一遍：一条健康候选的 fee 被改成 `997/1000` 后，表里那条记录被判定为不成立，行为符合预期（`negative-controls.json` 中 `NC9` 行，`invalid_condition_rejected: true`）。

## 11. Negative Controls（§20）

§20 要求的九种失效条件**全部覆盖**，另外多加了三种（一条来自 §22 的钉块失效、一条来自存储层、一条是正控制）。`negative-controls.json` 实测：`controls` 表 **24 行** = 23 行负控制（`NC*`）+ 1 行正控制（`PC0`），所以同文件里 `negative_controls` = **23**（只数负控制）、`rows_that_behaved_as_expected` = **24 / 24**、`all_expected` = true、`conditions_covered` = 九项名单（逐项名列在字段里）、`controls_beyond_the_nine` = 3 条说明。两个数不是互相打脸，是口径不同，读表时看字段名。

## 14. Limitations

诚实的边界，逐条写清「没做到什么」：

1. **只扫了 50,000 个区块，不是全链历史。** 5 段窗口共 5 万块，85 条候选；全链有多少 `PairCreated` 本阶段没回答（M7 的普查是另一套口径，不能拿来当这里的分母）。
2. **真实数据只跑出了 `no_authoritative_state` 一种否决。** 其余八种失效条件（代币不符、同币两侧、错链、畸形数据、`latest` 读取……）目前**只有负控制证据**，没有在这 85 条真实候选上自然发生过。所以「这些守卫有效」的证据来自受控篡改，不来自真实市场遇到它们。
3. **图这一步只报价了 48 条边。** 80 个已验证池里 56 个被 `NotAtTargetBlock` 跳过——它们的最新 `Sync` 不在快照区块 37,224,031 上。这是**历史快照的固有性质**（§17），不是漏读，但它意味着「验证过」与「图上可用」之间还差一次新鲜度。
4. **两把调用数差 1（441 / 440）**，差额是连接自发的 `eth_chainId`。已在 `#/rpc/note` 里标明，不是重复读取或缓存差异。
5. **手续费一律未知。** 80 张凭证没有一张带 fee，因此本阶段的产出**不能直接进套利计算**（M3/M7 的利润模型需要费率）。这是 §14 要求的取舍，不是待补的洞。
6. **真实普查测试默认 `#[ignore]`。** 它需要节点与 441 次只读调用；离线复现只能重放已提交的 `raw/`，不能重新问链。
7. **单端点。** 全部证据来自同一台节点（摘要 `rpc-faa716cada04a9ef`），跨端点一致性本阶段没测。
