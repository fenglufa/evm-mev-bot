### 6.4 「instrumentation 没有多问一次」是怎么证的（§34-M，不是承诺）

`crates/chain/tests/rpc_trace_safety.rs` 用 `std::net::TcpListener` 起了一个**自己 tally 每个 POST**
的进程内 JSON-RPC 桩（tokio 1.52.1 没开 `net`/`io-util` feature，所以用标准库线程）。核心那条测试做三件事：

1. 带 sink 的 adapter 走一遍 `connect` + 三种状态读 ⇒ 桩收到的**清单精确等于**
   `[eth_chainId, eth_getCode, eth_getBalance, eth_getStorageAt]`，sink 里的 event 数、顺序、`rpc_id` 都对得上；
2. **孪生的不带 sink 的 adapter** 打到第二个桩 ⇒ 收到**同一份清单**（`untouched.received() == stub.received()`）；
3. `dropped_events() == 0` 且 `refusals().is_empty()`。

重试那条测试把「烧掉一次超时再重试」钉成**一条记录两个 attempt**
（桩侧 arrivals = `[eth_chainId, eth_getCode, eth_getCode]`，sink 侧 `events = 1`、
两个 attempt 的 `outcome` 依次是 `http_status` 与 `ok`、
`finished − started == duration_ns`）。
节点直接拒绝那条钉成 `ChainError::RpcRejected` + 1 个 attempt（记录没有改变上层看到的错误类型）。

同一块（如 37599910）、同一组 6 个地址被反复读。`times_read` = 这份状态在这一 run 里被问了几遍，

| `eth_getTransactionCount` | 6 | 5、3、3、3、2、2 | **12** |
| `eth_getStorageAt` | 0 | —— | 0 |

其中最扎眼的三个键都是 **sender 自己**（`0xd450630c…`）：

| dedup_key（形如 `method\|chain\|block\|address`） | times_read |
| --- | --- |
| `code\|91342\|37599910\|0xd450630c…` | **6** |
| `balance\|91342\|37599910\|0xd450630c…` | 5 |
| `nonce\|91342\|37599910\|0xd450630c…` | 5 |

两个候选池各被读 4 遍 code、3 遍 balance、3 遍 nonce；WETH、mid token、`0x4200…11`

标签块（`latest`/`pending`）与编号块永不撞键（`a_block_tag_is_never_the_same_key_as_a_block_number`）。

**这 33 秒里有 18–21 秒花在「问一件本次已经问过、而且块已经钉死不会变的事」上。**
其中 `eth_getCode` 的 17 次重复单独就吃掉 11.9–13.8 秒 —— 全场最贵的一个可归因项。

> 注意口径：41 次重复**不是**「41 次免费的重读」。每次重读都真的付了一次约 235 毫秒起的单程。
> 也**不是**说首读的 14–15 秒合理 —— 它只是「本轮没有证据说它可以省」。

## 8. Serial / overlap findings（§33.8 → §24 Q3）

**完全串行，一次都没有并行。**

| run | rpc_wall | rpc_sum | rpc_union | overlap | serial_wait | gap | non_rpc | max_concurrency |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 37599910 | 32 929.5 | 32 871.3 | 32 871.3 | **0** | 32 871.3 | 58.2 | 59.0 | **1** |
| 37599962 | 33 773.1 | 33 730.4 | 33 730.4 | **0** | 33 730.4 | 42.6 | 43.4 | **1** |
| 37600021 | 33 688.7 | 33 644.2 | 33 644.2 | **0** | 33 644.2 | 44.5 | 45.3 | **1** |

（单位：毫秒。`serial_or_overlap` 在文件里对三个 run 都写着 `serial`。）

三条互不相同、但都指向同一结论的读法：

- `rpc_sum == rpc_union == serial_wait`：**「加起来」和「盖住多少地面」是同一个数**，
  意味着没有两个区间重叠过一纳秒。
- `max_concurrency = 1`：扫描线在任何时刻最多只看到一个在飞请求。
- `rpc_wall ≈ simulation_duration − non_rpc`：墙钟几乎全被「排队的 RPC」盖住。

`rpc_gap`（42.6–58.2 毫秒）是**窗口内没有任何请求在飞的空隙**（第一次发起之前和最后一次落地之后，
加中间的空档），它不是「本地计算」，是这段模拟没在等节点的那一小截。

**为什么 REVM 会串行**：状态读是被 EVM 逐条 demand 出来的 —— 一条 `SLOAD`/`BALANCE`/`CODE` 操作
要值才能继续跑，所以下一次读**必须**等上一次落地。本轮**没有**去证「哪条指令触发了哪次读」
（那要动 simulation crate，§2 禁止），只能证**结果形状是串行**。（→ 本报告 §10 的 C。）

| 37599910 | 32 930.3 ms | 32 871.3 ms | **998‰** | 59.0 ms（2‰） |

`non_rpc_duration_ns = span − union`（**减的是并集，不是求和** —— 任务书 §11 点名的那个错误；

结论：**一次真实 simulation 的总时长里，可以归因于 RPC acquisition 的部分是 99.8 %–99.9 %；
本地（REVM 计算 + 状态转换 + 编排）只占 43–59 毫秒。**
这条同时把 M8.1 留在文档里的那个问句（「24 秒到底花在哪」）收掉：不在 CPU 上。

## 10. Bottleneck classification（§33.10 / §25）

```text
primary   = D  Duplicate state-read bound
secondary = A × B  RPC volume bound × RPC latency bound
C  Serial dependency bound  —— 是让 A×B×D 全部藏不起来的放大器，不是独立的第二项
E  Provider/connection bound —— 本轮实测判死
F  Local simulation compute bound —— 本轮实测判死
```

每一条挂它自己的证据（不是「RPC 很慢」）：

| 分类 | 判定 | 证据（可直接回指字段） |
| --- | --- | --- |
| **D 重复读（primary）** | 成立，且是可归因的最大单项 | 41/80 次是重复；重复那 41 次花掉 **18 058–20 808 ms = RPC 时间的 549–617‰**；`eth_getCode` 的 17 次重复单项 11 939–13 779 ms。键带链+块，`unkeyed_calls: 0` ⇒ 不是漏计也不是借键 |
| **A 次数（secondary 之一）** | 成立 | 单 run 80 次调用、`sum` 32 871–33 730 ms —— **次数 × 地板就是总量的下界**：即便每次只花 235 ms，80 次串行也要 18.8 s；实测 33 s |
| **B 单次延迟（secondary 之一）** | 成立 | 三个 run 合计 240 次调用的 `min` = **232.5 ms**，任何方法都没低于它；`eth_getCode` p50 374–500 ms、max 1.9–3.0 s ⇒ 地板之上还有长尾 |
| **C 串行（放大器）** | 成立 | `max_concurrency = 1`、`rpc_overlap_duration_ns = 0`、`serial_wait == union == sum`（三个 run 都是）⇒ **没有任何延迟被并发隐藏**，D 与 B 的成本是**相加**而不是相互遮盖 |
| **E 提供方/连接** | **判死** | `failed_calls = 0`、`retried_calls = 0`、`total_attempts = total_calls = 80`（每个 run）；240 条 `attempts[].outcome` **全是 `ok`**、240 条 `error_class` **全是 `null`** ⇒ 这 33 秒**不是**超时与重传堆出来的 |
| **F 本地算力** | **判死** | `non_rpc_duration_ns` = **43–59 ms**，占 span 1–2‰；REVM 与状态转换在算，但它们是两位数毫秒，等节点是五位数毫秒 |
| **G 证据不足** | 不适用 | §24 五问全部有实测答复，无需 `UNKNOWN`（见本报告 §13） |

**为什么 primary 是 D 而不是 A×B**：A×B 给的是**下界** —— 80 次串行、每次按 232.5 ms 的地板算，
是 18.6 s；实测 33 s。这中间多出来的一截正好落在重复读上：41 次重复实测花掉
**18 058–20 808 ms**（本报告 §7.3）。所以 D 是**唯一一个既能量出金额、又明确属于
「问了不必问的东西」**的项。把它砍掉之后剩下的那一截（39 次首读，实测 12 922–15 006 ms，
地板下界 ≈ 9.1 s）就只能靠换 provider 或改并发再往下压 —— 两条都是本轮禁止碰的。

禁止条款照守：本文**没有**写「RPC is the bottleneck」这种没有分类的断言 ——
写的是「RPC 采集占 998–999 ‰（= 99.8 %–99.9 %），其中 55–62 % 是重复读」（每一句都有字段兜底）。

## 11. Limitations（§33.11）

1. **样本只有 live，且只有 3 个 run。** replay / fixture 的端到端样本数 **0**：
   路线 run 只在 live 一条路上（`arbitrage.rs:269` 的 `HttpChainAdapter::connect`），
   `--rpc-trace` 挂在这条路上。隔离逻辑（分桶、永不混合、fixture 单独标注）有单测，
   **但机制不等于市场数据**。
2. **桶的样本数是 1，不是 3。** 每个 run 一个证据目录、目录里 `simulations = 1`，
   所以 per-source 的 rank 全部 `null` + `insufficient_sample` + `minimum_samples`，只有 min/max 与
   `integer_mean` 可用；跨 run 的「一致性」是本报告逐文件对齐读出来的，不是分布统计。
   方法表的分位取**一次 run 内的 18–23 条调用**：p50/p90 有值，p95 只在 `eth_getCode`(23) 与
   `eth_getStorageAt`(20) 有值，p99（门槛 100）与 `eth_getBlockByNumber`（1 条）的一切 rank 都是 `null`。
   要做真的跨 run 分布，需要把多个 run 写进同一个桶 —— 本轮没有这个写入路径。
3. **记录点在字节上线那唯一一处 ⇒ 一次调用的内部拆不开。**
   请求构造、等节点、解码、状态转换是一段 `duration_ns`（任务书 §17 的 `breakdown_unavailable`）。
   本轮把「连接问题 vs 节点慢」分开的唯一手段是 `attempts[]`，不是子计时器。
4. **检测阶段的读取不在这份 trace 里。** sink 只挂在**模拟自己要读的那个 adapter** 上，
   所以 `price_legs`（建模拟之前定价用的读）和执行侧（`crates/execution` 经 submitter 发的一切）
   与 WebSocket 客户端自己的请求路径都**不在**这些数字里 —— 写在这里而不是算成 0。
5. **一次 run 只有一个 simulation。** 每桶 `simulations = 1`，`calls_per_simulation` 的分布只有
   1 条样本（文件里带着「a single sample … not a distribution」的 `note`）。
6. **串行的「原因」只证到形状，没证到指令。** 本轮能说的是「80 次里最多只有 1 次在飞」，
   不能说「因为第 N 条 `SLOAD` 依赖第 N-1 次的结果」—— 那要插进 simulation crate，§2 禁止。
7. **任务书 §31 的开销对照只有 2 个 untraced 样本**（本报告 §9.1），且它与 traced run 分处两个时间窗
   （M8.1 的 24 s 级 run 在 10-02 15:32–15:34，本轮的 33 s 级 run 在 20:43–20:48，同一天相隔约 5 小时）
   ⟶ 只提供括住，不提供分布，也不做「5 小时里节点变了多少」的比较结论。
8. **本轮不判「20–25 秒」这个数对不对。** 任务书里的区间是 M8.1 观测；本轮三次是 **32.9–33.8 秒**，
   差值归因于节点的应答速度（本报告 §9.1 的对照），不是代码。

## 13. §24 五问的答复
