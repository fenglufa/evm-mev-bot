## 1. 白话版（不含术语，先读这段）

**单位约定先说清**：证据文件里存的全部是**纳秒（ns）**。1 毫秒 = 1 000 000 纳秒，1 秒 = 1 000 000 000
纳秒。下面出现的每一个毫秒/秒，都只是把某个 ns 字段的小数点左移 6 位/9 位读出来的**同一个数**，
不是第二次测量，也不是估算。‰（千分比）同理：证据里存的是「分子 × 1000 ÷ 分母」的整数，两侧都是实测值。

打个比方：一次 simulation 就像打电话问 39 个问题。

- **问一次要等 0.23–0.86 秒**（最快的一次 229 781 708 ns ≈ 230 ms，最慢的一次 860 362 666 ns ≈ 0.86 s）。
  这几乎是节点的"起步价"，不是我们拨号慢。
- **我们是一个一个问的**：39 个问题排队，前一个没答完绝不问下一个。所以"打完这通电话"的
  总时长 ≈ 39 次等待时间之和（10.3 秒 ≈ 10 316 717 665 ns）。
- **打电话期间我们自己在算的东西只占 2‰**（28–30 ms / 把）：也就是 10 秒里有 9.98 秒在听电话，
  0.02 秒在记笔记。
- **两次提问之间的空白**（想下一个问题该问什么）每把 25.8–27.3 ms，只占窗口的 2‰。
  上一轮（M8.2）这个空白是 42.6–58.2 ms，**已经缩短了**。
- **重复提问已经归零**：同一个区块里同一个问题被再问一次的次数是 **0**（M8.2 是 80 次里有 41 次重复）。
  这一条是 M8.3.1 的成果，本轮**重新测量确认它没有回退**。
- **电话外面还有电话**：一次完整的生命周期（从看到行情到决定要不要下单）里，
  simulation 只是其中一段。实测三把的全生命周期墙钟是 18.75–22.50 秒，其中
  simulation 段 9.93–10.96 秒，**preflight 段 6.34–6.65 秒**，detection 段 1.43–1.50 秒，
  observation 段 0.50–0.55 秒。也就是说：**继续把 simulation 从 10 秒压到 8 秒，
  对"整条链路 20 秒"这件事只解决一小半。**

所以这次真正的发现是两条，而不是预设的那一条：

1. simulation 内部的成本结构已经**变成"单次延迟 × 次数、且完全串行"**，没有重复、没有本地计算可挖；
   想再快只能动"次数/并发/节点"这三样，而这三样本轮**明令禁止**（§18）。
2. 生命周期里**出现了一条和 simulation 同量级的第二条 RPC 大头**（preflight + detection 合计
   14.09 秒 / 三把，simulation 是 31.15 秒 / 三把），它此前不在诊断范围内。

每个 slot 在合并表里被读 3 次 —— **即每把 run 各读 1 次**，不是同一把里读了 3 次
（每把 raw 表里 slot 的 `reads` 全是 1）。所以 storage 内部**没有可复用的重复**（§1 第 6 问的答：
剩余 39 次里没有"还能再复用一次"的数据）。

**§7 语义标注：全部 `unknown`。** 文件里 `semantic` 字段给出的理由（原文，不是我的转述）：
本构建里 `reserve0 / reserve1 / blockTimestampLast` 这些名字**只**出现在解析池子 Sync 事件日志和
一次 `getReserves()` 的 `eth_call` 返回值里，**都不是 `getStorageAt` 问的那个 storage word**，
所以 §7 禁止用 slot 编号去猜名字 → 四个地址的 `semantic` 全为 `"unknown"`。这一条是"没答案"，
但它是有凭据的没答案，不是偷懒。

**§8 能不能合并（batch）：只记候选，不实现。** `mergeability`：
`status: "candidate_only_not_implemented"`，`question` 是「同一个地址的 storage 读是不是共享
端点、区块、simulation」。答案分两层：

- **每把 run 自己的表（`raw/*/storage-breakdown.json`）：4/4 个地址全部 `per_simulation_batchable: true`**
  —— 同一把 run 里同一个地址的所有 storage 读都落在 same_block / same_endpoint / same_simulation
  （20 次读）。这就是 batch 的**事实基础**。
- **合并表：4/4 个地址 `per_simulation_batchable: false`** —— 因为跨三把 run 时 block 和 simulation
  各不相同（`distinct_blocks: 3`）。文件自己的 `answer_scope` 说清了这层：batch 的候选只能是
  "某一把 simulation 自己的读"，跨 run 的分组不算。

**结论（Q3）**：`eth_getStorageAt` 是**最大的单一成本项**（RPC 之和的 519‰、窗口的 517‰），
这一点和 M8.2 的直觉一致；但它在 A–G 里**不构成一个独立的主分类**（见 §12）——
因为 519‰ 是"次数 × 单价"的乘积，而单价 230 ms 级、并发 1，这两件事分别属于 A 和 B/C。

## 11. §15 Provider latency 仍然单独读：慢 ≠ 节点慢

任务书要求不要因为"上一轮成功了就默认剩下的是 provider 的锅"。本轮用两个独立口径读同一件事：

1. **单次成本的地板**：所有五种方法里**最快的一次调用**是 `eth_getStorageAt` 的
   229 781 708 ns ≈ 230 ms（`rpc-summary.json` → `per_method[].min_duration_ns`）。
   即"最便宜的一次问话"就要 230 ms。五种方法的 min 全落在 230–241 ms 区间
   （storage 229 781 708 / code 236 928 875 / balance 235 435 334 / nonce 230 778 500 /
   header 240 516 750），**方法之间没有数量级差异**。
2. **失败/重试口径**：`total_attempts: 117`、`failed_calls: 0`、`retried_calls: 0`、
   `successful_calls: 117`，`error_classes` 为空。E 类因此是 `ruled_out_by_measurement`
   （0‰）—— 时间付给了"节点在回答"，不是"连接在失败"。

本轮**不能**回答的（这是缺什么，不是结论）：三把 run 都打在**同一个端点指纹**
`rpc-faa716cada04a9ef` 上（`storage-breakdown.json` → `addresses[].endpoint_ids`、
`rpc-gaps.json` → `per_simulation[].endpoint_id`）。**单端点样本无法区分"这个节点慢"和
"这条链所有人都这么慢"**；而证据文件里的 `provider_duration_field` 也明说了这一层的分辨率：
一次调用只在"变成线路上的字节"那一点计时，请求构造、等节点、解响应、转状态**不可分**，
只能报成一个 provider duration。§18 又禁止 provider switching，所以本轮不做对照。

## 12. §19 A–G 归类：主分类 G，次要 A / B / C

`bottleneck-classification.json` → `per_source[0]`（七类都在表里，verdict 由规则给出，不靠人工挑）：

| 类 | 名称 | 份额 | verdict | 该规则读了哪两个整数 |
| --- | --- | ---: | --- | --- |
| A | RPC volume bound | **860‰** | dominant | 117 次 × 最快一次 229 781 708 = 26 884 459 836 ns / 窗口 31 236 639 668 ns |
| B | RPC latency bound | **997‰** | dominant | union 31 148 791 915 / 窗口；地板 100 000 000 ns，实测最快一次 229 781 708 ns ⇒ 不被地板排除 |
| C | Serial dependency bound | **997‰** | dominant | serial_wait 31 148 791 915 / 窗口；`max_concurrency: 1`、overlap 0 |
| D | Duplicate state-read bound | 0‰ | ruled_out_by_measurement | duplicate 0 / 117 keyed reads；`m8_3_1_regression: false` |
| E | Provider/connection bound | 0‰ | ruled_out_by_measurement | 失败 0 + 超额尝试 0 / 117 次 |
| F | Local simulation compute bound | 2‰ | ruled_out_by_measurement | non_rpc 87 847 753 / 窗口（口径 span − union，**不是** span − sum） |
| G | Mixed / insufficient evidence | null（无自己的量） | dominant | 上面六条里 ≥2 条同时 dominant ⇒ G |

- `primary: "G"`，`primary_rationale`：三条以窗口为分母的分类**各自都达到 500‰**，
  所以"时间去了哪"没有单一答案，G 是老实的词；
  `secondary: ["A","B","C"]`，`dominant_span_categories: ["B","C","A"]`。
- `shares_are_not_additive`（文件原文要点）：A/B/C 是**同一段区间的三种读法**，不是三份切片。
  当每次只有一个请求在飞时，它们的分子是同一批纳秒，**相加不命名任何量**。
  A 的 860‰ 之所以小于 B/C 的 997‰，只因为 A 用"最快一次的价格"给次数定下界。
- 阈值是这张表自己的声明、不是测量：`dominant_per_mille: 500`、`material_per_mille: 50`、
  `latency_floor_ns: 100000000`（`thresholds_are_declared`）；每个 verdict 旁边都印出它读的那两个整数，
  想换一条线的读者可以拿同一批数重新排序。
- **主分类不是预设答案**：M8.2 是 D，本轮 D = 0‰（被实测判掉），而给出的 G 也不是"新 bottleneck"，
  它说的是：**剩下的时间被"次数"和"单价"同时占满，且串行让两者不能互相抵消。**
