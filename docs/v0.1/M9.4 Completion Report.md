## 1. Scope（范围）

**白话版（先看这一段）**

任务书把 Flashblocks 想象成一条**会主动推帧、每帧自带序号**的流。真实端点不是这样。
它只回答一句话：「再问我一次那个还没封住的块」；而那个块在我每次去问的时候，都比上一次长一点。

所以这一轮实际交付的东西是：

- 一个**早雷达**：拿 250 ms 一次的轮询去读那个还没封的块，把它存成「某个高度的第 N 种视图」，
  并列出「哪些池子被这批交易碰到了」——**只到这一步为止**。
- 每一次预确认读取都在同一个秒表下和一个 canonical 读取并排跑（两个 45 秒窗口），
  等块真的封好了，把「我先看到的」和「链上最终是这么写的」逐笔对账。
- 对账结果**永远以 canonical 为准**，没有一次例外。

一句话结论：**Flashblocks 在这个端点上是一个「更早看到、但没有任何额外权力」的信号源；
M9.4 把它接进来了，并且用类型层面证明它进不了 canonical 状态、进不了 PathFinder、进不了执行。**

**这一轮明确没做的事**（任务书 §35–§38、§53，一条都不碰）：签名、广播、真实套利评估、
private sequencer、自建节点、增量 PathFinder、3-hop amount optimizer、multi-hop simulation、
executor contract、HA、生产告警、资金管理、nonce 恢复、Telegram/webhook/KMS、24×7 runtime、
真实利润验证。

**判定**：`M9.4 STATUS = COMPLETE`（§23，任务书 §59 的 38 项逐条给证据）。

## 2. Architecture（架构）

审计 §4 的结论是**不新建 crate**：M9.4 的全部生产代码落在 `crates/live`（`evm-live`）里，
五个新模块 + 一处 `lib.rs` 的模块声明与再导出。

| 模块 | 行数 | 职责 |
|---|---|---|
| `crates/live/src/preconf.rs` | 683 | 归一化模型：`PreconfirmationFrame` / `PreconfirmationState` / `PreconfIdentity` / `AffectedPool` / `RadarEvent` / `RadarCounters` / `ReconciliationVerdict` |
| `crates/live/src/preconf_decode.rs` | 498 | 线格式解码：`frame_from_pending_value`、receipt 解码、`state_root_field`；fail-closed |
| `crates/live/src/preconf_loop.rs` | 694 | 传输循环：`LinkStage` 七态状态机、单消费者、背压高水位、`LinkRunReport` |
| `crates/live/src/preconf_provider.rs` | 299 | 帧供给：`FrameSource` trait + `PollingFrameSource`（复用既有 `evm_chain::HeadReader`）+ `ReplayFrameSource`（读已提交磁盘记录） |
| `crates/live/src/preconf_radar.rs` | 1057 | 雷达本体：`EarlyRadar` / `RadarConfig` / `PoolSet` / `CanonicalDigest` / `HeightRecord`，身份校验、视图持有、AffectedPool 派生、对账 |

三条结构性的边界（不是「纪律」，是「编译不过」）：

1. `evm-live` 的**生产依赖闭包里没有 `evm-state`、没有 `evm-graph`、没有 `evm-pathfinder`**，
   所以 `crates/live/src` 里根本写不出 `use evm_state::StateStore`——§4/§58 的类型隔离
   由 build graph 承担，门在 `crates/live/tests/preconf_isolation.rs`（7 项断言 + 三层扫描 + 每层阳性对照）。
2. 雷达**不发起任何 RPC**：它是一个纯函数 `frames + digests → RadarEvent`。真实的读取在测试
   harness 里，harness 用的是既有 `HeadReader` 的 `pending_raw()`，没有新增 HTTP 机械、没有新增方法（§34）。
3. 反向也扫：canonical 侧的源码里**没有任何一个文件提到雷达**，所以不存在「顺手把 flashblocks
   接进主流水线」的路径（§44 不得有第二条 canonical pipeline）。

## 3. Protocol Characterization（协议取证）

任务书 §5/§6 要求「先取证再写 decoder，禁止猜 schema」。审计窗口（§1 的 A–G）+ 本里程碑
两把真实窗口共同确认的形状，全部落在 `protocol.json`：

| 能力 | 实测值 | 见证 |
|---|---|---|
| 推送 / 订阅 | `NOT_AVAILABLE_ON_THIS_TRANSPORT` | 两把窗口的运行报告都写 `transport = http-poll-pending` |
|  provider 帧序号 | `ABSENT` | 162 次读取的 header key 全集里没有 index / sequence / slot / payloadId |
| 断线后重放 | `UNKNOWN`（§52：不许写成 SUPPORTED） | `link_resets = 0`，两把窗口都没问过这个问题 |
| cursor / gap 恢复 | `UNKNOWN` | 没有线序号可用于 cursor，且预确认侧 gap 不可测（§9） |
| pending receipts | `NOT_REQUESTED_IN THESE_WINDOWS` | `methods_requested` 只有两个方法，`receipt_lists_decoded = 0` |
| pending 视图的状态凭据 | `NONE`（`stateRoot` 全零占位） | 162 次读取里 157 次为全零占位，逐高度记在 `sequence.json` |

header 观测到 26 个 key，包含 OP-Stack 家族字段（`blobGasUsed`、`excessBlobGas`、`requestsHash`、
`withdrawalsRoot`），`miner` 即 sequencer——这是识别产品族的依据，端点**没有**发布版本号，
所以版本一律 `UNKNOWN` 而不是猜。

## 5. Wire Format（线格式）

`protocol.json#wire_format_notes` 三条：

1. 一个 pending 回答就是**一个完整的 block object**——没有 envelope、没有 notification method、
   没有 subscription id，也就是说线上没有任何东西可以用来「框住一条流」。
2. 同一个高度被反复回答，每次都是**同一批交易的更长列表**：一帧是「一个生长中视图的快照」，
   不是 delta。
3. 交易形状在两把窗口里只有一种：`full_object`，共 4348 笔次（逐次读取累加，不去重）。

因此 §8 的「序号」只能是本地指派的观测序号（见 §7）。

## 6. Decoder（解码器）

`preconf_decode.rs` + 9 个模块内单测。要点：

- **fail-closed**：解不出合法 pending object 就返回 `PreconfError::Decode`，不做部分填充；
  真实两把窗口 `decode_failures = 0`、`frames_rejected = 0`、`read_failures = 0`。
- 只有 hash 的交易（NC 里的 `HashOnlyTransaction`）视为不可用而不是「缺字段补 0」；
  receipt 缺 `status` 与 `status = 0` 是两种不同的事实，分开处理（NC11）。
- `state_root_field` 单独暴露占位判定，因此「这个视图没有状态凭据」是一句可以逐行核对的
  测量，而不是注释里的观点。
- §28 的 `N/A` 规则在解码层就成立：字段缺失进入 `Field<T>` 的 absent 态，绝不合成 `0`。

## 7. Identity（身份）

§8 要求身份不得来自线上帧序号——那条序号在这台端点上不存在（实测 162 次读取，0 次出现）。
`PreconfIdentity` 因此由四部分组成，且每一部分都能回指 raw 行：

| 成分 | 来源 |
|---|---|
| `chain_id` | 91342，每次连接读一次 `eth_chainId`（两把窗口共 4 次） |
| `height`（`number`） | 提供者自己的字段，每次读取都有 |
| `parent_identity`（`parentHash`） | 提供者自己的字段，每次读取都有 |
| `local_frame_sequence` | **本地按读取顺序指派**，不来自线上 |
| 视图判别 `view_hash`（`hash`） | 同一高度的不同视图哈希不同 ⇒ 哈希本身不能当身份（§2.2/§2.6） |

真实效果（两把窗口合计）：162 次读取 → 88 个高度 → 64 个高度出现过 2 种以上视图 →
5 个高度达到 ≥3 种视图；同一 (高度, 视图哈希) 被重复读到 5 次，这 5 次全部记为
`frames_duplicate`（window-a 4 / window-b 1），**应用一次、不派生任何新东西**（NC1）。

§2.6 的关键事实同时在真实数据上成立：候选视图的哈希与封块哈希**从未相同**
（`reconciled_hash_match = 0`，两把窗口都是 0）——这不是缺陷，是这台端点的性质，
所以 §15 的 canonical 对账必须按**内容**而不是按哈希来做。

## 8. Sequence Validation（顺序校验）

§9 的四类异常，逐类给「在真实流量上问了没有」：

| 类别 | 处理 | 真实窗口观测 |
|---|---|---|
| duplicate | 保留、计一次重复、不派生新事件 | 5 次（`sequence.json#rows.duplicate_reads`） |
| 错误高度 / 从未 pending 的高度 | 宣告为 skip，**永不回填** | 预确认侧 `N/A_NOT_MEASURABLE`（无线序号）；canonical 侧轮询跳过的高度可测：window-a 9 个、window-b 3 个，按号补齐后逐行落在 `reconciliation.json` 的 gap_fill 行 |
| 错误父块 | 视图作废、不合并 | `frames_wrong_parent = 0`；父校验三分计数 `passed 5` / `uncheckable 157` / `parent_unconfirmed 0`——「底下那个已封块还不知道」与「父哈希写错了」是两件事，且都不算通过 |
| 迟到帧（高度已封） | 先比对、再丢弃、计 `frames_late` | `frames_late = 0`、`late_frames_compared = 0`（窗口内没发生过，NC9 由 fixture 举证） |

`RadarCounters.sequence_gaps_measurable = false` 是这个里程碑最重要的一条诚实记录：
这条传输上问不出「缺了一帧」，所以 gap 一律写 `N/A_NOT_MEASURABLE` 而不是 `0`（§28）。

## 9. Reconnect Semantics（重连语义）

`preconf_loop.rs` 的 `LinkStage` 是显式七态：`Disconnected` / `Connecting` / `Connected` /
`Receiving` / `Validating` / `Recovering` / `Reset`。每次状态迁移都发一条事件，
`preconf_link_loop.rs` 里的 `every_link_stage_move_a_run_emits_is_an_edge_of_the_table`
把「实际发生过的迁移」与状态机表格逐条对齐——表里有的才算合法，跑出来没覆盖的边如实记为未覆盖。

§11 的作废规则：任何 `Reset` 之前，**先把所有 open view 作废**，因此不存在「静默带着旧视图重连」。
五种终止（`LinkEndedBy`）：`StopRequested` / `EventQueueClosed` / `ReadFailures` /
`DecodeFailures` / `Exhausted`（回放录制耗尽）。

两把真实窗口的实测：`ended_by = stop_requested`、`final_stage = disconnected`、
`link_resets = 0`、`canonical_backlog_high_water = 0`、window-a `views_invalidated = 9`
（预算耗尽前作废的 open view）、window-b `views_invalidated = 0`。

背压：单消费者，事件队列满时链路暂停而不是丢事件；
`a_slow_consumer_stops_the_link_without_losing_an_event` 是这条性质的测试证人。

## 11. Affected Pool（受影响池检测）

§12–§14 要求 `AffectedPool` 不得携带 reserve / price / amount。结构上：
`AffectedPool { pool, caused_by(交易哈希), strength(by target | by log), block_number,
local_frame_sequence }`，仅此。`preconf_isolation.rs` 的 `the_radar_types_carry_no_reserves_or_prices`
用字段名扫描把这条钉住，并同时断言「 planted 一个 `reserve0` 字段必须被抓住」。

**真实流量上的结果：命中已注册池 0 次。** 这个数字需要两个分母和一个非零阳性对照才能解读：

| 项 | 值 |
|---|---|
| 两把窗口里出现过的 distinct transaction target | 156 |
| M9.2 已举证的注册池（`graph-integration.json`，块高 37224031） | 80（160 条有向边 / 50 个代币） |
| 交集 | **0** |
| 阳性对照：这些交易打中的已知代币合约 | 1 |
| 阳性对照：这些交易打中的 sequencer 地址 | 2 |
| 观测到但**故意不用**的签名者集合 | 559（雷达按「调用了谁 / 谁发 log」归类，不按「谁签的」） |

两侧都非空、而交集为空 ⇒ 这是市场事实，不是解析器静默失败（审计 §2.9 在 14 s 窗口里
也只看到 1 条 V2 Swap log）。

canonical 侧的池集合比对（§16）：closing 臂只读区块对象、不读 receipt，因此它**不点名任何列表**，
109 次对账在「池集合」这条轴上全部记为 `UNVERIFIED`——这跟「两边一致」是两句不同的话。

## 12. Canonical Reconciliation（canonical 对账）

§15–§19 的内容对账，四类 verdict + 一个 no_view：`content_equal`、`content_prefix`、
`content_superset`、`content_divergent`、`no_view`；**每一行 `canonical_wins = true`**，
因为「canonical 赢」是 verdict 集合的性质而不是某个分支（§17）。

真实窗口（116 次对账，覆盖 91 个高度）：

| verdict | window-a | window-b | 合计 |
|---|---|---|---|
| content_equal | 35 | 44 | 79 |
| content_prefix | 20 | 10 | 30 |
| content_superset | 0 | 0 | 0 |
| content_divergent | 0 | 0 | 0 |
| no_view（该高度从未被 pending 见过） | 4 | 3 | 7 |
| hash_match | 0 | 0 | 0 |

`content_prefix` 是这台端点的核心形状：我先看到的列表是最终块的**前缀**（早期可见性是真的，
但它是部分可见）。

**重算抓到的一件生产计数不会自己说的事**：116 次对账只覆盖 91 个高度——同一个已封块被
重复对账 25 次。原因是 closing 臂每次轮询 `latest` 都会把同一个摘要再交一次，而雷达为了 §19
的迟到帧比对必须保留已封视图。重复对账之间 verdict 类别从未改变（`verdict_stability = 0`），
所以这是**计数口径**的差而不是正确性的差；但把它抹平成「116 个高度」就是一次谎报，
因此两个数一起写在 `reconciliation.json#repeat_closures`。

另一个必须一起看的口径：`sequence.json` 里 `heights_closed_at_least_once` 是 42（只对预确认臂
点过名的高度计数），而 `reconciliation.json` 的 `distinct_heights_closed` 是 46——差的那 4 个
正是 `no_view` 的 4 次。窗口 b 同理：42 + 3 = 45。三个数各自正确，任选其一当结论都会错。

## 16. A/B Latency（A/B 延迟）

§26 六个时间戳、§27 六个派生延迟，逐条重算（允许 ±2 ms，因为秒表读的是同一次交付的两个瞬间）。
`latency.json#definitions` 给出全部口径定义，其中最关键的一条：
`flashblocks_lead_ms = canonical_seen_at − first delivered frame of the same height`，
`canonical_seen_at` 是 closing 臂自己观测到的瞬间。

真实两把窗口（合并）：

| 派生量 | n | min | median | p90 | p95 | max | 非正样本 |
|---|---|---|---|---|---|---|---|
| `flashblocks_lead_ms`（交易口径） | 2792 | 905 | 1831 | 2878 | 3111 | 3701 | **0** |
| `flashblocks_lead_ms`（高度口径） | 84 | 905 | 1825 | 2867 | 3025 | 3701 | **0** |
| `canonical_lag_ms` | 91 | 811 | 1305 | 2428 | 2582 | 3168 | 0 |
| `reconciliation_latency_ms` | 91 | 188 | 639 | 1213 | 1465 | 1884 | 0 |

分窗口（交易口径）：window-a n=1357 / median 2305 / p95 3333；window-b n=1435 / median 1587 / p95 2606。
分窗口（高度口径）：各 n=42；window-a median 2190，window-b median 1587。

**这一节必须连着下一段读。** 审计窗口 G 用同一把秒表、两臂并发采到 733 笔两臂都见过的交易，
量到的 lead 是 min −692 ms / p50 **+203 ms** / p90 +834 ms / max +1240 ms，
其中 **187/733 = 25.5% 为非正**。本里程碑的两把窗口在 2792 个样本里**一个非正都没抓到**。
两件事同时为真，差别在样本定义：这里的交易口径只统计「本臂已经先点过名的那些块」里的交易，
3185 笔已封交易里有 393 笔属于两臂压根没在 pending 里见过的块，它们被排除、而不是被记成 lead = 0。
`latency.json` 因此带着 `sealed_transactions_total` / `sealed_transactions_never_pre_seen`
和一条 `selection_warning`：lead 的分布是「250 ms 轮询 vs 约 1.5 s 出块」在一天里两个 45 秒窗口上的
产物，审计测到的 25.5% 非正是**怀疑任何「有优势」结论的理由，而不是把它上调的理由**（§28）。

另外两条与任务书预期相反的实测（审计 §2.8）：
flashblocks 宿主的 pending→latest **更慢**（p50 1699 vs 1332 ms）⇒ 它的差异点不是「更早给出完整块」，
而是同一高度的**部分块可见性**；canonical 宿主自己的 `pending` 也已经是早期视图 ⇒
对照臂必须包含它，否则是拿 A 臂跟一个不存在的 B 臂比。

## 17. RPC Accounting（RPC 核算）

§34：仪表化 + Flashblocks 观测**不得偷偷新增 RPC**。

| 项 | 值 | 来源 |
|---|---|---|
| 用到的 RPC 方法 | `eth_chainId`、`eth_getBlockByNumber` 两个，仅此 | `protocol.json#methods_requested` |
| 预确认臂发出的读取 | 162（window-a 80 / window-b 82） | `pending-reads.jsonl` 每读一行 |
| canonical 臂发出的读取 | 117（59 + 58），其 gap 填充以嵌套行出现在每条 poll 行里 | `canonical-reads.jsonl` |
| `eth_chainId` | 4（每次连接一次） | 运行元数据 |
| **新增生产 RPC** | **0** | `summary.json#rpc_accounting_section_34` |

理由不是「我们很小心」，是结构性的：雷达不读端点（它是 frames → events 的纯函数），
`PollingFrameSource` 复用 M5 候选源已经在用的 `HeadReader::pending_raw()`，
而证据门本身**一次请求都不发**（只读已提交文件）。门里的 §34 自扫描把「这条声明所依赖的
符号名」从自己的源码里逐个查一遍，并且要求字面量在声明之外恰好只出现一次——否则扫描是盲的。

每一次发出的请求在 `raw/` 里都有一行对应；`manifest.json` 记录了抓取命令本身，
因此「谁花的这些请求」是可复核的。

## 18. Determinism（确定性）

§41/§43：

- `the_same_recording_through_the_same_clock_produces_the_same_evidence_twice`（link loop）：
  同一份录制 + 同一个虚拟时钟跑两遍，产出的证据逐字节相同。
- `records_come_out_in_chain_order_whatever_order_the_frames_arrived_in`（radar matrix）：
  输出顺序按链上顺序（高度 → 本地观测序号），不按到达顺序。
- 证据装配的两种模式：默认模式只做字节对照 + 独立重算，不写任何文件；
  `M94_EVIDENCE_REFRESH=1` 才重新装配。装配命令与检查命令都写进 `manifest.json#_provenance`。
  wall time 永远从 raw 引用，不重新测量——重新测一次就会变，变了就不是字节门。
- 表内排序一律用语义键（高度、endpoint digest、verdict 名），不用「排序后的第 N 行」
  （项目记忆里的证据门身份纪律）。

独立重算（§32）是这一节真正的分量：`summary.json#recompute_agreement_section_32` 对每个窗口
比较 **16 条轴**（frames_offered / accepted / duplicate / heights_seen / multi_view /
ge_three_views / state_root_placeholders / transactions_observed / canonical_closures /
5 类 verdict / hash_match / affected_pools_emitted），两把窗口 `disagreements = 0`；
逐对账行还另用两条交易列表独立重算 verdict 与三个延迟量。生产 helper 一个都没调用。

重算并**真的抓到过东西**（不是装饰）：重复对账 25 次这件事只有重算才能看见，见 §12。

## 21. Limitations（已知局限）

§52 + §48 + §62。**猜的部分一律写 UNKNOWN。**

1. **这不是「Flashblocks 流」**。这台端点只有 HTTP 轮询的 `pending` 重读；任务书 §2/§3 假设的
   推送、帧序号、payloadId、增量 delta 在这里都不存在。所以 §9 的 gap 检测在预确认侧
   永远只能写 `N/A_NOT_MEASURABLE`。换端点（真 WebSocket 推送）时这一整套结论要重测。
2. **lead 的分布不可外推**。两个 45 s 测试网窗口、2792 个交易口径样本、0 非正样本；
   审计另一次窗口在 733 个样本里量到 25.5% 非正。样本定义差异（393 笔 never-pre-seen 被排除）
   解释了方向，但没有解释幅度，因此这里**不主张**任何优势，只主张「更早点名、权力不变」。
3. **AffectedPool 在真实流量上是 0 命中**，且 log/receipt 那一半完全没被真实流量行使过
   （两把窗口都没读 receipt）：正确性只有 fixture + NC10/NC11/NC12 作证。
   80 个已举证池在这条链上此刻没有交易量，这是市场事实。
4. **§48 的 N ≥ 3 只在 88 个高度中的 5 个上达成**。
5. **replay / cursor / 断线恢复 = UNKNOWN**：`link_resets = 0`，问题从未被问过。
6. **端点版本 = UNKNOWN**（不发布版本字段）；「Flashblocks 还是 Subblocks 的上游演化」是仓库外的问题，
   本里程碑不答。
7. **pending 视图没有任何状态凭据**（`stateRoot` 全零占位），因此它连「可读状态的哈希」都不是；
   §13 的「不得带 reserve/price」在这里有第二条独立理由。
8. **对账里 109 次在池集合轴上是 UNVERIFIED**：closing 臂不读 receipt，所以它没点名任何列表。
9. **canonical 侧的 gap 可测但预确认侧不可测**——两臂不是对称的两条流，任何「A/B 就是同一件事比两次」
   的读法都错。
10. 本里程碑没有任何一项数字能变成钱的判断：利润 = `N/A`，因为没有一个字段来自 reserve、
    fee、gas price 或 amount。
