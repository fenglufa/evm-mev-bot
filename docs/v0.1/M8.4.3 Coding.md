# M8.4.3 — State Ownership & Lifecycle Diagnosis

## 1. 任务目标

本阶段只研究状态所有权、生命周期与跨阶段复用契约，不实施性能优化。

M8.4.2 已识别出跨阶段重复读取，但所有 42 个完全相同的重复候选均因 `lifecycle_ownership = not_checkable_from_a_record` 而无法证明安全复用。

本阶段需要回答：

1. 一次链上状态读取由哪个组件产生和维护？
2. 状态属于哪个链、区块、交易或执行生命周期？
3. 哪个组件负责判定其新鲜度与有效性？
4. 状态在什么条件下失效？
5. 下游阶段是否必须重新读取，还是能够消费上游已验证的状态？
6. `Preflight → Build` 是否存在可定义、可验证的状态契约？
7. `Simulation → Build`、`Opportunity → Simulation` 是否具有相同或不同的约束？
8. 哪些状态可以共享，哪些只能用于诊断，哪些必须重新获取？

**本阶段的成功标准是把未知项变成有证据的契约或明确的否定结论，不是减少 RPC 次数。**

* 如发现基线与预期不一致，记录实际状态；不得自行切换分支、重置或丢弃用户工作。

## 3. 严格范围

允许：

* 阅读和追踪现有代码。
* 添加只读诊断工具、静态检查与测试。
* 增加状态所有权、生命周期和依赖关系证据。
* 增加不改变运行语义的观测字段。
* 使用固定块、录制数据及已有 BuildOnly 路径进行验证。

禁止：

* 新增缓存或跨阶段状态复用。
* 修改 `StateReadCache` 的命中范围。
* 改变 RPC 调用次数、顺序或并发策略。
* 添加 batch、multicall、prefetch。
* 修改 REVM 状态读取语义。
* 修改机会检测、利润计算、Risk 或执行行为。
* 改变交易 nonce、fee、gas、余额或区块选择规则。
* 签名、广播或执行新的真实套利。
* 为了通过测试而放宽现有门禁。
* 将“测试结果相同”解释为“生产环境可以安全复用”。

如果现有架构无法回答某个问题，应记录 `unknown` 或 `not_proven`，不能用推测填补。

## 4. 建立状态所有权模型

针对每一种状态，分别识别以下角色：

* **Producer**：首次取得或计算状态的组件。
* **Owner**：负责管理该状态有效性的组件。
* **Scope**：状态所属的链、区块、交易、模拟或执行生命周期。
* **Version / Identity**：确定状态所代表的具体版本。
* **Freshness Rule**：判断状态是否仍满足消费者的要求。
* **Invalidation Rule**：使状态失效的事件或条件。
* **Consumer**：实际使用该状态的组件。
* **Authority**：当多个状态来源冲突时，哪个来源具有权威性。
* **Evidence**：支持以上结论的代码位置、测试或运行记录。

至少覆盖以下状态类别：

| 状态类别                 | 必须调查的内容                                                  |
| -------------------- | -------------------------------------------------------- |
| Pool reserves        | StateStore、Sync、GraphSnapshot 与 REVM canonical state 的关系 |
| Contract code        | chain、block、address 的身份约束与代码变更风险                         |
| Storage              | slot、block、状态读取顺序与 REVM 执行依赖                             |
| Native balance       | 账户、区块、交易执行前后余额语义                                         |
| Nonce                | pending/latest/block-tag 语义及同一执行通道中的变化                   |
| Fee / gas parameters | 数据来源、采样时间、有效期及 Build 使用规则                                |
| Block/header         | block number、hash、parent、pending/latest 的语义区别            |
| Chain ID             | 配置身份、RPC 返回值与启动时验证的关系                                    |
| `eth_call`           | calldata、target、block tag、执行上下文与状态依赖                     |
| Simulation result    | 输入状态身份、模拟上下文、输出结果与后续交易构建的关系                              |
| Transaction intent   | RiskApproved 输入、Preflight 结果与 Build 输入之间的约束              |

不得将上述所有数据统称为“链上状态”。不同类别应有独立的所有权和失效规则。

## 5. 定义状态生命周期

为每种状态建立以下生命周期视图：

`Acquired → Validated → Published → Consumed → Invalidated / Expired`

其中每个转换都必须有明确依据。

如果实际代码不存在某个阶段，应记录 `not_applicable`；如果代码没有足够信息，应记录 `unknown`。

至少分析以下失效条件：

* 链 ID 不匹配。
* 区块号或区块 hash 不匹配。
* `latest`、`pending` 与明确区块 tag 的语义差异。
* 同一高度发生 reorg 或 canonical block 改变。
* nonce 被其他交易或同一执行通道推进。
* 余额发生变化。
* fee 参数超出允许的有效期或与当前提交条件不匹配。
* 合约代码或 storage 所属状态版本改变。
* 模拟输入与最终 Build 输入不一致。
* Preflight 通过后，执行环境发生变化。
* 生命周期结束或消费者所要求的 freshness 条件无法证明。

注意：这些是必须调查的候选条件，不代表当前系统一定存在对应缺陷。

## 6. 专项调查 A：Preflight → Build

这是本阶段最高优先级。

针对 M8.4.2 中的 12 对 exact duplicate，逐一追踪实际调用路径。必须区分：

1. Preflight 读取了什么。
2. Build 读取了什么。
3. 两次读取是否表达完全相同的语义。
4. 两次读取分别服务于什么安全约束。
5. Preflight 的结果是否被保留并传递给 Build。
6. Build 是否具有自己的强制校验职责。
7. 两个阶段之间是否可能出现外部状态变化。
8. 当前架构是否存在能证明状态有效性的版本或 token。
9. 如果没有这样的契约，最小需要补充什么信息。

分别分析：

* chain ID
* nonce
* balance
* fee 参数
* block/header
* gas limit 或 gas estimate
* transaction intent 与模拟结果的绑定关系

对每项给出独立结论，不得因为 nonce 可复用就推导 balance、fee 或 header 也可复用。

必须明确回答：

* Preflight 是一次性检查结果，还是一个可被后续阶段消费的状态快照？
* Build 是否必须独立重新确认某些事实？
* 哪些值可能复用，但某些验证动作仍然必须保留？
* 哪些条件会使此前的 Preflight 结果失效？
* 当前代码是否能够检测这些失效条件？

**不能为了减少 RPC 而删除执行前安全检查。**

## 7. 专项调查 B：Opportunity → Simulation

重点判断：

* Opportunity 使用的是 StateStore、GraphSnapshot、RPC 读取结果，还是混合来源？
* 每个机会携带的 block identity 是否足以描述其输入状态？
* Simulation 是否重新获取 REVM 执行所需的 canonical 状态？
* Pool reserves 与 REVM 的 code、balance、nonce、storage 是否来自同一状态版本？
* 同一个区块号是否足以证明状态相同？何时还需要 block hash？
* Opportunity 形成后，状态变化应当导致机会过期、重新模拟还是重新检测？
* 当前架构如何区分“检测时有利”与“提交时仍然有利”？

不得把 GraphSnapshot 当作 REVM 完整状态的替代品，也不得仅凭同一 block number 推导所有数据可安全共享。

## 8. 专项调查 C：State Update → Simulation

追踪：

* Sync 事件怎样进入 StateStore。
* StateStore 怎样形成 GraphSnapshot。
* Replay 和 live 是否遵循相同的 StateUpdate 路径。
* 状态更新的确定性排序如何保证。
* GraphSnapshot 的 block identity 与 REVM 的读取区块如何对应。
* 同一块内的事件顺序和交易执行中间状态是否存在差别。
* 哪些状态只适用于机会筛选，哪些状态可作为模拟输入。
* 当前代码有没有明确的版本绑定、来源标记和一致性检查。

重点输出状态来源的权威性矩阵，不做数据结构重构。

## 9. 专项调查 D：Simulation → Build

检查 Simulation 输出与交易构建输入之间的完整绑定关系：

* chain ID
* target
* value
* calldata
* nonce
* gas limit
* fee 参数
* sender
* route / swap steps
* 模拟所依赖的区块与状态覆盖项
* 风险规则与批准结果

明确哪些字段已由 M6/M7 的现有校验保证一致，哪些属于模拟环境的附加条件，哪些尚未形成明确契约。

如果 Simulation 使用了 state override，必须明确 Build 是否能在真实链上重现该环境；不能把依赖 state override 的模拟结果当作可直接执行的证明。

本阶段不改变交易构建和签名流程。

## 10. 输出可机器检查的契约

建议在 `data/evidence/m8/m8.4.3/` 生成诊断证据，并在适当的 docs 目录添加报告。

在不强迫生产代码新增公共抽象的前提下，定义一个诊断级状态契约模型。字段至少覆盖：

* `state_kind`
* `producer`
* `owner`
* `scope`
* `chain_id`
* `block_number`
* `block_hash`（若适用）
* `block_tag_semantics`
* `consumer`
* `freshness_rule`
* `invalidation_rule`
* `authority`
* `evidence_refs`
* `ownership_status`
* `reuse_status`
* `reason`

枚举值必须有限、稳定、可校验。推荐状态包括：

* `proven`
* `partially_proven`
* `unknown`
* `not_applicable`

复用判断必须严格区分：

* `duplicate`
* `semantically_equivalent`
* `reusable_in_principle`
* `safe_to_reuse_now`

这些是不同层次，不能互相代替。

尤其是：

`same value ≠ same state identity`

`same state identity ≠ same lifecycle ownership`

`reusable in principle ≠ safe to reuse now`

若当前证据不能证明 `safe_to_reuse_now`，必须为 `false`，并列出缺失的证明条件。

报告必须附上实际代码位置或测试证据。不得仅靠人工描述生成 `proven` 结论。

## 11. 证据与实验要求

本轮是诊断任务，不要求新增真实 RPC 实验；优先复用 M8.4.2 已有三次 live BuildOnly 记录与固定块证据。

如果需要新运行：

* 必须使用 BuildOnly。
* 必须固定并记录配置和代码版本。
* 默认 `state_read_reuse=true`、`concurrency=1`，除非已有证据需要其他配置。
* 不签名、不广播、不花费 ETH。
* 不得为了增加样本而人为修改生产语义。
* 明确区分实测、静态推导、测试证明和未知事项。

证据应包含：

* `ownership-matrix.json`
* `lifecycle-contracts.json`
* `stage-dependency-matrix.json`
* `reuse-verdicts.json`
* `README.md`
* 必要的原始记录和可复算汇总

文件名可根据仓库既有格式调整，但不得丢失对应信息。

每项契约必须能追溯到实际代码、测试或已提交的证据。聚合结果必须能从原始数据重新计算。

## 12. 必须覆盖的测试

至少覆盖：

1. 同一链、同一区块、同一状态身份。
2. 同一高度、不同 block hash。
3. 同一目标、不同区块。
4. `latest` 与明确 block tag。
5. `pending` 与明确 block tag。
6. 相同值、不同来源。
7. 相同来源、不同生命周期。
8. Preflight 之后 nonce 变化。
9. Preflight 之后余额变化。
10. fee 参数或 header freshness 不满足。
11. Simulation 与 Build 输入字段不一致。
12. state override 依赖无法在真实执行环境中复现。
13. 缺少 owner 或 invalidation rule 时拒绝判定安全复用。
14. `unknown` 不得自动降级为 `safe_to_reuse_now`。
15. 证据文件的聚合结果可由原始记录重算。

测试应验证判定规则，不应通过虚构的生产运行结果来证明性能收益。

## 14. 明确禁止的成功标准

以下均不能单独作为本阶段成功依据：

* 测试全部通过。
* 两次 RPC 返回相同值。
* 两次读取地址和参数相同。
* 相同区块号。
* Simulation 与 Build 在固定夹具中结果一致。
* 重复读取次数下降。
* 代码增加了 Snapshot 或 Context 类型。

只有所有权、状态身份、生命周期和失效条件都有足够证据时，才可以判定某项复用安全。

## 16. 完成判定

只有满足以下条件才可标记 `M8.4.3 COMPLETE`：

* 四条重点链路均已调查。
* 每类关键状态均明确标记 owner、scope、freshness、invalidation 和 authority，或明确记录未知原因。
* `Preflight → Build` 的 nonce、balance、fee、header 等分别得出结论。
* 不把 StateStore / GraphSnapshot 与 REVM canonical state 混为一谈。
* 所有安全复用结论都有可追溯证据。
* 未知项不会被自动判为安全。
* 契约证据可重算，测试覆盖关键反例。
* 所有要求的回归和安全门禁通过。
* 没有引入生产行为变化或真实交易副作用。
* 完成报告中的数字与原始证据一致。

## 17. 下一阶段决策

本阶段结束后，只能根据证据选择以下一种结果：

A. 某项状态具备明确的所有权与失效契约，可以设计独立、受控的复用实验。

B. 状态理论上可复用，但当前架构缺少必要的 owner、version 或 invalidation 机制，需要先补足契约设计；本阶段不实施。

C. 状态必须重新读取或保持阶段隔离，不应优化掉该读取。

D. 证据不足，继续调查。

不要预先规定必须找到可以安全复用的项目。

本任务的最终目标不是“省掉多少次 RPC”，而是建立后续性能优化所需的状态正确性边界。
