## 白话结论（先看这一屏）

**结论：没有安全的 RPC 可以省。** 判定 = `NO_SAFE_RPC_REDUCTION_FOUND`。热路径一共 246 次请求（3 把 run，每把 82 次，物理 HTTP 尝试也是 246 次，因为并发度是 1）；理论上「问重复了」的是 **42 次**，实际**安全可省的是 0 次**。18 个候选里 3 个 P1、15 个 REJECT，P0/P2/P3 全空。

为什么 42 变成 0，三句话说清：

1. **42 次重复里 33 次压在「这条读取本身就是检查」的消费方上。** Preflight 要第二次 `eth_call`、Build 要第二次余额与高度——把第一次的副本递过去，闸门就变成拿一个数字跟自己的复制品比，检查消失，RPC 一次也没少（§11、§15）。
2. **M8.4.2 的五个复用资格，78 对里 0 对全过。** 逐格实测：`state_semantics` 78/78 满足，`block_identity` 只有 21 对满足（57 对是被量出来的「不满足」），`same_block` 21 满足 / 30 被违反，`lifecycle_ownership` **78 对全是「记录里查不出来」**，`no_freshness_requirement` 51 对查不出来 / 27 对不满足。中间那层 `reusable_in_principle` 因此是 42 个 unknown + 36 个 no，`safe_to_reuse` 全 78 为 false。
3. **要救这 42 次，得先有新机器。** 18 个候选里 5 个需要新的跨阶段载体（carrier），10 个需要新的生命周期/所有权规则，1 个需要一次真链受控实验。§3 禁止在本阶段建这些东西，所以它们只能被登记，不能被实现。

**本轮新增 RPC = 0，签名 0，广播 0，真实套利 0。** 所有数字都从 M8.4.2 已经提交的 3 把 run 记录（`data/evidence/m8/cross-stage/`）重算，一次节点都没问（§2.4、§26）。生产代码改动面 = **0**：模型和装配都放在 `crates/pipeline/tests/` 下，`git status --short` 里没有任何被跟踪文件被修改（§30 的偏好）。

**这不是失败**（§23、§33）：它意味着 M8 已经从「找明显重复的 RPC」进入「剩下的 RPC 大多背着业务语义」的阶段。下一阶段的抓手不再是 `RPC elimination`，而是延迟、端点架构、连接策略、区域部署（§33）。

## 5. Identity（§8、§24 第十一条、§25 NC1）

身份 = `method=<m>|` 加上按字母序排列的键项，键项来自 M8.4.2 已发布的 `RpcReadKey`（`crates/pipeline/src/canonicalization.rs`），本阶段只读不改。例：

```text
method=eth_call|block=37700740|chain=91342|data=0902f1ac|to=0x2a3ceafba30f6626170cbb0cd67392efb94bd9a4
```

无参数请求（`eth_blockNumber`、`eth_chainId`、`eth_maxPriorityFeePerGas`）没有 `dedup_key`，共 **21 次**，身份落到兜底语法 `method=<m>|endpoint=rpc-faa716cada04a9ef|method_kind=<m>`。

**44 个站点并不等于 44 个身份：实测是 31 个不同身份。** 其中 6 个身份被 **19 个站点共用（覆盖 57 次请求）**，其余 25 个身份各属一个站点（189 次）。共用组就是「同一件事被不同阶段问」的地方，也正是重复测量的落点：这 6 组里装着 **42 个精确重复对中的 39 个** 与 **36 个其他类别对中的 6 个**。最大的一组是 6 个 `eth_getBlockByNumber` 站点共用 `method=eth_getBlockByNumber|block=37700740|chain=91342|hydrated=false`（`observation.…pin`、`preflight.…binding_pin`、`preflight.…fee_pin`、`build.…binding`、`build.…fee_pin`、`simulation.…header`），另有 `latest` 形式的 3 站点组、`eth_chainId` 与 `eth_maxPriorityFeePerGas` 各 3 站点组、`eth_getBalance` 两个高度各 2 站点组。

剩下 3 个精确重复对（`preflight.eth_getTransactionCount.pair → build.eth_getTransactionCount.pair`）**没有**折进同一个站点级身份，原因值得单独记：这两个 nonce 站点各带 4 个 `dedup_key` 变体，各自公布的最小键是「数字高度形式」（37700755 与 37700761），而那 3 对重复发生在「tag 形式」的键上。所以站点级身份是「这个组公布哪一个键」的答案，不是「这个组只问了一件事」的证明——这就是表里必须同时公布 `recorded_key_variants` 的原因（见下段），也是把身份当成语义键而不是当成站点名的好处。

**一个组公布哪一个成员的身份，必须是键的函数，不能是文件读取顺序的函数。** 本轮修复了这一点：模型 `representative_rows()` 与重算门 `representative()` 现在都按 `(无键排最后, 记录的 dedup_key 字典序, run, rpc_id)` 选代表，NC5 因此从「比较组数」升级为「比较完整的语义列」（组标签 + 成员数 + 身份）。§24 第十二条与 §25 NC5 在这里被同一条规则同时管住。

披露：44 个站点里有 **34 个** 的记录里出现过不止一个 `dedup_key`（`recorded_key_variants` 的分布：1 键 10 站、3 键 19 站、4 键 2、6 键 4、9 键 5、12 键 1、18 键 2、30 键 1）。同一站点多个键是真实情况（同一处代码在不同高度问同一个东西），不是键算错了；表里因此同时公布「代表键」与「键变体数」两列，避免读者把 44 读成 44 个唯一键。

## 本轮三个非显然结论（供外部审稿者）

1. **「省 42 条」和「能省 0 条」同时为真。** 42 是同一问题被问了两次的次数；0 是「删掉其中一次之后检查还在不在」的答案。这两个数在一张表里共存，任何把它们合并成「削减率 0/42 = 0%」的写法都丢了结论本身。
2. **代表行的选择是证据门的地基。** 只要身份取自「先读到的那一行」，重排输入就能改动物理上相同 corpus 的公布身份，NC5 就只能比组数（永远绿）。改成按记录里的最小 `dedup_key` 选代表后，身份成为键的函数，NC5 才第一次能比较完整语义列并仍然通过。这条修复没有改变任何一个节省数字，改的是「这张表能否被信任」。
3. **`lifecycle_ownership` 在 78/78 对上都查不出来**，意味着现有记录格式无法证明「谁在答案到达之后持有它」。因此本阶段的安全结论是记录格式的产物，而不仅仅是市场行为的产物——要打破它，最小动作不是加缓存，而是让一条记录字段说出所有者。
