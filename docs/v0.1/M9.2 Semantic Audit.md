# M9.2 语义审计 — `PoolState.block_number` 到底是什么

## 1. 结论先行

**`PoolState.block_number` 目前含义是 (A)：这条池子最后一次 `Sync` 变异发生所在的块。**
不是 (B)「快照证明该状态有效的块」。

架构里**完全没有** (B) 的表达位：`PoolState`、`PoolRecord`、`StateSnapshot` 三个类型里没有任何字段能写「这个状态被证明有效一直到第几块」。因此 M9.1 的 56 个 `NotAtTargetBlock` 不是图建错了，而是**图的判定条件（同块相等）与 §4 的规范语义（`S <= T` 且 `(S, T]` 无后续 Sync）之间缺一个携带证据的类型**。

同时审计推翻了两个容易误判的前提：

1. **M9.1 的图目标块不是选出来的，是被数据决定的**：`crates/graph/src/builder.rs:76-77` 用 `snapshot.position.block_number` 当 target，而 `snapshot.position` 是「全 store 最远已应用位置」。37,224,031 恰好是 24 个池同时发第一次 `Sync` 的块（下面第 4 节实测），所以「24 池入图 / 56 池跳过」= 「恰好与那个被数据决定的块相等的池 / 其余全部」。
2. **M9.1 的原始证据不能直接用来做 M9.2 的新鲜度证明**：那次运行里，每池 `Sync` 搜索的上界是它自己所在窗口的 `to_block`（`crates/discovery/tests/historical_live.rs:202`，`let search_to = report.to_block;`），不是 37,224,031。第一个窗口是 4,050,000–4,059,999，那些池距 target 还差 **33,164,032 块**，中间有没有 `Sync` 至今无人查过。§25 要求的「证据来自实际日志查询而非假设」只能重跑。

## 3. §7 的答案：不引入第二套排序

§7 要求「若状态模型确实不带 tx index，先证明 `log_index` 是否已经是既有 replay 路径的规范全序，不要另造一套排序」。证明分两段：

**代码段（已成立）**：`recorded.rs:141-150` 不是一条注释，是一道加载闸门——任何「按交易顺序排 ≠ 按 log_index 排」的块文件都进不了 replay。所以在既有路径上，`(block_number, log_index)` 与 `(block_number, tx_index, log_index)` **可证等价**，且等价性是被强制的而不是被假定的。`UpdatePosition`（`crates/state/src/update.rs:14-20`）用前者，是对的。

**数据段（M9.2 实跑时补测）**：`crates/discovery/src/reads.rs:112-126` 的 `SyncRecord` **本来就带 `tx_index`**，其 `identity()` 是 `(block, tx_index, log_index)` 三元组。因此 §24 要求记录的 `selected_sync_tx_index` 有现成出处，不需要改 `PoolState`。M9.2 的重建实跑会顺带产出验证：对 GIWA 真实返回的全部 `Sync` 日志，逐块检查「按 (tx, log) 排序 == 按 log 排序」与「块内 log_index 唯一」，把结论从代码推论升级为真链观测。

**因此**：`PoolState` 不加 `tx_index` 字段，`UpdatePosition` 不动，排序约定仍只有一条。tx index 只作为**证据字段**存在于 `SyncRecord` 与证据表里。

## 4. M9.1 那 80 个池的真实分布（本次从原始证据重测）

读 `data/evidence/m9/m9.1/raw/pass-a.json`：

- 5 个窗口，各 10,000 块，合计 50,000 块：`4,050,000–4,059,999` / `28,540,000–28,549,999` / `31,710,000–31,719,999` / `37,180,000–37,189,999` / `37,220,000–37,229,999`。
- 80 个已验证池的「最新已知 `Sync`」落在 **48 个不同块**上。
- 其中 **24 个池的 `Sync` 块号恰好是 37,224,031**；它们自己的发现块分布在 37,223,105 / 37,223,106 / 37,223,107 / 37,223,108 / 37,223,109 / 37,223,488 上——即一个批量部署者在连续几个块里建了这批池，随后在 37,224,031 一个块内给这 24 个池加了第一次流动性。
- 剩下 56 个池：`state_block` 从 4,057,629 到 37,223,883 不等。距图块最远的是 `0x3289dd77…`，`state_block` 4,057,629，差 **33,166,402 块**；本文上一版在这里写过 8,679,049（`0x0320fce1…`，state_block 28,544,982），那是 56 个里从下往上第 3 个，不是最远的——本轮从 `pass-a.json#state.skipped` 的 56 条 `state_position` 重测更正。

也就是说 M9.1 报的「24 池入图」不是运气，是**相等判定的必然结果**：图块 = 全 store 最远已应用 `Sync` 的位置，只有在这个块里恰好发过 `Sync` 的池能进来。

## 5. 由此决定的改法（写码前先定，供 §16 的正确性论证引用）

§2 与 §16 禁止「为了覆盖率把 `state.block == target` 改掉」。审计结论给出了唯一合法的放松方式：**不是放松相等判定，而是为「更旧的状态仍然有效」补一个必须携带证据才能成立的第二档**。

- 第一档（今天的全部行为，原样保留）：`state.block_number == target` —— 状态就是在目标块上观察到的。
- 第二档（新增）：`state.block_number < target`，**且**存在一条针对该池的完整 `Sync` 扫描证据，其区间覆盖 `(state.block_number, target]`。没有这条证据，判定退回 `NotAtTargetBlock`。
- 目标块必须是显式输入（§18），不再由数据反推；`state.block_number > target` 必须可表达且必须被拒（NC1/NC5 的前置条件——今天的类型根本表达不出「目标块早于某个已存状态」）。
- 溯源不得破坏（§14）：`PoolState.block_number/log_index` 继续写 `Sync` 自己的位置，绝不改写成 target；`GraphEdge.state_position`（`crates/graph/src/edge.rs:42, 90-105`）已经在透传这个位置，下游天然看得到「这条边的价格来自哪条日志」。

具体类型见 M9.2-P1 的实现：只加 `SyncScanCoverage{from, through}` 与快照上一个可选 target，`StateUpdate` / `InMemoryStateStore` / `PoolState` 一字不改，也不新增并行 store（§17）。
