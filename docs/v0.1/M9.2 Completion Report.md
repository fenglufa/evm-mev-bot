## 白话结论（先看这一屏）

**M9.1 的图只装了 24 个池，不是那 56 个池没有价格，是图不会承认「更旧、但已证明没变」的状态。** M9.2 补的就是这条证明：从每个池自己的发现块一路查到目标块，只要中间没有第二条 `Sync` 日志，那更早的那条就是目标块上的价格。

- 结果：80 个池全部拿到目标块上的有效状态，**图里 80 个池、0 个跳过**（M9.1 是 24 / 56）。边从 48 条变成 **160** 条（80 池 × 双向）。
- 证明方式只有一种：**查日志**。整个过程没用一次 `eth_call`，没调用过 `getReserves()` 当市场状态（§5）。合约回答「现在是多少」，日志才能证明「这一块的中间人没来过」。
- 花的钱：**10,746 次** `eth_getLogs` 拿到 **230** 条 `Sync` 日志，扫过 **106,905,069** 个块次；同一条历史跑了两遍，选中的日志、顺序、图完全一致。

- **四个状态不是一句话**：Verified / State reconstructed / State valid at target / Graph eligible。这次四个数碰巧都是 80，但它们是四道独立判定，任何一道都能单独变小；本轮的 0 个 unavailable / 0 个 invalid 是实测结果，不是设定（§36）。
- 没做的事：不签名、不广播、不跑真套利（实测口径见第 6 节）；不声明这些池「现在」新鲜；不声明任何一个池可交易——找路径是下一个里程碑（§30）。

## 1. M9.1 遗留的问题（§35-1，任务书 §2）

M9.1 用四阶段验证确认了 80 个池，并把每池创建窗口里最后一条 `Sync` 写进状态层，图给出了 24 个池、48 条边，另外 56 个池被 `NotAtTargetBlock` 跳过。跳过原因写在 `data/evidence/m9/m9.1/raw/pass-a.json#state.skipped`（56 条，每条带自己的 `state_position`）。

问题不在图，在状态语义：图只承认「状态块 == 图块」，而 M9.1 从没打算让 56 个池的状态块等于图块——那些池的状态是它们创建窗口里的真实 `Sync`，块号从 4,057,629 到 37,223,883 不等（本轮按同一份 `pass-a.json` 重测），而图块是 37,224,031。所以 24/56 不是运气，是相等判定的必然：那 24 个池恰好和图块同一块发过 `Sync`。

同时 M9.1 的原始证据不能直接搬来当新鲜度证明：那次每池 `Sync` 搜索的上界是它自己窗口的 `to_block`（`crates/discovery/tests/historical_live.rs:202`），第一个窗口的池距目标块还差 3,300 万块，中间有没有 `Sync` 没人查过。§25 要的是「来自实际日志查询」，所以只能重跑。

## 2. 状态语义审计（§35-2，任务书 §3；结论详见 `M9.2 Semantic Audit.md`）

审计答案是 (A)：`PoolState.block_number` 是**这条 `Sync` 变异发生所在的块**，不是「状态被证明有效的块」。举证要点：

- `crates/state/src/store.rs:101-107` 逐字复制事件位置；`:117-135` 只允许严格更晚的 position 覆盖，所以存量 `(block, log)` 恒等于该池最新已应用 `Sync` 的位置，不含任何推断。
- `crates/state/src/snapshot.rs:24-28, 63-65, 71-73` 的 `position` 是「全 store 最远已应用位置」，是全局量，不是每池的证明边界。
- 架构里原本**没有任何字段**能写「这个状态有效一直到第几块」——缺的是携带证据的类型，不是判定条件写错了。
- §7 关于 `tx_index`：既有 replay 路径已经把 `(block_number, log_index)` 当规范全序，而且是**强制**的——`crates/chain/src/recorded.rs:141-150` 拒绝「按交易序排 ≠ 按 log_index 排」的块文件，`:151-159` 拒绝同块内 `log_index` 重复。因此不引入第二套排序；`tx_index` 只作为证据字段存在（`reads.rs:112-126` 的 `SyncRecord` 本来就带）。
- 真链侧的升级观测：本轮真实返回的 230 条 `Sync` 日志里，选序与逆序应答给出同一选择（`sync_reconstruction::a_node_that_answers_in_reverse_order_gives_the_same_selection`），代码推论因此有了实测对应物。

## 3. 选定的目标块模型（§35-3，任务书 §4/§18）

目标块是**显式输入**，不再由数据反推：`StateSnapshot` 加一个可选 `target_block`，`GraphBuild` 用它；不填（live/replay 全部既有路径）就沿用已应用位置，行为一字不变。

判定改成两档，两档都是证据：

| 档 | 条件 | 本轮命中 |
|---|---|---|
| 第一档（M9.1 的全部行为，原样保留） | `state.block_number == target` | 24 个池（`selected_sync_block` 就是 37,224,031） |
| 第二档（新增，必须有证据才成立） | `state.block_number < target` **且**该池有一条完整 `Sync` 扫描覆盖 `(state, target]` 且没发现更晚的 `Sync` | 56 个池 |

`state.block_number > target` 现在**可表达且必须被拒**（这是 NC1/NC5 的前置条件，M9.1 的类型根本写不出「目标块早于某个已存状态」）。第二档救不了晚于目标的状态：更晚的观测不能给更早的块定价，声称覆盖却从目标块之后才开始扫的区间，被同一个谓词拒绝。

证据类型只有两个，都是最小新增：`SyncScanCoverage{from, through}` 与快照上的可选 target。`StateUpdate` / `InMemoryStateStore` / `PoolState` 一字未改，也没有新增并行 store（§17：本轮 store_rejections 实测 0，见 `graph-integration.json#store_rejections`）。

## 4. `Sync` 重建方法（§35-4，任务书 §6/§7/§13/§14/§26）

`crates/discovery/src/reconstruct.rs` 的每池重建：从该池自己的发现块起，按固定块宽分片查 `Sync(uint112,uint112)`，**早停**——一旦选中的 `Sync` 落在某个片里，它之前的片不再需要往回扫，之后的区间已被覆盖；每池最多扫到目标块为止。

产出即 §13 要求的形状，且 target 与「最后权威 `Sync` 的位置」两个概念在证据里始终分开：`reconstruction.json` 的每行同时带 `target_block`、`selected_sync_block`、`selected_sync_log_index`、`selected_sync_tx_index`、`search_from`、`search_to`、`sync_events_seen`、`reason`、`reserve0/1`、`discovery_block`。

§14 溯源：`PoolState.block_number/log_index` 继续写 `Sync` 自己的位置，绝不改写成 target；`GraphEdge.state_position` 透传同一个位置。实测印证（`graph-integration.json#edges`）：160 条边里 **48 条**（24 池 × 双向）的 `state_position.block_number` 是 37,224,031，其余来自 47 个更早的块——即边的「定价时刻」逐条可查，没有被目标块抹平。

不越界（§26）：80 行里 `search_to` 全部等于 37,224,031，`selected_sync_block` 全部 ≤ 37,224,031（本轮从表逐行复核），测试 `no_request_ever_names_a_block_above_the_target` 在扫描器层同向把关。

本轮实测的重建结果分布：

- 80 个池共看到 **230** 条 `Sync` 日志（`reconstruction.json#sync_events_seen_total`，与逐行 `sync_events_seen` 之和一致）；选中状态落在 **47** 个不同块上。
- 与 M9.1 记录的 state block 相比：**4** 个池的重建结果更晚（`0x10650efc` 37,188,014→37,198,215；`0x3289dd77` 4,057,629→12,232,608；`0x5bef6275` 37,187,542→37,191,169；`0xf487d533` 37,189,041→37,191,169），52 个相同，**0 个更旧**。原因正是第 1 节说的窗口上界：M9.1 查到窗口末尾就停了。选择只能向前走，这本身就是排序与区间的交叉验证。
- 落后跨度（`sync-events.json#blocks_behind_target`）：min 0 / median 159 / max 33,165,620 / sum 106,841,368 / n 80。这是市场行为的描述（绝大多数池三年没动过价），不是缺陷，也不是「链很闲」的结论——见第 12 节。

## 5. 搜索策略（§35-5，任务书 §8/§11/§12）

**下界（§8）**：`from_block = discovery_block`，即该池自己的发现块，不用创世、不用「安全余量」。这条有硬代价，也如实写进 limitation：如果某个池的 `Sync` 早于发现它的 claim，那一行永远在区间外，该池会被报成 `state_unavailable` 而不是状态。

**块宽（§11 实测节点能力，`node-capacity.json`）**：探针 17 次请求、14 次被接受，150.75 s。节点的限制在**请求宽度**上：10,001 块的闭区间被接受，20,000 与 50,000 被拒（`first_rejection` 是 `-32602 block range greater than 10000 max`）。但真正绑住手脚的不是宽度，是**每片的日志量**：最忙的全链片 10,001 块返回 14,035 条日志、耗时 11,909 ms，逼近 `NODE_LOG_LIMIT`；一旦被截断，那段区间就再也证明不了「没有 `Sync`」（§25）。所以本轮沿用项目里量过的窄宽度，用更多请求换「不可截断」。

**代码默认宽度 4,999**（`default_chunk_blocks_in_code`），目标块实跑用 **9,999**（`chunk_blocks_used_by_the_run`）——9,999 是被接受的最大宽度的一半以内，且仍远低于节点上限。

**§12 A/B 对照**：两条策略按 §12 的四项（RPC 次数 / 返回日志 / 无关日志 / 墙钟）逐一处理，其中一条 arm 有完整文档、另一条没有，所以本轮**没有**给出「谁更便宜」的结论：

| 口径 | Strategy A（每池 `address` 过滤） | Strategy B（全链范围查询） |
|---|---|---|
| 完整文档 | `raw/strategy-a-pool.json` 已入库 | 无（两次尝试都没落盘，见第 15 节） |
| `eth_getLogs` 请求 | **21,439** | 未测 |
| 返回日志 | **227** | 未测 |
| 无关日志 | 该行写 null（每池过滤天然不产生） | 未测 |
| 墙钟 | 7,216,588 ms（一次自己节点的窗口） | 未测；只有逐片样本（12 片：min 316 / median 2,856 / max 11,909 ms） |
| 正确性 | 80/80 `target_state_valid` | 无法建立 |

因此 `strategy-comparison.json#decision` 里 `cheaper_arm_by_requests` 与 `correctness_first` 都是 **null 而不是 false**，`cost_assert_active: false`：§12 把正确性排在请求数之前，而一只没有文档的 arm 两样都没有，任何「B 更贵/更便宜」的说法都会是编造。表里同时记下「不许拿逐片中位数乘出整把成本」的理由（样本多数落在链上密集的近期区间）。

**同一选择的两把对照（有文档的那部分）**：目标块实跑（W=9,999）与 §12 实验 arm（W=4,999）按池语义键比对 80 行，本轮逐行量得：`chunks_scanned` 26 行不同、`search_from` 11 行不同、`logs_returned`/`sync_events_seen` 3 行不同（`0xf487d533` 2→6、`0xa47c8e56` 7→5、`0x5bef6275` 1→2，净 +3 即 227→230），**选中的 `Sync` 0 行不同**（`decision.target_run_against_the_measured_arm.same_selections: true`，由门禁测试 `the_target_run_selects_the_same_sync_as_the_experiment_arm` 对着入库字节断言）。宽度换了成本，没换状态——这正是 §12 要的答案形状。

**早停成本律**（逐行断言，非总计）：`floor = 选中 Sync 的块`（没选中则 `discovery_block`），`chunks_scanned == ⌈(target − floor + 1) / W⌉`，`search_from == max(discovery_block, target − chunks·W + 1)`，`search_to == target`，且 `Σ chunks_scanned == eth_getLogs 请求数`。本轮对两份文档各独立复算：W=9,999 侧 Σ = **10,746** = 请求数；W=4,999 侧 Σ = **21,439** = 请求数；80 行逐行成立。80 行里有 9 行的 `search_from` 被早停抬到 `discovery_block` 之上，全部由该律解释。

## 6. RPC 实测与安全（§35-6，任务书 §9/§28）

复用 `ChainAdapter` 与 `eth_getLogs`，没有新 RPC 客户端、没有新缓存、没有跨阶段复用（§9；`not_claimed` 第 5 条）。目标块实跑两把各自：**10,746 次 `eth_getLogs` + 1 次 `eth_chainId`**，230 条日志，106,905,069 块次，墙钟 3,073,928 ms / 2,683,183 ms，节点拒绝 0 次，轨迹完整（`events_dropped_beyond_the_cap: 0`）。

只读性是**量出来**的，不是声明的（`rpc-calls.json`、`summary.json#rpc`）：

- 本目录 5 份轨迹文件共 **41,512** 行调用，逐方法统计只有 `eth_chainId` 与 `eth_getLogs` 两种；`calls_outside_the_read_only_set = 0`。签名或广播必然在轨迹里留下读集合之外的方法名，这一项就是 §28 三项禁令（signatures / broadcasts / real_arbitrage = 0）的实测形式；运行期间没有加载私钥，代码里也没有广播路径。
- 第二道更强的核算：`per_run_call_accounting` 三行，每行「已落地行数 + 超限计数 = 扫描该解释的请求数（再加一次链 ID）」。本轮被计数而未落地的调用共 **1,440** 次，全部来自 §12 的 pool arm（单 sink 上限 20,000，`trace_is_complete: false`）；两把目标块运行一行都没丢。任何一次扫描解释不了的调用——无论有没有被写进轨迹——都会让这个和对不上，门禁就会红。

## 7. 状态覆盖（§35-7，任务书 §21）

`summary.json#state_coverage.equation`：**80 = 80 + 0 + 0**（verified = target_state_valid + state_unavailable + state_invalid），逐行分类在 `reconstruction.json#by_reason`：`target_state_valid` 80，其余三类各 0。

`summary.json#determinism`：`reconstruction_equal: true`、`state_and_graph_equal: true`、`row_order_equal: true`，两把 pass（a、b）。

## 12. 局限（§35-12）

1. **`tx_index` 只记录不使用**：重建选序用 `(block_number, log_index)`，这是 replay 路径既有的规范全序（由 `recorded.rs` 强制），不是本轮新造的第二套排序；但依赖前提是节点的 `logIndex` 是块内全局序号。
2. **下界等于发现块**：早于 claim 的 `Sync` 结构上在区间之外；这类池会被报成 `state_unavailable`。
3. **一个目标块、一个块宽、一个节点**：`node-capacity.json` 的每个数属于那个端点那一次窗口，随时间失效。
4. **新鲜度是历史区间内的「没有更晚」，不是「现在也新鲜」**（§25 的口径）：`state_valid_at_target` 只说扫描证明了 `(state, target]` 内没有该池的第二条 `Sync`。它不是实时的反爬对手，`not_claimed` 第 2 条明确拒绝 live 意义的 fresh。
5. **日志量截断风险仍在**，只是被窄宽度避开：若某段区间被 `NODE_LOG_LIMIT` 截断，那段就不能作为「无 `Sync`」的证据；本轮没有区间被截断（pool arm 与两把 pass 的 `scan_incomplete` 都是 0）。
6. **§12 只有一条 arm 有完整文档**：全链 arm 的总成本与正确性都没测，所以「哪种查询更省」在本里程碑是开放问题，不是结论。
7. **墙钟不可跨把比较**：同一 arm 在同一目标块跑两把，请求数完全一致，时长差 10.9%（3,073,928 vs 2,683,183 ms）。所以 `duration_is_not_the_criterion`，成本判定只读请求数。
8. **fee 仍未举证**：80 个 attested 池的 fee 全是 `null`，边按 `fee: null` 定价，与 M9.1 留下时一致（`not_claimed` 第 3 条）。
9. **不判可交易性**：本轮终点是 `GraphSnapshot`，PathFinder 属于下一里程碑（§30；`not_claimed` 第 1 条）。
