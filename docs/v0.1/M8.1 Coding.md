# 2. 核心原则

## 2.1 Correctness > Instrumentation

任何 instrumentation 都不能改变：

```text
Protocol
→ State
→ Graph
→ Opportunity
→ Simulation
→ Risk
→ Preflight
→ Build
→ Sign
→ Submit
→ Receipt
→ Settlement
```

的行为。

Instrumentation 是旁路能力。

---

## 2.2 不允许使用 wall clock 推导链上事实

区分：

### Chain time

例如：

```text
block.timestamp
```

它属于链上事实。

### Measurement time

例如：

```text
std::time::Instant
```

它只用于测量本机经过时间。

两者绝对不能混淆。

---

## 2.3 latency measurement 必须使用 monotonic clock

所有 duration measurement 必须基于：

```rust
std::time::Instant
```

或者等价的 monotonic clock。

禁止：

```rust
SystemTime::now()
```

用于 duration subtraction。

原因：

系统时间可能发生 NTP adjustment / clock jump。

# 5. Latency Trace 数据结构

需要定义一个统一的 trace。

概念模型：

```rust
struct LatencyTrace {
    trace_id: TraceId,

    chain_id: u64,

    opportunity_block: u64,
    opportunity_tx_index: Option<u64>,

    started_at: Instant,

    stages: Vec<LatencyStage>,

    completed: bool,
}
```

但不要机械照抄。

必须结合当前代码架构设计。

---

# 6. Trace ID

每一次 opportunity lifecycle 必须有唯一：

```text
trace_id
```

建议：

```text
UUID
```

或者 deterministic identifier。

但必须满足：

* 不与 tx hash 混淆
* 不与 block hash 混淆
* 不与 opportunity ID 混淆
* 可以关联同一 opportunity 的 simulation / execution / receipt
* 不包含敏感信息

如果项目已有稳定 opportunity ID，则优先复用已有 identity，而不是再造一套完全重复的 identity。

# 8. 每个 stage 的数据模型

建议：

```rust
struct LatencyStage {
    stage: Stage,
    started_at: MonotonicTimestamp,
    ended_at: MonotonicTimestamp,
    duration_ns: u64,
}
```

但可以根据现有代码进行合理调整。

必须保证：

```text
duration_ns >= 0
```

不能出现负数。

---

# 9. Stage 状态

不要假设每个 stage 一定完成。

必须支持：

```text
Started
Completed
Failed
Skipped
Cancelled
```

例如：

```text
Opportunity
→ Simulation
→ Rejected
```

那么：

```text
Simulation = Completed
Risk = Completed
Preflight = Skipped
Build = Skipped
Sign = Skipped
Submit = Skipped
```

而不是把 skipped stage 当成 0ms。

这是非常重要的。

---

# 10. Stage duration 与 total duration

至少提供：

```text
stage_duration
```

以及：

```text
total_duration
```

例如：

```text
Observation
  5ms

StateUpdate
  2ms

GraphUpdate
  1ms

OpportunityDetection
  3ms

Simulation
  14ms

Risk
  0.2ms

Preflight
  4ms

Build
  1ms

Sign
  0.8ms

Submit
  8ms

Inclusion
  1.2s

Receipt
  10ms
```

总时间不能简单认为是所有 stage duration 的无脑求和。

因为未来可能存在：

```text
parallel stages
```

因此必须定义：

```text
wall_clock_total
```

和：

```text
stage_duration_sum
```

两个概念。

# 11. 两种 latency 必须明确区分

## 11.1 Local Processing Latency

例如：

```text

Simulation
```

这些主要是本地处理。

## 11.2 External / Chain Latency

例如：

```text

Submit
Inclusion
Receipt
```

其中包含 RPC / network / sequencer / chain。

不要把它们混成一个 CPU latency。

```text

```

以及：

```text
ExecutionPreparationLatency
```

即：

```text

        ↓

```

以及：

```text

```

即：

```text

        ↓
Included
```

以及：

```text
SettlementLatency
```

即：

```text

        ↓

```

以及：


即：

```text

```



# 14. Opportunity 与 Execution 必须解耦

一个非常重要的设计要求：

```text
OpportunityTrace
```

不等于：

```text
ExecutionTrace
```

因为：

```text
Opportunity detected
→ Risk Reject
```

也应该有 latency。

同样：

```text
Opportunity detected
→ Simulation Reject
```

也应该有 latency。

因此建议：

```text
OpportunityTrace
       │
       ├── Detection
       ├── Simulation
       └── Decision
       
ExecutionTrace
       │
       ├── Preflight
       ├── Build
       ├── Sign
       ├── Submit
       ├── Inclusion
       ├── Settlement
       └── ProfitVerified
```

二者可以通过：

```text
trace_id
opportunity_id
```

关联。

---

# 15. 不允许为了 measurement 改变执行语义

尤其禁止：

```text
sleep()
yield_now()
extra RPC
extra simulation
extra balanceOf
extra receipt query
```

来获得 measurement。

Instrumentation 必须尽量：

```text
O(1)
```

并且只读取已经存在的数据。

如果一个 latency point 需要新增 RPC：

> 不要做。

因为新增 RPC 本身会改变 latency。

---

# 16. Observation timestamp

Observation 必须定义清楚。

不能写：

```text
observation = when Opportunity loop starts
```

如果实际上 block 已经早就到了。

优先记录：

```text
block_observed_at
```

也就是系统第一次确认：

```text
block N exists
```

的时间。

如果 WS notification 只是 hint：

```text
notification_at
```

和：

```text
block_confirmed_at
```

必须分开。

这一点与 M5 的：

> notification 是 hint，block facts 必须重新读取

原则保持一致。

---

# 17. Opportunity Detection timestamp

必须定义为：

> Opportunity engine 首次确认一个合法 opportunity 的时间。

不是：

```text
log received
```

不是：

```text
graph update started
```

不是：

```text
simulation started
```

而是：

```text
Opportunity object accepted
```

的时刻。

---

# 18. Simulation latency

必须测：

```text
simulation_start
simulation_end
```

但：

```text
simulation_end
```

必须是 simulation result 已经完整生成的时间。

包括：

* success
* revert
* timeout
* error

都必须结束 trace。

---

# 19. Risk latency

Risk 是一个独立阶段。

例如：

```text
SimulationResult
      ↓
RiskEngine
      ↓
RiskDecision
```

测量：

```text
risk_start
risk_end
```

不要把：

```text
simulation + risk
```

合成一个 duration。

---

# 20. Preflight latency

M7 的 14 项 preflight 已经是真实执行安全边界。

M8.1 必须测：

```text
preflight_start
preflight_end
```

同时记录：

```text
preflight_result
```

但：

> 不要增加新的 preflight check。

---

# 21. Build / Sign / Submit

分别测量：

```text
Build
Sign
Submit
```

注意：

### Build

从：

```text
Build started
```

到：

```text
Unsigned transaction ready
```

### Sign

从：

```text
Signing started
```

到：

```text
Signed raw transaction ready
```

### Submit

从：

```text
sendRawTransaction request started
```

到：

```text
RPC response received
```

不要把 receipt inclusion 放进 Submit duration。

---

# 22. Inclusion latency

定义：

```text
submit_response_time
        ↓
receipt.included_time
```

如果 submit RPC 返回 tx hash：

```text
T_submit_response
```

是：

```text
eth_sendRawTransaction
```

返回成功的时间。

然后：

```text
T_included
```

是 receipt 对应 block 被确认的时间。

---

# 23. Receipt latency

不要把：

```text
Submit → Included
```

和：

```text
Included → Receipt fetched
```

混成一个指标。

应该：

```text
Submit
 ↓
Inclusion
 ↓
Receipt
```

分别测。

---

# 38. Performance overhead

Instrumentation 本身必须尽可能轻。

原则：

```text
timestamp
→ store
→ timestamp
```

不要在每个 stage：

```text
serialize JSON
write disk
flush
RPC
lock global mutex
```

正确架构应该类似：

```text
Hot Path
   ↓
LatencyTrace
   ↓
In-memory event
   ↓
flush outside critical path
```

如果当前架构不适合异步 exporter：

> 可以先同步收集，但不要为了 M8.1 引入复杂 telemetry infrastructure。

---

# 39. Thread safety

当前项目是 single execution lane。

不要为了 telemetry 引入：

```text
global mutable singleton
```

优先：

```text
trace owned by lifecycle
```

必要时通过：

```text
&mut LatencyTrace
```

传递。

不要制造全局锁成为新的 latency bottleneck。

# 43. 必须建立 latency budget

不是性能目标，而是 baseline reference。

建议定义：

```text

Submission

```

例如：

```text
Detection
  Observation → Opportunity

Preparation
  Opportunity → Submit

Network
  Submit → Inclusion

Settlement
  Inclusion → ProfitVerified
```

不要直接规定：

```text
Simulation must < 10ms
```

因为当前还没有数据。

M8.1 的任务是：

> **先测出事实，再决定 M8 后续优化目标。**

# 44. Evidence Integrity

M8.1 产生的 evidence 必须：

* 可复现
* 可机器解析
* 不修改 M7 evidence
* 不覆盖历史运行
* 不混淆 fixture / replay / live
* 包含 commit / git revision
* 包含 chain ID
* 包含 execution mode
* 包含 sample source

建议 metadata：

```json
{
  "schema_version": 1,
  "git_revision": "...",
  "chain_id": 91342,
  "source": "live|replay|fixture",
  "execution_mode": "observe|build-only|submit",
  "generated_at": "...",
  "sample_count": 0
}
```

其中：

```text
generated_at
```

属于 evidence metadata，不用于计算 latency duration。

---

# 45. Replay 与 live 必须区分

输出：

```text
source = replay
```

或者：

```text
source = live
```

绝对不能把 replay latency 和 live network latency 混合统计。

例如：

```text
fixture simulation = 2ms
live simulation = 18ms
```

不能生成：

```text
simulation p50 = 10ms
```

除非明确这是混合统计，而且通常不应该这么做。

---

# 46. 不允许伪造真实 latency

这是 M8.1 最重要的验收原则之一。

禁止：

```text
sleep(10ms)
```

制造网络延迟。

禁止：

```text
synthetic timestamp
```

冒充真实链数据。

禁止：

```text
historical timestamp interpolation
```

冒充真实 observation time。

禁止：

```text
missing timestamp
→ estimated timestamp
```

除非字段明确标记：

```text
estimated
```

并且不进入真实 latency baseline。


并遵守 sample policy。

存在 deterministic latency fixture。

### Q — M7 Regression

M7 correctness 全部保持。
