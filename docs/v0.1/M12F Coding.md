# M12-F Coding Agent Task — 持久化执行台账与进程重启恢复安全

## 1. 任务目标

基于当前 `origin/main`，为 GIWA EVM MEV Bot 建立可靠的持久化执行台账（Durable Execution Ledger），使进程在交易提交前、提交过程中、收到响应后以及等待回执期间退出时，都能够在重启后恢复原有执行事实。

本轮的核心目标：

1. 交易发送前，必须持久化足以识别和恢复该笔交易的信息。
2. 进程重启后，能够恢复未完成交易及其 nonce 占用状态。
3. 对于提交结果不确定的交易，不得因进程重启而自动重新广播。
4. 不得仅凭 receipt 为 `null`、交易查询为空或短暂查询失败，就认定交易从未被节点接受。
5. 已有 M10 Executor、M11 Multi-Lane 和 M12-E 单次提交安全语义必须继续成立。
6. 所有核心故障场景都通过离线测试和可复核证据验证。

本轮不追求通用任务队列、不重构整个执行系统，也不引入新的交易执行状态机框架。

## 2. 当前基线与前置条件

开始修改前，先核验：

* 当前分支及 `origin/main` 是否包含 M12-E 的提交 `d4d047f`。
* M12-E 完成报告、manifest、生产源码及测试文件是否与报告一致。
* `SubmissionOutcome`、交易本地哈希生成、nonce lane 占用与释放、receipt 跟踪的实际调用链。
* 当前执行记录的数据结构、创建时机、状态变化和进程退出后的丢失路径。
* M10/M11 的状态机和已有持久化能力，避免重复实现已有功能。

必须先给出简短的代码路径审计结果，再开始修改。若实际代码与本任务假设不符，以仓库事实为准，并在报告中说明。

基线不符、M12-E 关键安全语义不成立或工作区存在无法解释的历史证据变化时，先停止并报告，不要覆盖现状。

## 4. 核心安全原则

### 4.1 先持久化，再发送

任何会导致真实交易字节被发送到网络的执行路径，必须先成功持久化发送意图和足够的恢复信息。

如果持久化失败：

* 禁止进入发送路径。
* 不得将交易视为已提交。
* 不得释放已经被其他有效执行占用的 nonce。
* 必须返回明确的本地持久化错误。
* 不得静默降级为仅内存模式。

必须通过测试证明：在持久化失败时，HTTP 发送到达次数为 0。

### 4.2 将交易意图与提交事实分开

台账至少应能区分以下事实：

* 已准备，但尚未允许发送。
* 已持久化发送意图，可能尚未实际发送。
* 已开始发送，提交结果可能未知。
* 端点接受了与本地交易字节相符的哈希。
* 已收到确定的拒绝结果。
* 已观察到交易回执。
* 已观察到回执对应的成功或失败执行结果。
* 记录存在异常或需要人工处理。

以上为需要覆盖的语义，不要求逐字照搬为 enum。优先复用现有 `SubmissionOutcome`、执行记录和状态机，避免重复定义相互冲突的状态。

必须区分“本地观察到的事实”与“尚未确认的推断”。

尤其注意：

* 持久化发送意图成功，不代表交易一定已经发送。
* 发送调用开始，不代表节点一定收到交易。
* `Accepted` 不代表交易已经进块。
* `receipt == null` 不代表节点没有接收交易。
* 查询不到交易不代表交易从未广播。
* 进程崩溃后，无法仅靠本地状态判断交易一定没有发送。

### 4.3 Unknown 是需要保留的安全状态

当交易提交结果为 `Unknown` 时：

* 持久化本地交易哈希。
* 保留 nonce、lane、交易身份及必要的恢复元数据。
* 重启后恢复为未解决状态。
* 不得自动重新广播原交易。
* 不得自动创建一笔替代交易绕过它。
* 不得仅因 receipt 查询为空就释放 nonce。
* 不得把 `Unknown` 转换成 `Rejected`。
* 不得在内存状态恢复失败时悄悄丢弃该记录。

如果现有系统没有安全的人工恢复入口，本轮至少应保证未知记录可查询、可审计，并阻止相关 lane 继续提交冲突交易。

## 5. 台账数据设计

首先审计当前 `ExecutionRecord` 及相关类型，再设计最小持久化记录。至少评估以下字段是否必要：

* schema/version。
* 稳定的 execution ID。
* 本地交易哈希。
* nonce 与 lane 标识。
* 链标识及必要的账户标识。
* 当前执行阶段。
* 最近一次提交结果分类。
* 创建时间及最近更新时间。
* 交易发送意图是否已持久化。
* 是否已观察到端点接受、交易回执及最终执行结果。
* 需要恢复的执行参数或安全引用。
* 记录完整性信息及可定位的错误原因。

敏感字段必须按必要性处理：

* 不得写入 RPC/WS URL 中的 token、API key 或凭据。
* 不得记录私钥、助记词或其他签名秘密。
* 不要为了方便恢复而默认持久化所有原始请求和响应。
* 原始签名交易字节是否需要落盘，必须根据当前签名流程、恢复需要和安全边界论证；不得自行假定所有交易都可安全明文保存。
* 若恢复所需的信息无法安全持久化，必须明确失败并阻止发送，而不是留下不可恢复的记录。

稳定 ID 和交易哈希的关系必须明确。对于已签名交易，优先使用真实本地交易哈希识别同一笔交易，不要用时间戳或随机 ID 替代交易身份。

## 6. 原子性、损坏检测和版本管理

持久化实现必须回答并测试以下问题：

1. 写到一半进程退出，会留下什么？
2. 磁盘写入失败时，旧记录是否仍可恢复？
3. 最后一次记录损坏时，启动是否会静默丢弃它？
4. 重复恢复同一份台账，是否会重复占用 nonce 或重复触发执行？
5. 新版本程序读取旧 schema 时如何处理？
6. 未知版本或不兼容记录是否会被忽略？

要求：

* 写入必须具备明确的原子性策略，不能直接覆盖唯一的有效文件后再寄希望于完整写入。
* 根据所选存储机制实现必要的临时文件、同步、原子替换或追加日志校验。
* 启动时检测损坏、截断、不支持的版本和重复记录。
* 对无法安全恢复的记录采取 fail-closed 策略。
* 不得在检测到损坏后自动创建空台账并继续交易。
* 不得通过忽略解析失败的最后一条记录来绕过安全错误。
* 对每一种可恢复和不可恢复的损坏情况，都要有明确的诊断信息。

不要宣称已经实现掉电级持久性，除非同步和文件系统语义确实支持这一结论。报告中应区分进程崩溃、操作系统崩溃和硬件掉电的保证范围。

## 7. 启动恢复流程

恢复必须在任何可能签名或发送交易的执行入口之前完成。

推荐逻辑：

1. 加载并验证台账。
2. 检查 schema 和记录完整性。
3. 重建所有未完成交易的本地执行状态。
4. 重建对应 nonce lane 的占用状态。
5. 恢复本地交易哈希及 receipt 跟踪关联。
6. 标记无法确定实际提交结果的记录。
7. 阻止受未解决记录影响的 lane 继续提交冲突交易。
8. 只有在全部恢复成功后，才允许相关执行路径进入正常流程。

如果任何关键记录无法恢复：

* 启动应失败，或者明确禁止相关交易执行。
* 不得清空台账后继续运行。
* 不得因一条坏记录而把整份文件无条件重置为空。
* 必须在日志和证据中明确指出失败原因。
* 不得将无法恢复的记录误报为已完成。

必须覆盖所有生产入口，包括 M10 Executor、M11 Multi-Lane，以及 M12-D 已审计的 `arbitrage::run_once` 和 `cli::run_validation` 等相关路径。以实际代码审计为准，不能仅在 CLI 主入口加一个恢复调用就宣称所有路径都受到保护。

## 8. 必须实现的崩溃恢复测试

使用离线临时目录、内存故障注入或本地测试桩完成，不连接真实网络。

### F1：持久化成功，发送前崩溃

* 创建交易意图并持久化。
* 在真实发送之前模拟进程退出。
* 重启并恢复。
* 验证记录仍然存在。
* 验证系统不会未经明确恢复策略就自动重发。
* 验证 nonce 状态符合已持久化的执行事实。

### F2：发送后响应丢失，随后崩溃

这是本轮最高优先级测试。

* 本地计算交易哈希。
* 持久化发送意图。
* 测试桩完整接收交易请求后丢弃响应。
* 客户端得到 `Unknown`。
* 持久化该结果。
* 模拟进程退出。
* 新进程重新加载台账。
* 验证本地哈希、nonce、lane 和未知状态全部恢复。
* 验证恢复期间及恢复完成后，不会自动再次广播。

### F3：发送过程中进程崩溃

* 在网络发送已开始但结果尚未持久化的窗口模拟退出。
* 重启后必须把记录识别为可能已发送。
* 不得把该记录视为确定未发送。
* 不得自动重发。

### F4：端点返回 Accepted 后崩溃

* 端点返回与本地交易一致的哈希。
* 在更新最终本地状态前模拟退出。
* 重启后不得误报交易已经进块或执行成功。
* 必须保留交易跟踪所需信息。

### F5：收到回执后、落盘前崩溃

* 模拟已观察到回执，但对应持久化更新尚未完成。
* 重启后应进入可继续核对的安全状态。
* 不得丢失原交易身份或将其错误地视为未发送。

### F6：台账文件截断或损坏

覆盖至少：

* 文件为空。
* JSON/二进制记录截断。
* 校验失败。
* 不支持的 schema 版本。
* 重复的 execution ID 或冲突 nonce 记录。
* 最后一条记录写入一半。

验证系统不会静默清空台账或继续提交冲突交易。

### F7：重复恢复

* 使用相同台账连续启动两次。
* 验证记录数量和状态不变。
* 验证同一 nonce 不会被重复占用或分配给冲突执行。
* 验证恢复过程不会触发签名或网络发送。

### F8：持久化失败

注入目录不可写、写入失败、同步失败或原子替换失败。

验证：

* 发送请求到达次数为 0。
* 不会进入成功提交状态。
* 不会静默回退为内存模式。
* 错误能被调用方识别。

### F9：旧状态与未知交易恢复

构造至少一笔 `Unknown` 交易，并验证：

* `receipt == null` 不会释放 lane。
* `eth_getTransactionByHash` 返回未找到不代表交易未被接受。
* 查询暂时失败不改变为 `Rejected`。
* 重启后仍然保留未解决状态。
* 不会签署或发送替代交易绕过该 nonce。

所有故障测试必须验证实际状态变化和实际发送次数，不能只断言某个函数返回了预期错误。

## 9. 状态迁移和并发一致性

持久化状态变化与内存状态变化必须有明确顺序。

要求审计并验证：

* 两个执行协程不会同时为同一个 nonce 建立冲突的持久化意图。
* lane 占用、持久化更新和执行提交之间不会出现可导致重复分配的窗口。
* 状态更新失败时，不会让内存状态与持久化状态静默分叉。
* 重复写入同一结果不会生成重复执行记录。
* 已完成的记录在归档或清理前仍可满足现有 receipt 跟踪和审计需要。
* 台账恢复和新交易分配之间存在明确的同步边界。

不要为解决持久化而重写 M11 的 Multi-Lane 调度算法。优先在现有抽象上增加必要的持久化边界和恢复保护。

证据门应至少包含以下负控制：

1. 将 `Unknown` 恢复结果篡改为 `Rejected`，检查器必须失败。
2. 将恢复后的 nonce/lane 占用改为空闲，检查器必须失败。
3. 将发送次数改成 2，检查器必须失败。
4. 将本地哈希一致性改为 false，检查器必须失败。
5. 将损坏台账的结果改为“成功恢复”，检查器必须失败。
6. 将持久化失败时的发送次数改为非零，检查器必须失败。
7. 将未支持的 schema 版本伪装为成功，检查器必须失败。

检查器不能读取自己生成的结论来证明自身正确，必须独立读取原始测试产物、实际记录或明确的测试输出。
