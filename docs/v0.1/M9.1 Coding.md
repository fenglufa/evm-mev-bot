# 1. Objective

Implement automatic V2-style pool discovery for GIWA Testnet.

The target flow is:

```text
GIWA Chain
    ↓
Historical Logs
    ↓
PairCreated Decoder
    ↓
CandidatePool
    ↓
Protocol Verification
    ↓
PoolAttestation
    ↓
Pool Registry
    ↓
StateStore
    ↓
GraphSnapshot
```

The central rule is:

```text
Discovery != Trust
```

A discovered address is only a candidate until protocol verification succeeds.

Do NOT treat every `PairCreated` event as a trusted V2 pool.

# 4. CandidatePool

Introduce a candidate representation if the current architecture does not already provide one.

Conceptual fields:

```text
CandidatePool
├── chain_id
├── pool_address
├── discovery_source
├── factory_address (when known)
├── discovery_block
├── discovery_tx_hash
├── discovery_tx_index
├── discovery_log_index
└── provenance
```

Use existing strongly typed identifiers wherever possible.

Do not introduce raw strings where existing project types are appropriate.

The candidate represents:

> “This address was discovered.”

It does NOT represent:

> “This address is a verified V2 pool.”

# 6. PairCreated Decoder

Support the V2-style:

```text
PairCreated(
    address indexed token0,
    address indexed token1,
    address pair,
    uint256
)
```

Decode:

```text
token0
token1
pair
pair_index
```

from the actual event encoding.

Validate:

```text
topics count
data length
address encoding
uint encoding
```

Malformed logs must return a structured error or be rejected according to the existing protocol error conventions.

Do not panic.

Do not use:

```text
unwrap()
expect()
panic!()
```

in production code.

The decoder must not modify Registry.

The decoder only produces a candidate.

Correct:

```text
Raw Log
 ↓
PairCreated
 ↓
CandidatePool
```

Incorrect:

```text
Raw Log
 ↓
Registry.attest()
```

# 9. Protocol Verification

Every CandidatePool must pass protocol verification before entering Registry.

At minimum verify:

```text
Identity
Token Pair
State
```

The verification process must produce evidence.

Conceptually:

```text
CandidatePool
    ↓
Identity Check
    ↓
Token Check
    ↓
State Check
    ↓
Verified Pool
```

---

# 10. Identity Verification

Verify that the candidate address behaves as a V2-style pair.

Use actual chain evidence.

Possible evidence sources include:

```text
eth_getCode
eth_call(token0())
eth_call(token1())
eth_call(getReserves())
```

Use whichever checks are justified by the existing architecture.

Do not claim a contract is V2-compatible based only on:

```text
PairCreated
```

or only on:

```text
Sync event shape
```

Identity evidence must be recorded.

---

# 11. Token Verification

Verify:

```text
token0()
token1()
```

and construct:

```text
TokenId(chain_id, address)
```

Reject:

```text
token0 == token1
```

Reject chain mismatches.

Reuse existing Registry validation rules instead of duplicating them.

---

# 12. State Verification

The market graph requires authoritative pool state.

The preferred state evidence remains:

```text
Sync(uint112,uint112)
```

Do not invent reserves from Swap events.

Do not infer reserves from prices.

Do not infer reserves from PairCreated.

A Candidate without authoritative state evidence must not be inserted into the tradable Graph.

If current verification architecture requires `getReserves()` for identity verification, that result must not silently replace the project's authoritative Sync state model.

Keep these concepts separate:

```text
Contract Verification State
```

and

```text
Authoritative Market State
```

---

# 14. Fee Rule

This is a hard correctness requirement.

Never assume:

```text
V2 => 0.3%
```

Never silently convert:

```text
None
```

to:

```text
997/1000
```

If fee cannot be proven:

```text
fee = None
```

If a trusted source proves the fee:

```text
fee = Some(proven_fee)
```

The evidence must identify why the fee is trusted.

This task must contain a test proving that unknown fee remains unknown.

Do not weaken M3's fee correctness assumptions.

# 15. Factory Provenance

If PairCreated provides a factory/emitter address, retain it as discovery provenance.

However:

```text
Factory emitted PairCreated
```

must NOT automatically mean:

```text
Pool trusted
```

Factory provenance is discovery information.

Protocol verification remains mandatory.

Do not turn the factory list into the sole trust mechanism.
