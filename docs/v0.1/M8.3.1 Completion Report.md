## 0. 白话版结论（先看这一段）

M8.2 那一刀量出来的是：**一次模拟要问节点 80 个问题，其中 41 个是把同一个问题再问一遍**
（同一个块、同一个地址、同一份状态），而这 80 次排队等回答，占掉整段模拟时间的
99.8 %–99.9 %。

M8.3.1 只做一件事：**让这一场模拟记住自己已经问过的问题**。同一个块里同一份状态，第二次
要用的时候不再打电话，直接看自己记下的答案。

实测结果（真实 GIWA Testnet，6 把 run，每边 3 把，`--execution-mode build-only`）：

| | M8.2 基线（reuse 关） | M8.3.1（reuse 开） |
| --- | --- | --- |
| 一次模拟问节点 | **80 次** | **39 次** |
| 其中重复提问 | **41 次** | **0 次** |
| 一次模拟等多久 | 33.3–36.6 秒 | 13.7–15.8 秒 |
| 一次模拟总共多久 | 33.3–36.6 秒 | 13.7–15.8 秒 |
| 模拟结果 | 完全没变（在能对照的固定块上逐字段验证） |  |
| 花钱 / 签名 / 广播 | 0 / 0 / 0 | 0 / 0 / 0 |

千分位上：**等节点的时间砍掉 575 ‰，模拟总时长砍掉 575 ‰**
（整数写法：省掉的 59 516 902 916 ns ÷ 基线的 103 393 656 000 ns，两边各 3 把合计）。
换算成大白话：**原来跑一次模拟要 33 秒，现在 14 秒，短了一半还多一点**。

这个数不是意外：M8.2 当时按重复读自己耗的时间预测「把这些重复消掉，能省 RPC 时间的
549 ‰–617 ‰」，这一刀实测 **575 ‰**，落在它给的区间里。

一个比喻：以前是每次做菜都重新打电话问供应商「今天鸡蛋多少钱」，问 80 次、其中 41 次问的是
同一天同一个摊位的同一件事；现在**这一场做菜从头到尾只问一次，之后看自己记的那张纸**。
纸随着这场做菜结束就扔掉——下一场做菜重新问、重新记（任务书 §2、§11 要的正是这个）。

**没有做的事**（任务书 §13 逐条禁止，全部未做）：没有批量 RPC、没有并发、没有预取、没调连接池、
没改 keep-alive、没改重试、没动 REVM、没改模拟/机会/风险/执行/交易的任何算法、没有全局缓存。
唯一变量就是这把「记住已问过」的开关。

## 1. Q1 — State read reuse 是否正确？

**正确，而且是三重证明：单元测试钉语义、固定块 A/B 钉结果、真实 run 钉账目。**

### 1.1 边界在哪

四个方法各有一个唯一的复用入口，全在 `crates/simulation/src/state.rs`：

| 方法 | 入口 | 行号 |
| --- | --- | --- |
| `eth_getBalance` | `balance_at` → `chain.get_balance` | state.rs:846 |
| `eth_getTransactionCount` | `nonce_at` → `chain.get_nonce` | state.rs:871 |
| `eth_getCode` | `code_at` → `chain.get_code` | state.rs:894 |
| `eth_getStorageAt` | `storage` → `chain.get_storage_at` | state.rs:956 |

缓存是 `RpcStateProvider` 的一个字段（`Mutex<StateReadCache>`，四个 map：code/balance/nonce/storage，
state.rs:308-314），provider 本身在 `crates/pipeline/src/arbitrage.rs:393` 每次模拟现场构造，
所以**缓存生命周期 == 一次模拟**（§2、§17）。锁用
`unwrap_or_else(std::sync::PoisonError::into_inner)`（state.rs:814-818），不是新的 panic 入口。

### 1.2 canonical key（§3）

* code / balance / nonce：`StateReadKey { chain_id, block, address }`（state.rs:184-188）
* storage：`StorageCacheKey { chain_id, block, address, slot }`（state.rs:203-208）

nonce 的 `block_tag`：**没有再加一个字段**。key 里的 `block` 只可能来自
`self.pin.number`（三个构造点 state.rs:917/949/974 全都取 provider 自己的 pin），
读取也按这个高度发出（`get_nonce(key.block, key.address)`），所以块号已经完整表达了
「问的是哪个块」——这正是 §3 允许的「基于实际语义设计，不要为了凑字段重复存储」。
测试 `reuse_reads_at_the_pin_and_never_at_a_later_height`（state.rs:2100）钉住这一点。

`eth_call`：**完全没缓存**。§3 说不能自己猜 key，就没有为它造 key——检测侧
（`arbitrage.rs:1221` 的 `price_legs`）走的是 `ChainAdapter::call`，不经过这个边界，
`StateReadCache` 里也没有第五个 map。

### 1.3 只缓存成功的读（§4）

`balance_at` / `nonce_at` / `code_at` 的形状都是：查缓存 → 未命中就发 RPC →
**`?` 成功之后**才 `put_*`。失败直接返回 `ProviderError::Unavailable`（state.rs:848 的
`map_err(|error| self.unavailable(...))`），失败值不进缓存。
测试：`a_failed_read_leaves_nothing_to_reuse`（state.rs:1992）、
`a_failing_node_is_unavailable_not_missing`（state.rs:1587）。

**80 → 39，每一把都是 39，零方差。**

| `eth_getStorageAt` | 20 | 20 | 0 |

固定块（stub）那一组：`80 → 39` 也逐格对上，只有 storage 是 21 而不是任务书示例的 20：
fixture `fixtures/simulation-m4/dump-37191169.json` 的那笔路由在这条路径上多碰一个 slot，
于是基线是 `23/18/18/21/1 = 81 次调用`、`80 次状态读取（不含 header）`，
reuse 侧是 `6/6/6/21/1 = 40 次调用 / 39 次状态读取`。**没有为了对上 20 而改报告，也没有改代码。**

### method sequence

§7 还要求比较调用顺序。顺序比较只在**共享同一个 pinned block** 的两臂之间才有意义，
所以由固定块 A/B 承担：`crates/simulation/tests/state_reuse_ab.rs:797` 的 `is_subsequence`
断言 reuse 臂的调用序列是基线臂**按原序删掉整条调用**的结果——没有新调用插进来。
live 两臂跑在不同的 head 上（6 个块号互不相同），它们的调用列表不是「同一串问题的两个答案」，
跨臂做子序列检查比的是链上状态而不是行为，因此明确**不做**，并在
`rpc-count-comparison.json` 的 `method_sequence.live_arms` 里写清了原因。

## 8. §12 的两本账怎么读（38 vs 39、77 vs 41，全部解释，不改数）

任务书 §12 的示例是 `code 6/17, balance 6/12, nonce 6/12, storage 20/0, 合计 miss 39 / hit 41`。
实测（reuse 臂，每把；三把逐格相同）：

| kind | hit | miss | 该方法 wire 数 | `misses_equal_wire` |
| --- | --- | --- | --- | --- |
| code | 27 | 6 | 6 | ✅ |
| balance | 12 | 6 | 6 | ✅ |
| nonce | 12 | 6 | 6 | ✅ |
| storage | 26 | 20 | 20 | ✅ |
| 合计（四类） | 77 | **38** | 38（+1 header = **39**） | |

每一列的出处：hit / miss 取自每把自己的 `simulation-traces.jsonl` 行（`state_read_cache`，
边界在读到答案那一刻记的数）；wire 列取自 `rpc-count-comparison.json` 的每把 per-method 计数
（请求计数器，与边界无关）。**每把的 lookups（= hit + miss，边界被问的次数）不在每把的记录里**，
它只以三把合计的形式写在 `cache-stats.json`：code 99 = 81 hit + 18 miss、balance 54 = 36 + 18、
nonce 54 = 36 + 18、storage 138 = 78 + 60，四类合计 345。因为每把的 hit/miss 三把完全一致，
每把被问的次数就是 33 / 18 / 18 / 46（合计 115 = 77 + 38）——这是合计除以 3，不是另一次测量。

三处对不上，每一处都有原因，而且**都是任务书自己的口径差异**：

1. **miss 38 vs 39**：`eth_getBlockByNumber` 不属于这四类（§1 明写它保持原行为、不进 cache），
   所以边界不会把它记成 miss。38 次 miss + 1 次 header = wire 上真实到的 39 次调用。
   也就是说「39」在**请求计数器**里，「38」在**边界账**里，两个都对，差的就是那次 header 读。
2. **code hit 27 vs 17、storage hit 26 vs 0**：§12 的 hit 列数的是**这一刀新带来的复用**。
   基线臂（reuse 关）本来就已经有 36 次命中/把（10 次直接 code 读 + 26 次 storage ——
   这两类在 M8.2 HEAD 就已经复用了），所以 reuse 臂的绝对命中是 77 = **41（这一刀新增）
   + 36（本来就有）**。把两臂相减看增量：code 27−10 = **17**、balance 12−0 = **12**、
   nonce 12−0 = **12**、storage 26−26 = **0**、合计 77−36 = **41**——
   **§12 那一列逐格对上**。
3. **storage 20/26 vs 20/0**：任务书示例假设 storage 此前没有复用，实际 HEAD 已经有，
   所以它 26 次命中、这一刀对它**没有新增**（removed = 0，见 §2 的方法表）。

`cache_hits` / `cache_misses` 的**跨臂差**恰好等于 §7 的 41 次消失的重复，
这条由 `only_the_account_kinds_move_between_the_two_arms` 断言：
`removed == baseline.duplicate_reads`，且 header 与 storage 两列在两臂之间**一格没动**。

## 9. §16 那个隐藏问题：是不是所有 state read 都过了同一个边界？

任务书担心的是「某一部分 cached、某一部分 uncached，然后误以为优化完成」。两条证明，一条算术、
一条代码。

**算术**：reuse 臂里四类全部 `misses_equal_wire == true`（§8 的表）——
边界没答上来的读**全部**变成了请求（miss = wire），到达节点的请求**全部**是边界被问过的
（wire = miss）。任何一条绕过边界的 simulation 状态读都会让这个等式破掉，而且是被一个

破掉，不是被一次审计「看过」破掉。

**代码**：四个方法在 simulation 侧的唯一出口就是 §1.1 那四行。明确**在这个边界之外**、

## 11. Q8 — 是否存在新的 correctness risk？

诚实列四条，前三条已被测试压住，第四条是本里程碑自己的边界：

1. **缓存陈旧**（同场模拟内块被推进 → 拿到旧状态）。压住：key 带链+块+地址(+slot)，
   且 key 只可能由 `self.pin.number` 构造；`reuse_reads_at_the_pin_and_never_at_a_later_height`
   + `a_read_at_one_block_is_not_the_read_at_the_next` 双双钉死。M8.2 之前「同一场模拟反复读
   同一个 slot」本来就已经在复用，这次只是把三种账户状态读也纳入同一规则。
2. **失败被缓存**（timeout 变成一份「答案」，后续步骤被它答掉）。压住：`?` 早退在 `put_*` 之前；
   `a_failed_read_leaves_nothing_to_reuse`。
3. **跨场泄漏**（下一场模拟吃到上一场的答案，尤其是不同块之间）。压住：cache 是 per-simulation
   provider 的字段（`arbitrage.rs:393`），drop 随 provider；
   `two_simulations_never_share_a_read` + `a_second_simulation_over_the_same_endpoint_pays_for_its_own_reads`。
4. **本里程碑证的边界**：live 两臂不共享 pinned block，所以「结果相同」这条**只在固定块那一组证**；
   live 那一组证的是计数、重复归零、时间与账目自洽。想同时要「真实链 + 同块两臂」需要能冻住
   head 的状态源，那是节点能力问题，不是这把开关的问题——记在这里，不粉饰成已证。

另有一处**测量侧的注意**：`rpc_wall / simulation span = 999 ‰` 是两臂共同的形状，
它说明节省来自等待；但如果哪天本地计算占比变大，这个比值就不再是免费的旁证，需要另立指标。
