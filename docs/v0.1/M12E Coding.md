# M12-E Coding Agent Task — 交易提交结果不确定性与重试安全

## 1. 任务目标

在不部署 GIWA 节点、不连接真实 RPC、不使用真实资金的前提下，修复交易发送路径中的自动重试风险，并建立可验证的交易提交结果分类与本地交易哈希追踪。

核心原则：

> **一次交易提交请求没有得到明确结果，不等于交易没有提交成功。**

M12-D 已确认 `crates/chain/src/rpc.rs` 中的通用 HTTP 请求循环会对部分失败重试，而 `eth_sendRawTransaction` 通过同一通用请求路径发送。该问题必须在第一次真实广播前解决。

本轮只解决交易提交安全，不建设持久化执行台账，不重写 M10/M11，不部署节点。

## 3. E1 — 分离读取重试与交易发送策略

### 3.1 普通读取

保留普通只读 RPC 当前的重试行为，除非审计证明该行为本身存在独立缺陷。

本轮不得因为修复发送安全而无意改变所有读取请求的延迟、请求次数、超时或错误语义。

### 3.2 交易提交

`eth_sendRawTransaction` 必须使用独立、显式的发送策略。

最低要求：

* 每次 `submit()` 调用最多发送一次 HTTP POST。
* 不得因传输失败、超时、非 JSON 响应或非 2xx HTTP 状态而在同一次调用内自动重发。
* 不得把通用读取的重试循环直接复用于交易提交。
* 不得为了绕开重试问题而重写整套 M10 Submitter 或执行状态机。
* RPC trace 必须能够反映真实发生的请求次数，不能将两次 HTTP 尝试伪装成一次。

优先使用最小改动，在 RPC 层提供显式的一次性请求路径或等价的策略参数，让调用者能清楚地区分只读请求与交易提交。

不要只通过字符串匹配 `eth_sendRawTransaction` 来决定是否重试；策略应通过明确的调用接口表达。

### 3.3 必须保持的回归行为

* 普通读取的既有测试仍然通过。
* 明确的 JSON-RPC 错误仍可与传输层错误区分。
* RPC trace 中的 attempt 数量、失败分类和调用次数保持真实。
* 不增加逐候选、逐交易额外 RPC 探测。
* 不改变 M9–M11 的策略选择和机会评估语义。

## 4. E2 — 明确提交结果的分类

以现有 `SubmissionOutcome` 和生命周期为基础，建立可审计的提交结果分类。

至少区分以下情形：

| 情形                    | 必须遵守的处理原则                     |
| --------------------- | ----------------------------- |
| 收到格式正确且与本地哈希一致的交易哈希   | 可以记录为提交端点接受请求；不等于交易已上链        |
| 收到与本地哈希不一致的哈希         | 不得当作正常成功；进入不确定状态并保留本地预期哈希     |
| 连接失败或超时               | 结果不确定，不自动重发                   |
| 收到非 JSON 响应           | 结果不确定，不自动重发                   |
| 收到非 2xx HTTP 响应       | 默认不能证明请求未被接受；不自动重发            |
| 收到无法明确解释的 JSON-RPC 错误 | 保守处理，不得仅凭存在 `error` 字段就释放执行状态 |
| 收到明确、可证明的交易拒绝         | 可记录为拒绝，但必须依据可验证的错误语义          |

特别注意：

* `already known`、`known transaction` 等可能表示交易已经在节点的交易池中。
* `nonce too low` 可能表示相同交易已被接收，也可能存在另一笔交易占用了该 Nonce。
* `replacement transaction underpriced` 不能证明原交易未被接受。
* 不得把这些情况简单归类为“肯定未发送成功”。

不得凭空构造 GIWA 专属错误码或错误语义。如果现有响应无法可靠区分明确拒绝与结果不确定，应采用保守分类，并在报告中列出未能确认的错误语义。

## 5. E3 — 本地交易哈希与追踪状态

在请求发出前，确定本次签名交易的本地哈希，并确保提交结果与这份哈希绑定。

必须核实并实现：

1. 本地预期哈希来自当前签名交易对象，而不是来自 RPC 返回值。
2. 请求发送前即可获得本地预期哈希。
3. 无响应时，调用者仍然可以知道本次可能已提交的交易哈希。
4. RPC 返回的哈希必须与本地预期哈希比较。
5. 哈希不匹配时不得继续走正常 Accepted 成功路径。
6. `Unknown` 状态必须保留足够信息，让现有生命周期继续保留 Nonce lane 和追踪状态。
7. 日志和证据记录能够区分本地预期哈希、节点返回哈希、提交结果与后续回执状态。

优先复用现有交易对象和生命周期数据结构。是否需要调整 `SubmissionOutcome` 字段，应根据实际消费者确定，避免大范围修改所有调用者。

### 状态语义必须严格区分

* `Accepted`：端点返回了与本地交易一致的接受结果。
* `Rejected`：有足够证据证明该请求被明确拒绝。
* `Unknown`：请求是否被接收无法确定。

无论何种情况下，`Accepted` 都不等于 `Mined`、`Confirmed` 或 `Realized Profit`。

如果哈希不匹配、响应不完整或错误语义不明，必须避免将状态推进到需要明确提交成功作为前提的下一阶段。

## 6. E4 — 不确定结果的安全处理

本轮采用保守策略：

**对提交结果不确定的请求，不自动重发。**

收到 `Unknown` 后：

* 保留该交易的本地哈希。
* 保留现有 Nonce lane 和执行追踪状态。
* 不把该交易当成失败交易立即释放 Nonce。
* 不因为一次 `eth_getTransactionReceipt` 返回 `null` 就断言交易从未被接受。
* 不因为一次 `eth_getTransactionByHash` 查不到交易就断言可以安全地构造另一笔交易。
* 不自动递增 Nonce 来绕过未知状态。
* 不自动生成新的签名交易来替代原交易。
* 允许现有回执追踪和已有生命周期机制继续核实链上状态。

如果当前生命周期无法安全地保持 `Unknown`，只允许在现有 M10/M11 架构内进行必要的最小修复，不得新建第二套交易执行状态机。

本轮不实现自动重发与复杂 reconciliation 服务。若未来需要在不确定状态下重发，必须另立任务，单独证明重发条件、交易哈希一致性、Nonce 所有权和端点行为。

## 7. E5 — 故障注入与负向测试

使用本地 HTTP 桩服务、现有测试框架和确定性测试。不得访问真实 GIWA、Flashblocks 或 Ethereum L1。

至少新增或完善以下测试：

### A. HTTP 请求次数

1. 发送请求收到有效且匹配的哈希：只收到一次 POST。
2. 服务端读取完整请求并记录后关闭连接：只收到一次 POST，返回 `Unknown`。
3. 服务端收到请求后延迟响应，客户端超时：只收到一次 POST，返回 `Unknown`。
4. 服务端返回非 JSON：只收到一次 POST，返回 `Unknown`。
5. 服务端返回 HTTP 502：只收到一次 POST，返回 `Unknown`。
6. 服务端返回明确 JSON-RPC 错误：只收到一次 POST，结果按经过审查的错误分类处理。
7. 服务端返回不匹配的交易哈希：只收到一次 POST，进入不确定状态。

测试必须记录桩服务实际收到的请求次数，不能只断言客户端函数被调用一次。

### B. “已接收但响应丢失”控制

必须构造以下负向场景：

1. 桩服务完整读取并记录原始交易字节。
2. 桩服务模拟接受交易。
3. 响应被关闭或丢弃。
4. 客户端得到不确定结果。
5. 断言同一次提交调用没有第二次 POST。
6. 断言本地预期哈希被保留。
7. 断言 Nonce lane 不会因为该响应丢失而立即释放。

这条测试是本里程碑的核心验收用例。

### C. JSON-RPC 错误语义

至少覆盖：

* 明确拒绝。
* `already known` 或等价的已知交易错误。
* `nonce too low`。
* `replacement transaction underpriced`。
* 未知错误码或无法解释的错误消息。

只有在现有实现及可引用的接口语义足以证明某错误意味着明确拒绝时，才能把它分类为 `Rejected`。其他情况采用保守策略。

### D. 生命周期回归

验证：

* `Unknown` 不释放 Nonce lane。
* 哈希不匹配不进入正常 Accepted 路径。
* `Accepted` 不被误当成已确认。
* 后续回执能够继续使用本地预期哈希追踪。
* 读取侧 RPC 重试策略未被意外改变。
* 现有 M10 Executor、Signer、ReceiptTracker 和 M11 Multi-Lane 测试保持通过。

不得以测试桩“模拟了交易进入区块”为理由声称真实链上行为已验证。

## 8. 范围外事项

本轮禁止：

* 部署 GIWA 节点。
* 启动节点或同步链上数据。
* 连接真实 RPC、Flashblocks 或 L1。
* 使用真实私钥或真实资金。
* 签名并广播真实交易。
* 实现多端点路由、自动故障转移、HA 或多节点。
* 实现自动重发策略。
* 实现完整的持久化执行台账。
* 重写 M10 Executor、Signer、ReceiptTracker。
* 重写 M11 Multi-Lane。
* 接入 M9.4 Radar 的生产执行路径。
* 扩大到策略、PathFinder 或套利算法改造。

M12-D §13.2 的进程重启后执行台账持久化缺口仍然保留，记录为独立后续里程碑。不得将本轮的本地哈希追踪误称为跨进程持久化。

## 9. 安全审计与代码质量

除功能测试外，必须检查：

* 所有 `eth_sendRawTransaction` 生产调用点。
* 是否存在绕开一次性提交路径的旁路。
* 是否仍有提交路径复用通用重试循环。
* 是否有 `Unknown` 被转换为 `Rejected`、`Accepted` 或空机会结果的路径。
* 是否存在哈希不匹配仍释放 Nonce lane 的路径。
* 错误消息和 trace 是否泄露端点 URL、API Key、JWT 或其他敏感内容。
* RPC trace 的 attempt 数与真实 HTTP 请求次数是否一致。
* 新增代码是否引入额外 RPC 调用。
* 是否有测试或构建过程意外修改 `data/evidence/m10/manifest.json` 或其他历史证据。

如果发现其他问题，记录证据及建议后续任务，不要顺手扩大范围。

## 10. 串行验证门禁

按顺序执行，不得并行运行 Cargo 门禁：

1. `cargo fmt --all -- --check`
2. `cargo clippy --workspace --all-targets -- -D warnings`
3. `cargo test --workspace --no-fail-fast -- --test-threads=1`

必须解析完整日志，不得只看退出码。

报告：

* 命令与实际退出码。
* 每条命令的实际耗时。
* 测试目标总数。
* `passed`、`failed`、`ignored` 分别是多少。
* 是否存在警告、超时或未执行目标。
* 新增负向测试各自的实际执行结果。
* 生产代码 diff 与发送路径的调用次数审计。
* M10/M11 回归结果。

`ignored` 不得计入 `passed`。

如果测试会重印历史 M10 manifest，必须按仓库既有惯例核对并恢复无关历史证据，不得把测试副作用混入本轮功能改动。

## 12. 完成标准

只有同时满足以下条件，才能将 M12-E 标记为完成：

* `eth_sendRawTransaction` 不再经过自动重试的通用读取路径。
* 一次提交调用最多发出一次 HTTP POST。
* 读取侧原有重试行为保持通过回归测试。
* 本地交易哈希在提交前确定，并在 `Unknown` 情况下可追踪。
* 哈希不匹配不能作为正常成功处理。
* 无响应、非 JSON、HTTP 错误和不确定 JSON-RPC 错误不会触发自动重发。
* `Unknown` 不会被误当作明确拒绝，也不会随意释放 Nonce lane。
* “服务端已接收但响应丢失”的负向测试通过。
* M10/M11 回归与全部串行门禁通过。
* 历史证据没有被无关修改。
* 完成报告和 manifest 的统计相互一致。

完成后停止，等待审查。不得自行部署节点、发起真实交易或进入真实环境验证。
