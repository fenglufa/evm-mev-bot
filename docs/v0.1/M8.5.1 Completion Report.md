## 白话结论（先看这一屏）

**结论：不能信，而且省不出 RPC。** 判定 = `REUSE_BLOCKED`，净省 RPC = **0**，`safe_to_reuse_now = false`。

三句话说清为什么：

1. **Preflight 要的那一次读数，就是「头块这一次」。** 它的职责是当第二双眼睛：代码里头部读数缺失时是直接拒绝（`crates/execution/src/preflight.rs:194`），不会退回用发现阶段的数字。把上游的副本递进去，闸门就变成拿一个数字跟自己复制品比——检查消失了，但 RPC 一次也没少。
2. **「块」这个字段实测会改答案。** 同一个 `to`、同一份 `getReserves()` 数据、两个高度：相隔 170147 块的两把对照，2 口池两个字段**都变了**。所以「去掉块再复用」不是简化，是把不同的问题当成同一个问题。
3. **本轮记录里 60 次 `eth_call` 的带块语义身份 60 个全不一样**，也就是说：即便十个资格要素全部证明完毕，这 3 把 run 里也没有一次「重复提问」可以省。省不出来的东西，不是还没找到，是算术上不存在。

「省不出」≠「还没找到」：省不掉的那一次就是检查本身，删它等于删闸门。这与 M8.4.4 的结论同类（那一轮是 `SAFE_PROPAGATION_PROVEN_NO_NET_RPC_SAVING`），区别在于本轮连「资格证明」都没通过——所以标签是 `REUSE_BLOCKED` 而不是 `SAFE_*`。

**本轮新增 RPC = 0，真实运行次数 = 0**（§46 允许 ≤3 次 BuildOnly，一次都没用）：所有数字都从 M8.4.2 已提交的记录重算。签名 0、广播 0、真实套利 0。

## 1. Objective（§1–§5、§68）

任务书把本阶段定义成**诊断**，不是优化：先回答「这个 `eth_call` result 究竟是什么、谁有资格相信它」，再谈能不能跨阶段交给别人用（§68 原文反对一上来就问「能不能缓存」）。

因此本阶段的交付物是**资格结论 + 支撑它的表**，不是任何行为改动。§56 的绝对禁令逐条生效：不加缓存、不改生产 RPC 行为、不减 `eth_call`、不删 Preflight 的第二次读、不动机会算法/仿真/风控/建单/执行/签名/广播/真实套利。§31/§32 禁止「为了确认 eth_call 再打一次 eth_call」，所以本轮只观察已有流量。§58 规定成功 = 把资格证明清楚，`SAFE_CANDIDATE_FOUND / REUSE_BLOCKED / NOT_ENOUGH_EVIDENCE` 三个答案都算完成。

生产代码的实际改动面（`git diff --stat` 实测）：被跟踪文件只有 `crates/pipeline/src/lib.rs` **+1 行**（`pub mod eth_call_semantics;`）。新增文件 = 1 个诊断模块 + 2 个门禁测试 + 证据目录。

## 5. eth_call semantic identity（§8/§51：`EthCallIdentity` 与 `EthCallArtifact` 分开建模）

发布的身份词表是 4 项：`["chain_id", "block", "to", "calldata"]`（来自 `normalized-identities.json.identity_terms`），理由记在同一张表的 `why_these_four`：**只有这 4 项能改变 EVM 实际执行什么**。

同一件事有三种拼法，本轮把对应关系写死在表里而不是靠读者猜：

```text
发布形态（带块）  eth_call|chain=91342|block=37700740|to=0x2a3c…|data=0dfe1681
发布形态（去块）  eth_call|chain=91342|to=0x2a3c…|data=0dfe1681
候选记录自己的    call|91342|37700740|0x2a3c…|0dfe1681
记录内字段        method=eth_call|chain=91342|data=0dfe1681|to=0x2a3c…
```

`chain_id`↔`chain`、`calldata`↔`data` 是重命名，门禁 `the_identity_strings_are_the_records_own_dedup_keys` 要求翻译表两侧同时成立，防止「我改个字段名就算证明了身份」。

身份项**不能**被删掉的理由是实测的，不是论证的（`negative-controls.json.key_control.identity_collapse_counterfactuals`，60 次请求）：

| 去掉哪一项 | 独立身份数从 60 变成 | 后果（同一张表的原文） |
| --- | --- | --- |
| 全保留 | 60 | — |
| `block` | 26 | 18 个实测对被并成 6 组，正是 §41 要防的错 |
| `to` | 39 | 两口候选池互相顶替 |
| `calldata` | 21 | `token0()` 与 `getReserves()` 共享答案 |
| `chain_id` | 60 | **本语料照不出**：60 次全在 1 个链值上 |

诚实记录：`chain_id` 这一项在现存语料里没有任何对照能证明它起作用，表里明写「这项是模型声明保留的，本语料不提供能抓到它缺失的对照」。这是本轮唯一一处「保留但未被实测支撑」的身份项。

## 6. Block semantics

- 形态：60 次**全部**是 `number`（`block_forms = {"number": 60}`），带 tag 的行 **0** 行（`rows_with_a_tag_block_term = 0`）。所以本语料里不存在「latest」这种由节点解析的写法；形态判定沿用 M8.4.2 的 `RpcReadKey::block_form`，不新造规则（`block_term.form_rule`）。
- 高度分布：37700740 ×6、37700753 ×14、37700778 ×6、37700793 ×14、37700806 ×6、37700821 ×14（合计 60），即 3 把 run，每把「发现块 + 头部块」两个高度。
- 块的哈希来源：`hash_provenance_rule` 明写「记录只报高度，除非钉住它的那次读取同时返回了哈希」，本语料常见取值是 `not_in_the_record`——写出来而不是留空。
- 去块之后的分组：26 个「同目标」组里 **8** 组跨多个高度。这 8 组就是「去掉块会误并」的实测范围。

## 7. Request semantics（§7 禁止假定，§36 禁止写成 null）

`call-surface.json.request_parameters` 对 `from / value / state_override / gas` 四条各给：状态、规则、被省略时节点会用的默认值、以及这条判断覆盖多少请求。

| 字段 | 状态 | 覆盖 | 规则（表内原文要点） | 未发送时的默认值 |
| --- | --- | --- | --- | --- |
| `from` | `proven_absent` | 60/60 | `CallRequest` 只有 `to`/`data` 两字段，任何调用方都无法指名发送者；params 对象只写两个键 | 节点自己的默认发送者，**记录未捕获它是什么** |
| `value` | `proven_absent` | 60/60 | 同上，且请求类型没有承载它的字段 | `0` |
| `state_override` | `proven_absent` | 60/60 | 本 build 发出的 params 数组恰好两个元素（调用对象 + 块项），没有第三项放 override | `[]` |
| `gas` | `proven_absent` | 60/60 | 请求类型无该字段 | 节点默认 |

四条 `settled` 全为 `true`。锚点：`crates/chain/src/types.rs:155`、`crates/chain/src/rpc.rs:726`（`"data": request.data.to_string()`）。

注意 `from` 的措辞：证明的是「本 build 发不出这个字段」，不是「节点没有默认」。默认值是什么**未被记录**，这一点写在规则里，没有粉饰成已调查。

## 8. Result semantics（§51 的 `EthCallArtifact`）

结果在记录里**以解码后的字段存在**，原始返回字节从未落盘。每站的 `result_type`（实测）：

| 调用点 | result_type | ownership_form |
| --- | --- | --- |
| `detection.tokens` | `alloy Bytes, decoded to Address` | `projection_only` |
| `detection.reserves` | `PoolState { token0, token1, reserve0, reserve1, last_synced, read_at_block, source }` | `projection_only` |

| `build.asset_snapshot` | `AssetReading { amount, source }` | `held_by_struct_field` |

因此 3 个调用点带 `RESULT_NOT_RECORDED` 阻碍（`detection.tokens`、`detection.reserves`、`preflight.tokens`）：**跨阶段能交接的不是「那次答案」而是「那次答案被投影后的少数字段」**。`detection.reserves` 的字段有明确写入点：`crates/pipeline/src/arbitrage.rs:266`（`"getReserves_blockTimestampLast": self.last_synced.to_string()`）——语料里每一把 run 都经过这行，所以锚点指的是代码而不是某一把的目录。

§42 的红线在本表落地成一条门禁（`the_measured_pairs_are_the_candidate_record_s_own_eth_call_rows`）：所有相等比较都在**同种已记录答案**之间做（`reserve0`/`reserve1` 对 `reserve0`/`reserve1`），一次都没从「建单结果相同」反推「`eth_call` 结果相同」。表里对应的原文字段是 `dependency-matrix.json.what_this_table_refuses_to_infer`。

## 11. Freshness

状态：`proven` = `preflight.reserves`、`build.asset_snapshot`；`partially_proven` = `preflight.l1_fee`；`not_applicable` = `preflight.tokens`；`unknown` = `detection.tokens`、`detection.reserves`。

两格 `proven` 的依据不是「有一个 TTL 常量」，而是**消费方自己声明了它要哪一块**：`preflight.reserves` 的 `purpose` 写「在同一路线上用头部储重量新定价，不再达标就拒绝」，锚点 `crates/execution/src/giwa/preflight_facts.rs:223`（`head at latest`，这次读取钉住的头部）+ `crates/execution/src/preflight.rs:194`（头部读数缺失就拒绝）。等价于一条**零窗口**规则：有效范围恰好是那个高度。`build.asset_snapshot` 同理，快照与 after-snapshot 成对（`profit.rs:48`）。

`unknown` 两格是发现阶段：代码里没有任何地方声明这次读能新鲜多久，也没有显式的「无窗口」规则——本轮把它写成 unknown，而不是替它编一条规则。

本轮**没有**证明的：跨阶段交接时消费方能不能**验**这条零窗口规则。`preflight.reserves` 的 `consumer_verification` 被降级为 partial 正是这件事——它能验「是不是头部」，但唯一的验法是再读一次。

## 12. Invalidation

6 格里 0 个 `proven`：`not_applicable` 2（`preflight.reserves`、`build.asset_snapshot`——生命周期短到没有可失效的窗口，见 §10 的 `absent_step_rule`），`unknown` 4。

对应阻碍名 `INVALIDATION_NOT_ESTABLISHED` 出现在 `detection.tokens`、`detection.reserves`、`preflight.tokens`、`preflight.l1_fee` 四站。本仓库确实存在的两套过期机制都**不适用**于这条流：M5 的 STALE 管的是候选（opportunity）生命周期，M8.3.1 的复用边界明写是「一次仿真自己的」，两者都不是跨阶段的读结果登记表。本轮没有新增任何失效通道（§56 禁止，且 §30 禁止在生产加缓存）。

诚实边界：本轮**只**证明了「代码里没有针对 `eth_call` 答案的失效机制」，没有证明「不需要失效机制」。前者是可查的事实（锚点在 `read_is_the_check` 与生命周期 `invalidated` 列），后者是设计主张，留给 §23。

## 13. Authority

6/6 `proven`。判定内容：在**具名高度**上，该端点的答案就是这一高度的规范状态；每份记录都带端点指纹（M8.3.2 起就有的 `endpoint_id` 口径，本轮未改）。锚点在 `call-surface.json.rpc_boundary`：`crates/chain/src/rpc.rs:725` 的 `"eth_call",` 分支是唯一起点。

这条是八个轴里唯一全绿的轴，因此也是本轮结论的关键：**权威从来不是问题**。问题一直在于「交接的这次读数是不是消费方要的那一次」——即 §11/§19。本轮没有、也无权证明：同一高度在另一个端点上会给同样的答案（语料里只有这一个端点指纹，没有跨端点对照）。

## 20. Why no optimization was performed

三层，缺一不可：

1. **规则层**：§31/§32 禁止本轮做任何优化或为了确认而多发请求；§56 逐条禁止缓存/减 `eth_call`/删 Preflight 第二次读/改机会、仿真、风控、建单、执行、签名、广播。

3. **算术层**：带块身份 0 重复（§19），本轮语料不存在可复用的第二次同问。

所以 `net_rpc_saving = 0` 不是「还没做」，是三条独立理由各自的结论。生产 RPC 行为本轮**零改动**（§1 的 diff：只 +1 行模块声明）。
