# M8.4.4 Coding Task

## Verified Block Context Propagation & Controlled Reuse Experiment

## 0. 任务定位

这是 M8.4 Hardening 的下一阶段：

> **M8.4.4 — Verified Block Context Propagation & Controlled Reuse Experiment**

本阶段不是泛化缓存，不是继续做 RPC 优化，也不是直接修改生产默认并发策略。

唯一目标：

> 验证一个由上游阶段获得、经过明确身份验证的 `block_number + block_hash`，是否可以安全地从 `Preflight` 传播到 `Build`，并让 `Build` 在保留必要 consumer-side verification 的前提下，安全复用这个已经验证过的 block context。

M8.4.3 已经证明：

* `block_header` 是目前 11 类状态中唯一同时满足：

  * ownership proven
  * identity 明确
  * semantic equivalent = true
  * reusable in principle = true
* `PreflightReport` 是目前唯一明确存在的 `Preflight → Build` 跨阶段边界载体；
* 当前 `PreflightReport` 没有 block identity；
* 不能共享裸 block height；
* 不能共享 tag；
* 必须同时携带 `block_number + block_hash`；
* consumer 侧必须继续验证 hash；
* 本阶段之前没有任何 `safe_to_reuse_now` 的跨 stage 复用项。

因此：

**M8.4.4 的第一优先级不是“省掉一次 RPC”，而是证明这个跨阶段契约是否成立。**

# 3. 核心问题

需要回答下面 8 个问题。

### Q1

谁产生 verified block context？

### Q2

谁拥有它？

### Q3

它的生命周期是什么？

### Q4

它的身份是什么？

必须明确：

```text
chain_id
block_number
block_hash
```

其中：

```text
block_number alone != identity
block_hash alone != sufficient cross-chain identity
chain_id + block_number + block_hash = canonical identity
```

如果现有项目已经有更严格的 canonical identity 定义，遵循现有定义。

---

### Q5

Preflight 如何证明这个 block context 是真的？

必须来自真实 chain authority。

不能：

```text
自己填 block_number
自己计算 hash
从 GraphSnapshot 猜
从 StateStore 猜
从 opportunity 猜
从 simulation 猜
```

---

### Q6

Build 如何验证这个 block context？

必须：

> **consumer independently verifies the block hash**

不能只相信 producer。

也就是说：

```text
Preflight
  ↓
verified context
  ↓
Build
  ↓
verify chain_id
verify block_number
verify block_hash
  ↓
only then consider reuse
```

如果 consumer 无法验证：

```text
拒绝 reuse
```

不能 fallback 成：

```text
“这个值看起来一样，所以继续”
```

---

### Q7

block context 什么时候失效？

至少必须明确：

```text
same block number + same hash
    => same canonical block identity

same block number + different hash
    => invalid

different block number
    => invalid

different chain
    => invalid
```

如果项目当前已经有更严格的 freshness / canonicality 规则，必须复用现有规则。

---

### Q8

如果安全成立，究竟省掉什么？

必须精确回答：

```text
saved RPC
saved stage
retained verification
```

不能只报告：

> RPC 减少。

必须报告：

```text
Baseline:
    producer RPC
    consumer RPC
    verification

Reuse:
    producer RPC
    consumer verification
    saved consumer RPC
```

# 5. Producer-side contract

Preflight producer 必须完成：

```text
1. obtain block header
2. obtain number
3. obtain hash
4. verify header identity
5. create verified context
6. attach it to PreflightReport
```

注意：

这里的“verified”必须有代码证据。

不能仅仅：

```rust
VerifiedBlockContext { ... }
```

然后结构体名字叫 Verified。

必须存在真实 validation。

---

# 6. Consumer-side contract

Build consumer 收到：

```text
PreflightReport
    ↓
VerifiedBlockContext
```

之后必须进行独立检查。

至少检查：

```text
chain_id == expected_chain_id
block_number == expected_block_number
block_hash == canonical hash for block_number
```

如果 Build 已经持有同一个 canonical header source：

```text
reuse verified context
+
verify canonical identity
```

如果没有：

```text
perform verification RPC
```

**不要为了省 RPC 而删除 verification。**

---

# 7. Negative controls

必须实现至少以下 negative controls。

## NC1：same height / different hash

例如：

```text
producer:
    number = N
    hash = H1

consumer:
    number = N
    hash = H2
```

必须：

```text
REJECT
```

---

## NC2：different height / same hash

必须：

```text
REJECT
```

---

## NC3：different chain

必须：

```text
REJECT
```

---

## NC4：missing hash

如果类型系统允许构造：

```text
number = N
hash = None
```

必须：

```text
REJECT
```

更理想的是：

> 类型系统直接不允许构造未验证的 `VerifiedBlockContext`。

---

## NC5：tampered context

构造 producer 输出后修改：

```text
block_number
```

或：

```text
block_hash
```

consumer 必须拒绝。

---

## NC6：stale context

producer：

```text
block N
```

consumer：

```text
head already N+1
```

需要根据项目已有 freshness semantics 判断。

不能自行规定“永远允许”。

必须明确：

```text
是否允许 build 使用旧 block context？
```

如果当前 Build 的安全语义要求 latest/current，则必须拒绝。

如果当前语义允许固定历史块，则必须明确这是：

```text
fixed-block context
```

不能混成 live-head context。

# 8. 最重要的语义区分

必须明确区分：

### Fixed historical block

例如：

```text
block = 37600021
```

用于：

```text
simulation
replay
fixed-block experiment
```

这种情况下：

```text
number + hash
```

可以作为确定性的 block identity。

---

### Live preflight block

这是：

```text
Preflight 在某个时间观察到的 block
```

它可能在 Build 前变旧。

因此：

```text
verified != fresh forever
```

必须同时区分：

```text
identity correctness
```

和：

```text
freshness correctness
```

M8.4.4 不能因为 identity verified 就宣称 live reuse 永远安全。

# 13. 重要：不要只比较最终 Build 结果

必须同时证明：

```text
same input identity
+
same block identity
+
same Build result
```

因为：

> “最终 transaction 一样”

不能证明：

> “中间状态可以安全复用”。

这正是 M8.4.3 对 Simulation → Build 所强调的边界。

---

# 14. No-extra-RPC gate

必须有专门测试保证：

Baseline 和 reuse arm 的差异：

```text
只能来自明确设计的 header reuse
```

不能出现：

```text
额外 RPC
额外 block lookup
额外 state read
额外 simulation
```

尤其需要证明：

```text
reuse arm 没有因为 verification 而偷偷增加额外 RPC
```

或者如果增加了 verification RPC：

必须诚实报告：

```text
saved RPC = 1
verification RPC = 1
net saved RPC = 0
```

这种情况下：

> **M8.4.4 不能宣布 RPC 优化成功。**

但可以宣布：

> verified context propagation contract 成立。

---

# 15. 成功条件不是“必须省 RPC”

M8.4.4 有三种合法结论。

## Result A — Safe reuse + RPC saved

最理想：

```text
producer verifies
consumer verifies
same canonical identity
same Build result
negative controls reject
RPC count decreases
```

可以：

```text
M8.4.4 PASS
```

并记录：

```text
header RPC saved = N
```

---

## Result B — Safe propagation，但 net RPC = 0

例如：

```text
producer verification
+
consumer verification
```

最终：

```text
RPC count unchanged
```

仍然可以完成：

> Verified Block Context contract proven.

但不能宣称：

> RPC optimization achieved.

---

## Result C — Contract cannot safely propagate

例如发现：

```text
consumer 无法独立验证
```

或者：

```text
freshness semantics 不成立
```

或者：

```text
PreflightReport 生命周期不足
```

则必须：

```text
REJECT REUSE
```

并记录：

> M8.4.4 safe reuse denied.

这仍然是有效结果。

**禁止为了让 M8.4.4 “成功”而降低 safety bar。**

# 21. Live freshness experiment

如果代码结构允许，可以额外做一个非常小的 controlled freshness test。

目的不是优化。

只是回答：

> Preflight 获得的 verified context 到 Build 时，什么时候必须重新验证 / 拒绝？

至少构造：

```text

Preflight block N
Build block N

Case B:

```

**不能自行规定答案。**


# 22. 不允许修改 M8.3.3

M8.3.3 已经验证：

```text

C2
C4
```

存在 bounded parallelism 的性能收益。

但 M8.4.4 不研究并发。

因此：

```text

```

保持不变。

任何为了让实验跑得更快而修改 concurrency 的行为：

**禁止。**

# 23. 不允许修改 StateReadCache

M8.3.1 已经证明：

```text
80 → 39 RPC
```

是 simulation-local state read reuse。

M8.4.4 完全不碰这个机制。

必须确保：

```text
M8.4.4 的 RPC reduction
```

不能混入：

```text
StateReadCache hit
```

否则无法知道到底是谁节省了 RPC。

---

# 24. 不允许把 GraphSnapshot 变成 BlockContext authority

必须保持：

```text
GraphSnapshot
    !=
REVM canonical state
```

GraphSnapshot 可以提供：

```text
opportunity
pool topology
reserve projection
applied height
```

但不能成为：

```text
block hash authority
```

除非现有代码已经明确规定它是 canonical header authority。

---

# 25. 不允许共享裸 block number

任何 API：

```rust
block_number: u64
```

如果意图是跨 stage 表示 canonical block identity，都必须审查。

跨 stage identity 必须至少：

```text
number + hash
```

并带：

```text
chain identity
```

不能出现：

```text
VerifiedBlockContext {
    block_number
}
```

然后另外一个地方偷偷拿 hash。

# 26. 类型安全优先

如果可行：

```text
VerifiedBlockContext
```

应该只能通过类似：

```text
VerifiedBlockContext::from_verified_header(...)
```

构造。

避免：

```rust
VerifiedBlockContext {
    ...
}
```

在业务代码里随意构造。

如果因为 Rust visibility / fixture / test 需要开放构造，也必须：

```text
production construction path
```

明确存在，并且测试可以构造 negative fixtures。

---

# 27. 必须记录 provenance

Verified context 最好能够回答：

```text
who produced it?

which block?
when verified?
```

至少需要：

```text
chain_id
block_number
block_hash
```

以及能追溯：

```text

```

如果时间字段只是诊断信息，不要把时间戳当 canonical identity。

# 28. 时间语义

必须区分：

```text

```

与：

```text
block identity
```

`verified_at`：

* 不能成为 block identity；
* 不能替代 block hash；
* 不能证明 freshness；
* 只能辅助诊断。

---

# 29. Error semantics

所有 verification failure 必须有明确错误。

例如：

```text
ChainMismatch
BlockNumberMismatch
BlockHashMismatch
MissingBlockHash
StaleBlockContext
UnverifiableBlockContext
```

具体名字按项目现有 error style。

禁止：

```rust
unwrap()
expect()
panic!()
```

在新增 production path。

---

# 30. 不允许 fallback 偷偷绕过 verification

特别注意：

```text
if verified_context_invalid {
    fetch_new_header()
}
```

如果这样做：

必须明确记录：

```text
reuse_attempt = rejected
fallback = performed
```

否则 evidence 会误认为：

```text

```

实际上只是：

```text
fallback fresh read
```

这会污染实验结论。

# 36. 特别注意测试执行方式

此前 M8.4.3 已经真实遇到：

> 并行 `cargo test` 会因为多个测试进程同时操作 `target/pipeline-tests/` scratch directory 而产生假失败。

因此：

**所有 evidence / integration / workspace gate 必须串行执行。**

禁止为了节省时间：

```text
cargo test A &
cargo test B &
cargo test workspace &
```

必须：

```text
一个完成
↓
下一个
```

如果出现失败：

1. 记录真实退出码；
2. 判断是否 scratch contention；
3. 串行重跑；
4. 不能直接覆盖失败记录；
5. 报告中必须保留真实失败原因。

但是 producer 的 block identity 只有 height。

→ **FAIL**

```text

```

但是没有证明两个 arm 使用同一个 canonical block。

→ **FAIL**

---

### 情况 D

```text

```

但删除了 preflight safety check。

→ **FAIL**

---

### 情况 E

```text

```

但是 live semantics 未证明。


# 47. 一句话执行原则

> **先证明“verified block context”这个跨阶段契约成立，再证明 Build 可以安全消费；只有当 producer verification、consumer verification、canonical identity、freshness 和 negative controls 全部成立之后，才允许讨论省掉那一次 RPC。**

M8.4.4 的核心不是：

> “再优化一个 RPC。”

而是：

> **第一次建立一个真正有 owner、有 identity、有 freshness、有 consumer verification 的跨 stage state contract。**
