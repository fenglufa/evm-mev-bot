## 白话版（给不看代码的人）

上游的门卫（Preflight）先看了一眼某个块，把「几号块 + 这一号的块指纹是多少」写在一张条子上，递给后面的下单人（Build）。这一步真正要回答的问题不是「能不能省一次问节点」，而是：**下单人拿到条子以后，会不会就不自己核对了吗？**

答案是不会，而且这不是靠嘴说的：下单人自己也要读一次那个块，读到的结果必须和条子上写的一致，活儿才继续；不一致（比如条子说的是同一号块、但指纹不同）它当场拒绝，并且说清拒的是哪一个字段。三种情况下下单人建出来的交易完全一模一样——一模一样这件事本身，就是「传下来的条子没有改变任何决策，只是让两处对齐了同一个块」的证据。

至于省不省：一点都没省。因为规则要求下单人**保留自己那一次读取**，所以传条子既没多加一次问（新增校验读数 0 次），也没少问一次（0 次）。三臂、三把真实运行、以及和上一个里程碑三把真实运行的逐格对照，都给出同一个数：**0**。

## 2. 【§41.1】本阶段到底验证了什么

一句话：**「共享一个已验证的块身份」这件事本身成立，且不以放弃任何一步自己的核对为代价。**

拆成三件可核对的事：

1. **传递成立**：producer（Preflight）读到的 header 变成一个带三要素的上下文，交到 consumer（Build）手里；consumer 用自己的绑定读数（`expected` = 本步 intent 的块身份，`observed` = 本步真正读到的 header）核对它。固定块 3 把里 3/3 `accepted`，且带上下文的 6 行（accepted 3 + rejected 3）`consumer_read` 全为 `true`；baseline 的 3 行是 `no_context`，该字段为 `null`（`contract/consumer-verification.json`，counts：accepted 3 / rejected 3 / no_context 3，共 9 行）。
2. **不改答案**：三臂建出来的交易逐字段相同——`compared_fields` 十字段（chain_id / tx_type / nonce / to / value / gas_limit / input / access_list / max_fee_per_gas / max_priority_fee_per_gas）`every_field_equal_in_every_run: true`，`sender_expected` 与 `serialization_bytes`（50）相同，`fingerprints_equal_all_runs: true`，fingerprint `0xda922714c890ad91a20f78785b866840e177f6d9f694e63cc5504519926f0aba`。
3. **拒绝得起**：把「同一号、另一个 hash」递过去，3 把全部 `rejected / block_hash_mismatch`，而且它**照样建出同一笔交易**（`the_control_builds_the_same_transaction`）——被拒的是传下来的上下文，不是这一步的路线。

## 3. 【§41.2】为什么选 block_header

M8.4.3 的 §17 收口在 A：它把 11 类状态逐类问了一遍「谁产生、谁拥有、属于哪个生命周期、什么让它失效」，把 M8.4.2 记录的 42 个重复候选按四级判定，**0 条到达 `safe_to_reuse_now`**，42/42 卡在同一处——答案字节与 block hash 没有一起被记录，所以「同一个 key」不等于「同一个值」。那一轮的结论是：只有 `block_header` 一类具备设计受控复用实验的条件，缺的正是一个**同时带 number 与 hash 的载体**。本轮就是去造那个载体，而不是去省 RPC。

## 5. 【§41.4】producer 是谁

`crates/execution/src/preflight.rs` 的执行前闸门：`PreflightFacts` 里那条 pin 住的 header 读取，经 `verify_block_context(facts)` 变成 `ProducerOutcome::{Verified, Refused}`，写进 `PreflightReport.block_context`。`contract/producer-verification.json` 9 行（3 把 × 3 臂）：`verified` 6 / `refused` 3，`refused` 全部来自 baseline 臂——那一臂**没有上下文可传**，所以按 §31 记成 `refused / unverifiable_block_context`，consumer 侧的答案就是 `no_context`（缺席是一个行，不是空值）。

provenance（§27）每行都带：`source`（这条 header 读取是谁问的）、`verified_by`（§5 的 producer 腿）、`scope`。live 三把的 scope 不是 producer 自报的：门禁从「读到的 head 是否还等于 pin」独立推出（`scope_derived_from_head_and_pin`），三把 `head_minus_pin` 实测 17 / 15 / 14，全部 `fixed_historical`，与 CLI 记的一致。

## 6. 【§41.5 / §41.9】consumer 是谁，以及它如何独立验证

consumer 是 `crates/execution/src/sequence.rs` 的 Build 那一步。它做的是**自己的核对**，不是比对 producer 的话：

- `expected` 由本步 intent 的三元组构成；
- `observed` 是**本步自己读到的那个 header**（`BlockBinding::Confirmed/Reorged` 的答案；`Unverified` 时 `observed = None`，直接拒）；
- 传给 `consumer_check` 的 `head_number` 在建单这条腿上是 `None`——这一步不读 head，所以一个 `LiveHead` 语义的上下文在这里**不能**被当作已验证（§21 Case B），只能被 `unverifiable_block_context` 拒掉。这条不是散文：`a_live_head_context_is_refused_at_the_build_boundary_that_reads_no_head` 实测判过，且 §12.2 记下 live 现场 `live_head_scope_contexts: 0`。

所以 §24（`GraphSnapshot` 不当 hash 权威）与 §6（consumer 必须自己验）同时成立：`observed` 来自这一步的绑定读数，producer 的答案只用来对齐、不用来替代。

判到的因由（不含猜测的部分）：被比较的那个叶子 `.per_source[].most_time_by_summed_call_duration.calls` 不是「这一步发了几次」，而是**按时长排名选出来的第一名所对应的次数**——两个臂是两个进程，第一名会随时长换人。就地重读的当前绿 run（`target/simulation-tests/m8.4.2-cross-stage/isolation/*/bottleneck-classification.json`）：baseline 臂第一名是 `eth_getStorageAt` 21 次 / 13 592 414 ns，其下三档都是 6 次（`eth_getCode` 7 448 374 ns、`eth_getBalance` 3 795 291 ns、`eth_getTransactionCount` 2 848 249 ns）；instrumented 臂第一名同为 `eth_getStorageAt` 21 次 / 20 338 126 ns，其下也是三个 6 次。红 run 的两个数（6 与 21）正好是「第一名」与「并列 6 次那一档」的差别。形状比较（每个 key、每层）在两次红 run 里都过了，只有这一个次数不同；而且它**与机器负载同现**（人为加负载能复现，单独重跑 9/9 绿）。

一条要说清的界限：「6 次那一档的合计时长在某次 run 里越过 21 次那一档，于是第一名换人」是**机制推断，不是读数**——红 run 用的 scratch 子树已被后续绿 run 覆盖，那两次究竟选出了哪个方法，本轮就地读不到。作为参照，当前绿 run 里 baseline 臂的两档差距是 13 592 414 ns 对 7 448 374 ns，而单次调用最慢值已到 2 553 750 ns（baseline）/ 4 561 958 ns（instrumented），也就是说这个差距不是数量级上的安全余量。

与本轮的关系：该测试二进制把 `evm-execution` 当 dev-dependency 链进来了（`crates/simulation/Cargo.toml` 第 21 行），但本轮新代码没有在其中执行——三臂所有产物里 grep `block_context` 命中 0 个文件，`cross_stage_experiment.rs` 只从 `evm_execution` 引一个 `ExecutionMode` 枚举。因此本轮把它记为**既有门禁的时长派生选择器在负载下会翻面**，不算本轮引入的回归，也不改动它（§2 的「只记录，不消除」同样适用于门禁的缺陷：留在这里，不动别人的门）。下一格如果要修，方向是把这类「由时长选出的第一名」从逐字节计数比较里摘出去，或按 source/method 取并集对齐而不是按数组下标。
