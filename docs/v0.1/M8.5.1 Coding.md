# 1. 为什么现在研究 eth_call

M8.4.2 已经发现：

```text
Opportunity Detection
        ↓
Preflight
```

存在一组较大的 `eth_call` 跨阶段候选。

但 M8.4.2 同时证明：

```text
same target
+
same calldata
+
different block
```

不能直接视为 duplicate，更不能直接视为 reusable。

M8.4.3 又证明：

> “存在重复读取”与“存在可以安全复用的状态”是两个完全不同的问题。

因此 M8.5.1 必须先回答：

> `eth_call` 的结果究竟是什么？

可能存在三种完全不同的语义：

### A. Canonical state query

```text
eth_call
    ↓
在 block N 的 canonical EVM state 上执行
    ↓
产生确定性结果
```

这种结果可能具有明确：

```text
chain
block
target
calldata
result
```

理论上存在跨阶段复用可能。

---

### B. Derived computation

例如：

```text
eth_call
    ↓
某个协议计算
    ↓
用于 Opportunity Detection
```

结果虽然确定，但它是：

> derived artifact

而不是 canonical state 本身。

这种情况下必须另外证明：

```text
owner
lifecycle
freshness
```

---

### C. Ephemeral probe

例如：

```text
eth_call
    ↓
只是为了快速筛选机会
    ↓
结果立即丢弃
```

这种情况下：

> 即使 target + calldata 完全一致，也不代表它值得跨阶段复用。

---

# 8. 特别检查 from

这是一个非常容易被忽略的问题。

例如：

```text
eth_call {
    from: A,
    to: P,
    data: X
}
```

与：

```text
eth_call {
    from: B,
    to: P,
    data: X
}
```

可能产生不同结果。

因此：

```text
same to
+
same calldata
```

绝对不能直接定义 semantic equality。

必须确认当前项目的实际调用：

```text
from = ?
```

以及：

```text
from 是否固定？
```

如果固定：

可以记录：

```text
from_semantics = fixed
```

但不能因此把 `from` 从理论 identity 中永久删除。

---

# 9. 检查 value

同样：

```text
value = 0
```

与：

```text
value > 0
```

可能改变 execution。

必须实际检查项目调用参数。

# 17. Result 是否 deterministically reproducible

如果：

```text
same canonical block
+
same eth_call semantic identity
```

是否一定得到：

```text

```

理论上 EVM `eth_call` 的 deterministic property 可能成立，但必须检查当前项目是否存在：

```text
block.timestamp
block.number
blockhash
COINBASE
BASEFEE
PREVRANDAO
BALANCE
external state
```

以及：

```text
state override
```

等因素。

这里不要求重新证明 EVM。

要求证明：

> 当前项目这个 `eth_call` 的具体 execution context 是否足以保证结果一致。
