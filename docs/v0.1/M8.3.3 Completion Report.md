## 1. 白话版（不含术语，先读这段）

**单位约定先说清**：证据文件里存的全部是**纳秒（ns）**。1 毫秒 = 1 000 000 纳秒，1 秒 = 1 000 000 000
纳秒。下面每一个毫秒/秒都只是把某个 ns 字段的小数点左移 6 位/9 位读出来的**同一个数**，不是第二次
测量。‰ 同理：证据里存的是「分子 × 1000 ÷ 分母」的整数，两侧都是实测值。

打个比方：一次 simulation 是给节点打一通要问 39 个问题的电话。

- **上一轮（M8.3.2）这 39 个问题是一个一个问的**：前一个没答完绝不问下一个，所以通话总长 ≈ 39 次
  等待之和 ≈ 10 秒。
- **这一轮允许「同时问 2 个 / 4 个」**，但**只允许对已经证明互相无关的问题**这么做：同一个账户的
  余额 / nonce / 代码这三件，问哪件都不影响另一件的答案；一批合约字节码也一样。
- **存储槽（storage）没有拿到并发资格**：它一次只能挂一个请求，下一个要问哪个槽取决于上一个的答案，
  这一轮**证不出来**它们独立，所以照旧排队，并在依赖图里记 `dependency = unknown`（不猜）。
  这一条决定了收益的上限 —— 39 次里 20 次是 storage，它们串不串行走的是同一批槽。
- **问的问题一个没多、一个没少**：三臂都是每把 39 次、0 重复、0 重试，问的还是同一个「历史区块」
  （每笔都点名写出来了）。并发只改「怎么发出去」，不改「发什么」。
- **结果**：允许 2 个同时问，10 秒变 8.36 秒；允许 4 个，变 7.85 秒。**同一块固定历史区块的重放下**
  （每个回答都被桩故意按住 10 毫秒，好让重叠可测）三臂的模拟结果**逐字段完全相同**，
  墙钟 656.0 / 496.6 / 484.1 毫秒。
- **但节点并没有更卖力**：把每次调用的耗时加起来反而**变长了**（C4 是 C1 的 1132‰），最慢的一次
  从 0.59 秒涨到 0.84 秒。也就是说快是因为「等待被叠在一起」，不是因为「对方答得更快」。
  端点在压力下变慢这件事本轮**观测到了但没解释**，它同时和「九把跑在九个不同区块」混在一起。

**因此本轮真正的发现是两条**：

1. 有界并发在这条路由上确实能把 simulation 墙钟压掉 **约 16%–21%**（live 中位），且**语义一个比特没变**，
   界也从不被突破；
2. 收益的量级**受 storage 的串行下界支配**（180/342 次读），并且**被端点侧的每调用变慢吃掉一部分**，
   所以它不是「界越大越快」的直线。

## 4. §3 实现：有界并发调度长什么样

新增 `crates/simulation/src/acquisition.rs`（831 行）+ `state.rs` 的接线：

- **两个已证明独立的 hand**：`account_triple`（同一地址的 balance / nonce / code）与
  `touched_contracts`（计划先定好地址集合、再一批 bytecode）。除这两处之外**没有任何读被并行化**。
- **storage 明确不并行**：REVM 的 async fiber 一次只挂一个 database 请求，下一个 slot 取决于上一个
  返回值；本轮证不出独立性 ⇒ 依赖图记 `dependency = unknown`，顺序照旧（§5–§7「不能证明必须保持
  依赖顺序」+「禁止猜测」）。
- **调度器是 chunk 化 `join_all`**：按界切块，逐块 await；某块里出现失败就**等完该块即停**，不再开下一块，
  调用方按**输入序**报第一个错（不是 `try_join_all`：那会让同一块里已发出的兄弟请求变成悬空任务）。
  结果顺序与输入顺序一致，即使回答乱序到达 —— 这是 §3 的「不改变 simulation 语义」在实现层的落点。
- **配置与观测是两个数，不互相替代**（§15）：每次 simulation 自带 `ConcurrencyReport{ configured,
  observed_peak, batches, batched_reads, batch_dispatches, note }`；`configured` 是命令行给的界，
  `observed_peak` 是调度器在每次 dispatch 前后自己 bracket 出来的高水位。证据里三者并列出现：
  `configured_concurrency`、`observed_max_concurrency`（provider 侧）、`wire_max_concurrency`（RPC trace 区间扫出来的）。
  `CONCURRENCY_NOTE` 把三条容易被读反的关系写死在文件里：缓存命中的读**不进**峰值；重试在 provider 侧
  仍是一次读、在 wire 侧算两次 attempt；界被给过不等于它发生。
- **CLI**：`--state-read-concurrency`（`crates/cli/src/lib.rs:781`），默认 1，拒绝 `0`（那不是界，是「什么都
  不能挂起」）、拒绝 >8、拒绝溢出；`-1` 由 clap 在参数层就拒。
  **这里要更正上一笔提交说明里的一句话**：commit 0a1d867 写的是「只接 1/2/4/8」，实际实现**不是白名单** ——
  1..=8 的任何整数都接受（测试显式把 3 和 5 也跑通了，`crates/cli/tests/arbitrage_args.rs:740-751`），
  拒绝的是 0、>8、放不下、负数四种。§2 的四臂当然还是 1/2/4/8，但「拒绝 3」这条政策任务书没要求，
  实现也就没做。**证据不受影响**（本轮只跑了 1/2/4），文档以本段为准。
- **§3 的禁止清单逐条没碰**：没有 batch JSON-RPC、没有 multicall、没动连接池/keep-alive、没有换或选
  provider、没有 prefetch、没有投机执行、没有全局/跨 simulation/跨块缓存、没有改 REVM、没有动
  opportunity/graph/risk/execution/preflight/detection、没有 SequencerDirect、没有签名、没有广播、
  没有删 `state_read_reuse`、没有改 M7 路径。

## 14. §14 Limitations（本轮不能说什么）

1. **九把在九个不同区块**（§20 明确允许）。跨臂的 p50 之差里混着块差；能干净相减的只有 §8 的固定块。
   三臂区间不重叠是方向性证据，不是同块对照。
2. **单一端点**：全部指向 `rpc-faa716cada04a9ef` 一个指纹、链 91342。换端点、换网络的结果未知。
3. **样本量**：每臂 3 把 ⇒ p50 是实测中位，**p90/p95/p99 = `null`**（最小样本 10/20/100，§21 不许伪造）。
   任何「尾延迟」结论本轮都给不出。
4. **C8 未跑**：§2 允许它是可选的，本轮没跑，所以「界再翻倍会不会继续有收益 / 会不会反转」没有数据。
5. **storage 仍是 `dependency = unknown`**：180/342 次读保持串行。本轮的收益是「只并发那两把已证的
   hand」的收益，**不能**读成「state 读全部并发的收益」，也不能读成 storage 并发不安全。
6. **execution lane 的读界面未测**：那只适配器没有 sink。九把里只有 18 次读被 `route-run.json` 引用到，
   其余连引用都没有（§11）。本目录不说它是 0。
7. **九把并没有走到同一阶段**：3 把停在 `Built`（c2-02、c4-01、c4-03），6 把更早停在费用闸 ——
   它们读到的 base fee 高于给计划定价的上限（`invalid intent: ... underpriced`，例如 c1-01 的
   1000626 vs 1000628）。这是这条路由在那一秒的市场判定，与 state 读取耗时无关（九把都跑完了
   simulation，那才是 §19 要求的）；但「停在哪个阶段」与臂号相关（C1 0 把、C2 1 把、C4 2 把），
   所以三臂的**下游**记录不同，只有 simulation 段是同一口径。
8. **端点在更高界上更慢**：每次调用的平均耗时随界单调上升（255 586 677 → 268 922 679 → 286 557 265 ns），
   `eth_getCode` 的单次中位 C4 是 C1 的 **1551‰**（253 137 375 → 392 833 875 ns），单次最慢
   411 977 792 → 837 262 792 ns。**这是观测，不是解释**：它和「九个块」这一项混淆在一起，
   而且本目录没有任何客户端侧的排队/连接数据可以把它归给端点。
9. **是否存在 provider rate limiting：无法判定**。实测 0 次失败、0 次重试、`error_classes` 全空，
   也**没有** 429 / 限流错误码可指；固定块桩侧端点同时持有连接峰值 == 界（1/2/4），但这只说明桩
   接受了几路，不说明真实端点的限流阈值。因此「界再高会撞限流」既不能被排除也不能被主张。
10. **p95/p99 的缺失是设计代价**：§21 宁可 null 也不给数。想看尾延迟需要每臂 ≥100 把（p99），
    而按本轮实测速率每臂 100 把 = 300 把 live run（约每把 10 s 的 simulation 段 + 生命周期 ≈ 每把 20 s
    量级的墙钟 ⇒ 单机连续约 100 分钟以上的运行窗，另加端点配额），这不是本轮能顺带做的事。
11. **固定块的桩每响应 10 ms**：那是为了让 overlap 可测而**设计**的，所以它的绝对墙钟（656/497/484 ms）
    与 live 的 9.9/8.4/7.8 s 不可比，只有「同一块、同一批响应」这一件事可比。

## 17. §15 / Q10：Decision（只描述实验结果，不排名）

允许写的措辞，本轮的数字版本：

```text
C2 reduced simulation wall time by 1575828667 ns (to 841‰ of C1's p50)
C4 reduced simulation wall time by 2084313667 ns (to 790‰ of C1's p50)
On the fixed block, the same route: −159453875 ns (756‰) and −171907625 ns (737‰)
```

本轮**不**写「C4 比 C2 更好」「并发是最优解」「界越高越快」—— 每臂只有 3 把、九个不同块、
单一端点、p90/p95/p99 为 null，这些减法本身就不是同一块上的差。

**判定（§34 的门槛语义 + §33 的成功定义）**：

> **Evidence supports proceeding to a production bounded-concurrency implementation** —— 在
> 「只把已证明独立的 hand 并行化」这一条被原样保留、并且以下 6 项在下一阶段被显式闭合的前提下。

支持它的三条：语义一致性是**硬门槛**且已过（21/21 + 指纹 + 五道门）；界从不被突破、重叠是 trace 出来的
（不是配置的）；降幅的量级不是噪声（三臂区间两两不重叠，且固定块同块复现同方向）。

限制它的 6 项（下一阶段的工作项，不是本轮的失败）：

1. storage 的独立性仍未证明 —— 它是 180/342 次读，也是 serial wait 剩 7 成的来源；
2. 每臂样本 3 ⇒ 尾延迟为 null；同块对照只有固定块那一组；
3. 端点侧「界越高单次越慢」的观测未归因（§14(8)、§14(9)）；
4. execution lane 的读界面在本轮不可见（§14(6)）；
5. simulation 之外每把还有 ~5.2 s 的已测读耗时与一整条未测界面，链路总延迟不由 simulation 单独决定；
6. 本轮的 CLI 默认仍是 1；把它改成任何别的数都需要一次独立的、带广播授权的决定（§3）。
