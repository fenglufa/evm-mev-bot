# EVM MEV Bot

## v0.1 Technical Design

---

# 1. 设计目标

v0.1 的技术目标只有一个：

> **建立一个可以从真实 EVM 链数据恢复市场状态，并从市场状态中发现套利机会的最小完整 MEV Engine。**

完整链路：

```text
Chain
  ↓
Block / Log
  ↓
Protocol Event
  ↓
State Update
  ↓
Pool State
  ↓
Market Graph
  ↓
Opportunity Detection
  ↓
Arbitrage Opportunity
```

v0.1 暂时停止在：

```text
Opportunity
```

后面。

也就是说：

```text
Simulation
Risk
Execution
```

只建立接口和边界，不成为 v0.1 的核心实现。

---

# 2. v0.1 的核心闭环

最终必须跑通下面这个真实闭环：

```text
真实 Block
    ↓
真实 Logs
    ↓
真实 DEX Pool
    ↓
真实 Reserve
    ↓
StateStore
    ↓
Graph
    ↓
Arbitrage Path
    ↓
Optimal Input
    ↓
Expected Profit
```

如果这一条链路没有跑通：

> v0.1 不算完成。

---

# 3. 系统边界

v0.1：

```text
                    EVM MEV BOT
                         │
       ┌─────────────────┼─────────────────┐
       │                 │                 │
     Chain            Protocol            State
       │                 │                 │
       └─────────────────┼─────────────────┘
                         ↓
                       Graph
                         ↓
                   Opportunity
                         ↓
                      Replay
```

暂不进入：

```text
Simulation
Risk
Execution
Signer
Private Relay
Bundle
```

---

# 4. 第一版不要设计成微服务

v0.1：

> **单进程。**

推荐：

```text
Single Process
├── Chain
├── Protocol
├── State
├── Graph
├── Opportunity
├── Replay
└── Metrics
```

不要：

```text
Chain Service
State Service
Graph Service
Opportunity Service
```

这种架构。

MEV Hot Path 对跨进程通信没有需求，反而会增加：

* latency；
* serialization；
* deployment complexity；
* state synchronization；
* debugging complexity。



# 41. AMM Swap Formula

对于：

```text
x = reserve_in
y = reserve_out
f = fee factor
a = input
```

输出：

```text
amount_out =
    amount_in_with_fee * reserve_out
    /
    reserve_in + amount_in_with_fee
```

其中：

```text
amount_in_with_fee = amount_in * fee_factor
```

例如 0.3%：

```text
fee_factor = 997 / 1000
```

---

# 42. Optimal Input

两池套利不能只：

```text
固定 input = 1 ETH
```

而应该计算：

```text
optimal input
```

然后：

```text
profit(input)
```

在：

```text
input = optimal_input
```

附近取得最大值。

# 91. Flashblocks 的位置

如果某条 EVM 链存在类似 GIWA 的 Flashblocks / preconfirmation feed：

```text
Chain Feed
├── Standard Block
└── Preconfirmation Feed
```

两者最终都转换为：

```text
ChainEvent
```

再进入：

```text
Protocol
 ↓
State
```

这样不会污染 State 层。

GIWA 当前公开节点项目也把 Flashblocks作为可选 WebSocket 能力，而不是标准 EVM RPC 本身。

---

# 92. Flashblocks 不进入 v0.1 核心假设

v0.1 首先保证：

```text
Standard EVM Block
```

完整正确。

Flashblocks 属于：

```text
Low Latency Feed
```

在进入 Live Pipeline 时接入。

原因：

> 如果 State Engine 只能依赖 Flashblocks 才工作，那么系统就无法真正成为 Multi-EVM Bot。
