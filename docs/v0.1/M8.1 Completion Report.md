## 3. Architecture

三层，边界就是「谁有权决定这条生命周期是什么」：

```text
crates/metrics  ——  事实的形状。不认识 pipeline，不认识执行，不认识链。
                    Stage 枚举 + 一行 14 格的不变量 + 分位数规则。
crates/pipeline ——  事实的采集。TraceRecorder 是唯一能写下阶段的地方。
crates/cli      ——  开关与入口。两个 flag，一个只读子命令。
```

只有三个接入点（§16–§29 要求的所有阶段都从这三处折出来，没有第四个）：

1. **路线 run**（`pipeline/src/arbitrage.rs`）：一条机会从被命名到停在哪儿，14 格全走一遍，
   live 侧用 ns 精度的自己的钟。
2. **发现半侧**（`pipeline/src/runner.rs`）：live / replay 的 observation → state → graph → detection，
   全部读 M5 早就写下的 stamps（§15：一个新瞬间都不测）。
3. **历史折算**（`pipeline/src/history.rs`）：只读 M7 证据文件，把它里面已经存在的毫秒差搬进 trace。

`crates/execution` 与 `crates/simulation` **不在接入点清单里** —— 这是「不改执行语义」得以成立的结构性原因，
不只是「我小心没改」：执行层没有任何一条路径能拿到 recorder。

## 5. Measurement Method

- **只有一个钟**：`crates/metrics/src/clock.rs` 的单调 ns 钟。全仓 `SystemTime::now()` 只出现在
  `unix_ms()` 一处，且只写进「文件是什么时候生成的」这类元数据字段（§2.3）。
- **绝不出现负跨度**：读数倒挂时钳到 0 并注明，不做回绕（T8 双测试钉住）。
  7 条 trace 实测 `duration_ns < 0` 的行数：**0**。
- **每个数都必须回指一个已经存在的字段**（§15）：路线 run 只读 run 自己为了业务原因写下的 stamps；
  发现半侧读 M5 的 hop；历史折算读 M7 的 `latency_ms.rung_stamps`。
  7 条 trace 的 `instrumentation_refusals` 全部为 `[]`。
- **分位数**：nearest-rank，与 M5 `metrics.json` 同一套算法（`nearest_rank_agrees_with_the_m5_series_over_the_same_samples`
  拿 M5 的序列对过）。门槛 p50/p90/p95/p99 = 2/10/20/100 个样本；
  不够就 `null` + `"reason": "insufficient_sample"`。一个 rank 只有在它的下标严格小于最后一个样本下标时才报，
  所以报出来的数**永远是发生过的一次测量**，不会是把 `max` 重印一遍。
- **不混合来源**：`live` / `replay` / `fixture` 分桶，`sources_are_never_blended: true`（7/7）。
- **两种总量**（§10）：`wall_clock_total`（起点到终点的墙）与 `stage_duration_sum`（14 格相加），
  两者之差就是没被任何一格盖住的排队时间 —— 本轮最大的一次是 887.6 ms（live run 1）。
- **成本分类**（§11）：`local_processing` / `mixed_reads_and_compute` / `network_or_chain` 三桶相加
  必须精确等于 `stage_duration_sum`（7/7 条成立）。`simulation` 一格按它**实际怎么挣的**归类：
  状态源是 `rpc:` ⇒ mixed，读录制 dump ⇒ local。这条是本轮第二个真缺陷的根因修正（`d4f61a9`）。
- **开销**（§38）：时间戳 → 存一格 → 时间戳。每格 O(1)，无 sleep、无 yield、无额外请求（§15），
  一条生命周期恒定 14 格。
  **本轮没有单独测「开 flag 与不开 flag 的墙差」** —— §38 要的是这个论证结构（每格两次读数 + 一次写入），
  不是再一个数；能当量级参照的是同一台机器上那些「几乎不做事」的格子实测到的下限：
  `risk` 0.011–0.016 ms，replay 的 `observation` / `state_update` / `graph_update` 落在同一个毫秒内
  （文件里写的是「这是时钟分辨率，不是它不花时间」）。

## 12. Known Limitations

完整 13 条在基线报告 §42.8；下面挑最要紧的 6 条 + 本轮写文档时新发现的第 13 条：

1. **样本量决定 p99 不存在**。本轮最大桶 2 个样本；live 侧结构上永远是 1 个样本/会话。
2. **`receipt` 与 `inclusion` 实测不可分**（§15 不许为拆分它多发一次请求），因此 `receipt` 恒 `skipped`。
3. **历史 trace 只有跨度、没有时刻**（无共同零点 ⇒ `started_ns/ended_ns/wall_clock_total` 全 `null`）。
4. **表达力上限**：ladder 没有 `preflighted_at_ms` 这一格，且没有叫 `rejected` 的结果词，
   所以「闸门拒了」的形状是 `preflight` completed + 后续每行 skipped 的 note 里引用闸门原话。
   本轮选择欠称（一律 skipped）而不是虚称 failed，并把这件事记成 M8 后续的活而不是偷偷补一格。
5. **`git_revision` 只能证明「哪个 commit 编出的二进制」，不能证明工作树 clean**。
   本轮每条证据都出自 clean tree 重建后的运行（7 份 summary 的 revision 全部等于 HEAD），但文件本身自证不了。
6. **模拟里的 RPC 读次数没被记录**（`RpcStateProvider` 不记；录制 dump 记 `reads`，可比的那份记着 64 次），
   所以 §13 候选 1 的「可能原因」目前只有代码路径可指，没有实测计数。
7. （本轮写文档时新发现，尚未修）**同一个检查项在代码里有两个名字**：`PreflightCheck::InputAssetBalance::name()`
   返回 `"input_token_balance"`，而 JSON 里 serde 按变体名 snake_case 输出 `"input_asset_balance"`。
   本轮没碰它（它在 execution 层，改它属 §1 禁的语义面之外但仍是 M7 资产）；记给 M8.5 observability。

## 16. §53 十七问的答复

1. **当前完整 lifecycle 有哪些 timestamp？** 14 格 × (started, ended) + 17 个 hop 名 + 5 个端到端里程碑；
   live 侧起点终点是同一个单调 ns 钟上的两个读数，历史侧只有跨度没有时刻。
2. **每个 timestamp 的语义是什么？** 基线报告 §42.3 一行一格列全了（含「终点必须是答案产出而不是发起」的几处），
   本文 §4 给定义口径。
3. **Observation → Opportunity 的定义？** `observation.started` → `opportunity_detection.ended`，
   即 §13 的 `detection_latency`。实测 live = 2,418 / 2,369 / 2,797 ms；replay = 2.0 ms。
4. **Submit → Inclusion 的定义？** `submit.ended`（RPC 对 `eth_sendRawTransaction` 答复的那一刻）
   → `inclusion.ended`（收据证明入块）。**收据不在 Submit 里**（§21）。实测 3,367 ms（M7 那笔，1 样本）。
5. **Inclusion → ProfitVerified 的定义？** 中间穿过 `receipt`（本轮恒 skipped，原因见 §12 #2）与
   `settlement`；实测 `inclusion→settlement` = 27,221 ms，`settlement→profit_verified` = 0.000 ms
   （同毫秒 = 时钟分辨率，不是不花时间）。
6. **哪些 latency 是本地计算？** `opportunity_detection`、`risk`、`build`、`sign`，
   以及读录制状态时的 `simulation`（§11.1）。
7. **哪些包含 RPC / network？** `observation`、`submit`、`inclusion`、`receipt`、`settlement`、
   `profit_verification`（§11.2），加上 `preflight`（mixed）与**读真状态时的 `simulation`**（mixed）
   —— 后者是本轮修掉的根因：live 三条里它占阶段和 85–92 %。
8. **M7 的 6 笔真实交易能否得到 latency？** 能，9 格（见 §8 的表），全部来自 M7 已经写下的字段，零重建。
9. **不能的话缺哪些字段？** `observation/state_update/graph_update`（M7 的路线 run 没做观测）、
   `risk`（记了内容没记耗时）、`receipt`（与 inclusion 共用一个瞬间）、`wall_clock_total`（无零点）。
10. **live observation 有多少 opportunity？** 60 秒纯观测 = **0**；3 个 live 路线 run 各 1 个机会
    （`opportunity_count: 1`），合计 live 侧 3 条 trace、3 个样本/桶。
11. **样本量是否足够计算 p99？** **不够，差两个数量级**：需要 100 个样本，最大桶 2 个。p99 全 `null`。
12. **fixture 与 real market 是否严格分开？** 是。`TraceSource` 三类强制标注，`sources_are_never_blended: true`
    （7/7），fixture 桶在统计里自称 `replay`（它走的是真实录制，所以不许它冒充 `live`；
    `fixture` 这一类本轮没有任何生产者 —— 宁可没有，也不拿合成行情充数，见 §12 与基线报告 §42.8 #8）。
    业务侧市场类别另有一格 `REAL_MARKET` / `CONTROLLED_FIXTURE`，本轮 3 个 run 都是 REAL_MARKET 且
    `successful_real_arbitrage = false`。
13. **instrumentation 是否新增 RPC？** **0 次**。所有数都是读 run 自己已经写下的字段；
    `instrumentation_refusals` 7/7 为空（有拒绝写会立刻在这里露出来）。
14. **instrumentation 是否改变执行语义？** 没有：execution/simulation/risk/opportunity 四个 crate
    一字节未改（§11 的 diff 事实），flag 关闭时逐字节相同（测试钉住），本轮 0 签名 0 广播。
15. **是否发现明显 bottleneck？** 发现 5 个（§13），最大的是「模拟这一格的时间其实在节点上」（约 1,000 倍），

16. **哪些问题留给后续 M8？** 样本攒够（M8.8）、真实 Submit 全链样本（需授权）、`preflighted` 那一格与
