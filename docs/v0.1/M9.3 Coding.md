# 1. Objective

实现一个纯 Rust、纯内存、确定性的 `PathFinder`，从 M9.2 已经构建好的 `GraphSnapshot` 中枚举符合约束的 V2 多池套利闭环。

M9.3 的核心目标不是判断盈利，也不是执行套利，而是：

```text
GraphSnapshot
    ↓
Bounded Path Search
    ↓
Closed Cycle
    ↓
Canonical Cycle
    ↓
CycleCandidate
```

必须严格区分：

```text
Path
≠
CycleCandidate
≠
Executable Opportunity
≠
Simulated Profit
≠
Executed Profit
≠
Realized Profit
```

M9.3 只负责：

> **从一个已经经过 M9.2 状态一致性验证的 GraphSnapshot 中，确定性地枚举合法闭环。**

# 5. Core Definition

## 5.1 Path

定义：

```text
Path = ordered directed Edge sequence
```

满足：

```text
edge[i].token_out == edge[i+1].token_in
```

例如：

```text
WETH
 ↓ Pool A
USDC
 ↓ Pool B
DAI
```

是一个 open path。

---

# 6. Cycle Definition

M9.3 只输出闭环：

```text
start_token == final_token
```

例如：

```text
A → B → A
A → B → C → A
A → B → C → D → A
```

M9.3 第一版最大 hop：

```text
MAX_HOPS = 3
```

因此只允许：

```text
2-hop:
A → B → A

3-hop:
A → B → C → A
```

不得实现 4-hop 或以上作为默认生产能力。

如果内部实现使用泛化 `max_hops` 参数，可以支持：

```text
2..=3
```

但默认值必须为 3。

不要通过 arbitrary candidate count 截断搜索。

---

# 7. Why MAX_HOPS = 3

第一版必须明确限制搜索空间。

PathFinder 不应该无界 DFS。

搜索空间会随着 hop 数快速膨胀，并且当前图允许：

```text
multiple pools per token pair
```

因此：

```text
bounded DFS
+
MAX_HOPS = 3
```

是当前正确的边界。

以后如需 4-hop，必须单独评估搜索空间、benchmark 和 pruning，而不是在本任务中顺手打开。

---

# 8. Pool Reuse Rule

一个 Cycle 内：

```text
PoolId MUST NOT repeat
```

例如：

```text
A
 ↓ PoolX
B
 ↓ PoolX
A
```

必须拒绝。

即使拓扑上形成闭环，也不是有效的套利 cycle。

要求：

```text
pool_ids are unique within candidate
```

---

# 9. Intermediate Token Reuse Rule

第一版要求：

```text
intermediate TokenId MUST NOT repeat
```

允许：

```text
A → B → A
A → B → C → A
```

禁止：

```text
A → B → A → C → A
```

禁止原因：

这种路径可以拆成多个独立 cycle，会造成搜索空间膨胀，并产生非 canonical 子环。

因此：

```text
start token
+
distinct intermediate tokens
+
return to start
```

作为 M9.3 canonical cycle topology。

---

# 10. Multiple Pools Per Token Pair

这是 M9.3 必须正确支持的核心能力。

例如：

```text
Pool1:
A ↔ B

Pool2:
A ↔ B
```

必须能够发现：

```text
A
 → Pool1 → B
 → Pool2 → A
```

同时也必须发现反向交易方向：

```text
A
 → Pool2 → B
 → Pool1 → A
```

但后续 canonicalization 只能消除 rotation，不能把 reversal 合并。

---

# 11. Edge Identity

不要使用：

```text
[token_in, token_out]
```

作为完整 edge identity。

因为：

```text
A → B
```

可能存在：

```text
Pool1
Pool2
Pool3
```

必须使用现有仓库的 `EdgeId` / 等价 identity。

如果现有：

```text
EdgeId =
(chain_id?, pool_id, token_in, token_out)
```

则优先复用。

不得重新定义一套冲突 identity。

# 12. Cycle Identity

Cycle identity 必须至少包含：

```text
chain_id

```

推荐最终 Candidate 结构：

```text

    chain_id,
    target_block,

    fee_status,
}
```

具体字段名称可以根据现有代码风格调整，但语义不得改变。

---

# 13. Rotation Canonicalization

同一个 Cycle 可以从任意 token 开始。

例如：

```text
A → B → C → A
B → C → A → B
C → A → B → C
```

这三个必须视为：

```text
ONE cycle
```

因此必须进行 rotation canonicalization。

---

# 14. Reversal MUST NOT Be Deduplicated

下面两个不能合并：

```text
A → B → C → A
```

和：

```text
A → C → B → A
```

它们是不同的 directed trading cycles。

原因：

* token direction 不同
* pool direction 可能不同
* reserves direction 不同
* price impact 不同
* fee direction 可能不同
* 后续 profitability 可能完全不同

所以 canonicalization：

```text
eliminate rotation
```

但：

```text
DO NOT eliminate reversal
```

---

# 15. Recommended Canonicalization Algorithm

对于：

```text
edges = [E1, E2, E3]
```

生成：

```text
[E1,E2,E3]
[E2,E3,E1]
[E3,E1,E2]
```

选择 lexicographically smallest representation。

注意：

* 比较应基于稳定 identity
* 不要基于 pointer address
* 不要基于 HashMap iteration order
* 不要基于随机值

如果现有 `EdgeId` 已实现 `Ord`，优先直接使用。

最终：

```text
canonical_key = minimum(rotation(edges))
```

重要：

> fee incomplete 的 Cycle 可以被 PathFinder 枚举，但不能被当作可交易机会。

因此：

```text

    ↓

    ├── FeeComplete
    └── FeeIncomplete
```

后续：

```text

    ↓

```

而：

```text

    ↓

```

M9.3 不负责解决 fee。

# 23. Search Algorithm

推荐使用 bounded DFS。

概念：

```text
for each start_token:

    dfs(
        start_token,
        current_token = start_token,
        depth = 0,
        tokens_seen = {start_token},
        pools_seen = {},
        edges = [],
    )
```

每次：

```text
current_token
    ↓
candidate routes
    ↓
edge
```

对于 edge：

### Case A

```text
edge.token_out == start_token
```

如果：

```text
depth + 1 >= 2
```

则形成 CycleCandidate。

### Case B

```text
edge.token_out != start_token
```

如果：

```text
depth + 1 < MAX_HOPS
```

继续 DFS。

否则停止。

---

# 24. Search Ordering

推荐稳定顺序：

```text
start_token ascending
    ↓
next_token ascending
    ↓
edge_id ascending
```

如果现有 GraphSnapshot 已提供确定顺序，可以复用。

最终仍必须对输出 candidates 做稳定 canonical ordering。

# 25. Cycle Length

合法 cycle：

```text
2 <= hop_count <= 3
```

不得产生：

```text

A → A
```

即使未来某些 graph model 支持 self-loop，也必须在 PathFinder 中拒绝。

---

# 26. Candidate Output Ordering

最终结果必须 deterministic。

建议：

```text
sort_by(
    chain_id,
    target_block,
    canonical_key
)
```

具体排序字段可按现有类型设计调整。

但不能依赖 HashMap/BTreeMap 偶然顺序。

# 27. Duplicate Prevention

最终输出中：

```text canonical_key MUST be unique
```

推荐：

```text HashSet<CanonicalKey>
```

或在稳定排序后 `dedup`。

如果使用 HashSet：

> HashSet 只负责 membership，不得直接决定最终输出顺序。

最终必须重新排序。

# 60. Final Design Principle

M9.3 最重要的原则：

> **PathFinder 负责回答“图中有哪些合法闭环？”**

它不回答：

> “这个闭环赚钱吗？”

更不回答：

> “现在应该交易吗？”

最终职责边界必须保持：

```text
Discovery
    = What pools exist?

State Reconstruction
    = What was their authoritative state at target?

Graph
    = What directed markets exist at target?

PathFinder
    = What valid cycles exist?

Amount Optimizer
    = At what amount might the cycle be economically interesting?

Simulation
    = Does the exact transaction actually execute?

Risk
    = Is it safe to execute?

Execution
    = Can we submit it?

Settlement
    = What actually happened?

Profit Verification
    = What did we actually earn?
```

M9.3 只占其中一层。

**不要越权。**
