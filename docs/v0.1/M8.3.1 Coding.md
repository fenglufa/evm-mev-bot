### M8.3.1 Coding Task — State Read Reuse

**目标**

在现有 M8.2 HEAD 基础上，实现 simulation 内部的 state-read reuse。

只优化以下四类已经被 M8.2 证明存在重复的读取：

```text
eth_getCode
eth_getBalance
eth_getTransactionCount
eth_getStorageAt
```

其中：

* `getCode`：允许复用
* `getBalance`：允许复用
* `getTransactionCount`：允许复用
* `getStorageAt`：虽然当前 20 次没有重复，但必须支持正确的 canonical key
* `eth_getBlockByNumber`：本阶段可以保持原行为，不主动优化

# 2. Cache 生命周期必须非常严格

**Cache 只能属于一次 simulation。**

禁止：

```text
global cache
process-wide cache
cross-simulation cache
cross-block cache
```

正确模型：

```text
Simulation N
    ↓
StateReadCache N
    ├── code
    ├── balance
    ├── nonce
    └── storage
```

simulation 结束后：

```text
drop(cache)
```

下一次 simulation：

```text
new cache
```

---

# 3. Canonical Key

必须明确实现以下 key。

### Code

```text
(chain_id, block_number, address)
```

### Balance

```text
(chain_id, block_number, address)
```

### Transaction Count

```text
(chain_id, block_number, address, block_tag)
```

如果当前代码中 `block_number` 已经完全表达 block tag，则必须基于实际语义设计，不要为了凑字段重复存储。

### Storage

```text
(chain_id, block_number, address, slot)
```

### eth_call

**本阶段不要自行猜 key。**

如果当前 adapter 的 `eth_call` 能拿到完整 canonical calldata：

```text
(chain_id, block_number, to, data, value)
```

才允许加入 cache。

否则：

```text
dedup_key_unavailable
```

不要通过 hash、debug string、序列化参数等方式偷偷创造一个未经证明的 key。

---

# 4. Cache 必须只缓存成功结果

例如：

```text
RPC
 ↓
success
 ↓
insert cache
```

失败：

```text
RPC
 ↓
error
 ↓
DO NOT CACHE
```

尤其不能：

```text
timeout → cache error
```

否则后续 simulation 行为会改变。

---

# 5. 最重要的正确性要求

必须证明：

```text
before simulation
==
after simulation
```

不是只比较：

```text
success / failure
```

至少比较：

```text
simulation outcome
revert status
gas used
return data
profit
risk decision
```

如果当前 simulation result 类型有更严格的 canonical representation，则优先使用现有类型。

---

# 6. 做 A/B 对照，而不是只跑优化版

必须存在：

```text
A = no cache
B = cache enabled
```

两条路径使用：

**完全相同：**

* pinned block
* transaction
* sender
* target
* calldata
* value
* gas
* EVM config
* state overrides
* chain context

唯一变量：

```text
state-read cache
```

---

# 7. RPC 数量必须直接证明

针对同一个 simulation：

```text
baseline:
80 calls

cached:
39 calls
```

不要只依赖 trace 推导。

必须使用 RPC stub / request counter 得到实际：

```text
baseline_request_count
cached_request_count
```

并比较 method sequence。

预期：

```text
baseline:
23 getCode
18 getBalance
18 getTransactionCount
20 getStorageAt
1 getBlockByNumber

cached:
6 getCode
6 getBalance
6 getTransactionCount
20 getStorageAt
1 getBlockByNumber
```

**如果实际结果不同，不要修改报告去适配预期，而是解释原因。**

---

# 8. 特别验证 sender 三件套

M8.2 已经发现：

```text
sender account
    getCode
    getBalance
    getTransactionCount
```

存在明显重复。

因此必须增加一个针对 sender 的测试：

```text
same simulation
same sender
same pinned block
```

验证：

```text
first getCode     → RPC
second getCode    → cache

first balance     → RPC
second balance    → cache

first nonce       → RPC
second nonce      → cache
```

而不是：

```text
第一次 simulation cache
第二次 simulation 偷偷复用
```

后者禁止。

---

# 9. Storage 必须做 negative test

当前真实样本：

```text
20 storage reads
20 unique
0 duplicate
```

因此不能因为做 cache 后测试只覆盖重复情况，就误把 storage cache 当成已经验证。

至少需要：

```text
same key twice
→ 1 RPC

different slot
→ 2 RPC

same slot, different address
→ 2 RPC

same slot/address, different block
→ 2 RPC

same slot/address/block, different chain
→ 2 RPC
```

这样才能证明 canonical key 真正包含：

```text
chain + block + address + slot
```

---

# 10. 跨 block 隔离必须测试

例如：

```text
simulation A
block = N

simulation B
block = N+1
```

即使：

```text
address = X
slot = Y
```

也必须：

```text
2 RPC
```

不能：

```text
1 RPC
```

这是历史模拟最重要的安全边界之一。

---

# 11. 跨 simulation 隔离必须测试

即使：

```text
same chain
same block
same address
same slot
```

两个独立 simulation：

```text
Simulation A → 1 RPC
Simulation B → 1 RPC
```

总计：

```text
2 RPC
```

而不是：

```text
1 RPC
```

# 16. 需要特别检查一个隐藏问题

**Cache 的位置非常重要。**

不要简单在最外层写：

```rust
fn get_code(...) {
    if cache...
}
```

然后发现某些 simulation 路径绕过了它。

M8.2 证明的是：

```text
RPC boundary
```

因此 M8.3.1 必须确认：

> 所有实际进入 `eth_getCode / eth_getBalance / eth_getTransactionCount / eth_getStorageAt` 的 simulation state acquisition 都经过同一个 reuse boundary。

否则最后可能出现：

```text
某一部分 cached
某一部分 uncached
```

然后误以为优化已经完成。


否则退回重新设计。
