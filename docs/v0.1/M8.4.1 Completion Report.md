## 1. 白话版（不含术语，先读这段）

**单位换算先看这一行**：本报告全部时长用纳秒（ns）记录，1 秒 = 1 000 000 000 纳秒，1 毫秒 = 1 000 000 纳秒。文中每个大数后面都括上「多少秒」，读数的时候看括号就够了。例：`32 221 657 873 ns` ≈ **32.2 秒**；`440 291 ns` ≈ **0.44 毫秒**。

**这次到底在问什么。** 机器人跑一次「能不能套利」的判断，要向前节点问很多次数值：某个账户有多少钱、某个槽里存了什么、某段代码长什么样。上一个里程碑（M8.3.3）证明了：把这些提问同时发出 2 个或 4 个，整段时间能缩短。但它留了一个没答的问题——**那些数值提问之间是不是真的必须排队？** 如果非排队不可，那 M8.3.3 的收益就有天花板；如果其实可以并行，那天花板还很远。

**答案一（那 20 个「槽里存了什么」的提问）。** 一次判断里读了 20 次槽。三把都是同一个结果：**没有任何一次能被证明「可以和不问它就问不出来的那一次同时发」**。19 次被判定为「必须等前一次」，每次都写清了等的是哪一次、凭什么说它得等；剩下 1 次是本轮第一次读槽，前面没有可比的对象，就老老实实记成「不知道」（unknown），**没有**把它当成「可以并行」。

**为什么「槽号不一样」不算证据。** 直觉会说：两个不同的槽，肯定互不影响，可以一起问。这个推理在本轮被明确禁止（§5），因为下一个要问哪个槽，是执行程序自己决定的，而它下一步做什么可能正好取决于刚拿回来的值。三把里 570 个「两次读槽的配对」，0 对拿到「独立」的判定。

**答案二（既然没有真依赖，为什么还是排队）。** 排队不是网络决定的，是**执行引擎的形态**决定的：它一次只把一个问题放进飞行中，拿到答案才决定下一个问什么。线路上的观测完全对得上：每一把的同时在飞上限是 **1**，重叠时间是 **0 纳秒**。也就是说，本轮能证明的是「它确实串行」，**不能**证明「它必须串行」——后者要改的那条通道正是 §1 这轮不许碰的。

**答案三（判断之外的时间去哪了）。** 一次跑动除了「判断」这一段，还要跑「找机会」「再确认一遍价格和手续费」「把要发的交易组装起来」。这轮把三段都接上了同一个记录器：**判断之外一共 118 次提问**（判断之内 117 次），其中再确认段 69 次、找机会段 18 次、组装段 22 次。按各段自己量到的时间加起来，判断段 32.2 秒、再确认段 18.5 秒、找机会段 5.4 秒、组装段 5.3 秒（这四段之外还有 6 次调用落在任务书七个名字之外的 stage 上，合计 1.5 秒，另有 3 次代码没给标记；完整的 235 行分配见 §9 的表。这些是 3 把分别测到再相加的，不是同一把的总账）。**结论不是「判断最慢所以先修判断」，而是「判断之外的提问次数和它差不多，时间也不小」。**

**这次没做的事。** 没并行化任何东西，没合并任何提问，没加缓存，没换节点，没签任何名，没发任何交易，一分钱没花。报告里所有数字都不构成「这样改会更快」的证据 —— 要下那个判断，缺的是被本轮禁掉的那些改动本身。

## 6. 每条 read 的四个字段（§4）

`storage-reads.json` 60 行，每行都带：`address`、`slot`、`block`（本轮的 pin）、`caller`（问它的 REVM 阶段原文）、`stage`、`dependency`、`depends_on`（它等的那一次）、`evidence`（这一条判定的证明文本）。**没有一行缺字段**，所以 §27 的「100% 有 address/slot/block、100% 有 dependency 分类」是按行检查过的，不是抽样。

`dependency-map.json` 的 node 还额外发布 `uses_prior_response`（§4 的第四个字段：`yes` / `possible_not_determined` / `no_by_construction`）。本轮 60 个 node 里 **0 个 `yes`**：`not_determined` ×3（没有前一次可比）、`possible_not_determined` ×57（排队来自 leg 的顺序）。理由：本轮记录的是**请求**，值在解释器里怎么流动不在记录面内，所以写 `yes` 就是拿错材料做论断。

## 13. §22-§11 Limitations

**任务书点名的五项：**

1. **provider latency 与 network RTT 没有分离**：本轮在「请求变成线上字节」的那一点记一次总时长（`provider_duration_field`），请求构造、节点排队、往返、响应解码与状态转换不可分。所以「provider 是瓶颈」「network latency」都不能说（§20）。
2. **样本量**：每类 3 个样本。`minimum_samples_for_rank` = {p50 2, p90 10, p95 20, p99 100}，所以每把的 p90/p95/p99 是 **null** 并附原因，没有任何一个百分位被估出来（114 个空隙宽度样本是例外，那一组够 10/20/100 的门槛）。
3. **unknown dependency**：3 条（每把第一条读槽）没有可比的前一次；57 条 `ordered` 里的 `uses_prior_response` 只能到 `possible_not_determined`，因为值在解释器里的流动不在记录面内。**本轮没有能力**判「能不能并行」，只判了「有没有必须排队」。
4. **execution visibility 的四个边界**：见 §10 的 1–4（构造期的 chainId、WebSocket、mode 没走到的 stage、不写 span 的 stage）。
5. **live 的块不同**：三把跑在 37 677 656 / 684 / 710 三个不同块上，且**没走到同一步**（一把停在 preflight 费用闸，71 行调用；两把走到 build，82 行）。两把之间的差首先是块之间的差。

**本轮没有的口径**：没有并发臂（`state_read_reuse` 三把都是 on，`mixed_arms: false`），所以本目录既不能证成也不能推翻 C1/C2/C4 的任何排名。

**本轮发现、按 scope 未改的三处文案缺陷**（数字面不受影响，全部是文本面）：

- **D1 —— `unreachable_reads` 第 2 条过期**。`outside-simulation-rpc.json` 的 `unreachable_reads[1]` 仍写「车道的读不在这里计数」，但 schema 3 之后**它们就在这些表里**（69 行 `preflight` + 22 行 `build`）。该文案来自 M8.3.2 的 `BLIND_SPOTS` 常量（`crates/pipeline/src/diagnosis.rs:1914` 起），同一份文本此刻同时活在三个证据根里：`data/evidence/m8/post-reuse/`、`data/evidence/m8/concurrency/`、`data/evidence/m8/storage-dependency/`（池化 JSON + 每把 run 的 JSON 与 README）。

## 15. §22-§12 Conclusion：现在知道了什么
