## 1. 白话版（先读这段）

把一条 pipeline 想成一条流水线：发现机会的人、决定要不要下注的人、算 EVM 的人、拼交易的人，四个人各自会打电话问行情节点（RPC）一些问题。这一轮只问一件事：**他们有没有打了重复的电话**，以及**重复的那通能不能不打下第二次**。

- 打了 246 通电话（三把 run 合计）。其中 78 通是「前面已经有人问过同一件事」。
- 这 78 通里，42 通看起来可以省（问的是同一个东西），30 通不能省（问的是同一个账户、但要的是不同高度的状态——省了就等于拿旧块的答案当新块用），6 通说不清（两个问法的块高度在记录里推不出来）。
- 那 42 通「看起来可以省」的，全部**没能证明可以省**。原因很实在：**记录里没有任何字段写「第一次拿到的答案归谁管」**。归节点连接层？归那次 simulation？归整个 run？这决定了第二个人能不能直接拿第一个人手里的答案。不知道归属就省，等于让 A 阶段去读 B 阶段脑子里的东西——读到了也可能是过期或者不该读的。
- 打个比方：你和同事各自打电话问过同一家餐厅「今晚有没有位」，两通电话问的是同一件事（数据相等）。但你不能把你打的那通报给同事让他别再打——因为「这位子给谁留、什么时候作废」这件事不在电话记录里，只在各人的行程表上。**「答案一样」不等于「可以共用」。**
- 还有一个容易看错的量：simulation 内部本来就有缓存，每把 run 有 77 次命中。**命中一次＝没有打电话**，所以这 77 次不在 246 里。本轮数的全是真打出去的电话（§18）。
- 结论方向按任务书 §35 的「结果 C」：**大量重复是真的，能不能复用证明不了**。所以下一步不是加缓存，而是先搞清 state ownership / lifecycle（谁存答案、活多久、谁能读）。

单位口径提醒：本报告所有「次 / 对」都是同一次 run 里的**逻辑请求**（一通电话＝一次 ask，重试不另算，§25），不是 HTTP 报文条数。

## 4. §4 Method：canonical RPC identity

一次 ask 的身份由 8 项组成（任务书 §8 清单原序）：`chain_id`、`method`、`category`、`block`（含 `block_form`）、`address`、`slot`、`to`、`calldata 摘要`，加 `endpoint_id`（端点摘要，M8.3.2 起就有）。

三条实现要点，都是本轮取证出来的，不是设计的：

1. **身份只从记录里已有的 dedup key 反解**（`identity_from_the_recorded_dedup_key`，78 对里 66 对）。12 对是无参请求（`eth_chainId`），走 `identity_from_a_parameterless_request`。反解失败就拒绝并记 `identity_unavailable`——本轮 0 条。**不去用行自己的 `block_tag` / `target` / `slot` 补**：两个来源会造出两个字段都不支持的数；不一致在这里是**被测出来的事实**（`integrity.rows_whose_fields_disagree_with_their_key = 0`），不是靠后写的字段覆盖掉。
2. **一个存字段拆不成两个字段**。任务书 §8 要 `block_number` 与 `block_tag` 两栏，但 M8.4.1 的记录只存一个 block 词——它要么是一个高度，要么是一个标签。所以表里给的是 `block` + `block_form`（`number` / `tag` / `absent`），缺的那半不发明值。
3. **分类挂规则不挂方法名**。§9 六类 read 由这条 ask「问的是什么」判，不由方法名子串判；每条候选行都带 `category` 与规则出处，`eth_chainId` 归 `chain_identity`，不是 state read。

## 5. §5 Duplicate Definition

六类（任务书 §4），本轮实测：

| 类 | 判据（一句话） | 对数 |
|---|---|---|
| exact_duplicate | 身份逐项相等，包括 block | 42 |
| semantic_duplicate | 写法不同、语义相同（`latest` vs `pending` 属此类） | 0（口径见下） |
| same_target_different_block | 同 target、身份去掉 block 后相等、block 不同 | 30 |
| same_method_different_semantics | 同方法但不同用途 | 0 |
| same_target_block_undetermined | 同 target，但两边的 block 关系推不出来 | 6 |
| not_a_duplicate | 不属于以上任何一类 | 不列（78 对里没有它） |

两个必须写清的口径：

- **`semantic_duplicate` 报的是「这份记录量不出来」，不是「没发生过」**。记录里存的是被折叠后的 call，`latest` 与 `pending` 事后无法区分（`duplicate-summary.json` 的 `semantic_duplicate` 字段带着这句）。因此 42 这个 exact 数是**已经吸收了**语义等价对之后的数——它是下界口径的一个特例，不是上界。
- **retry 不算 duplicate（§25）**：一行＝一个逻辑请求，它的 HTTP 重试列在旁边（`attempts`）。三把 run 的 `rows_with_more_than_one_physical_attempt` 都是 0，所以这个规则在 live 数据上没有对手；它在 `canonicalization/tests.rs` 的 `retry_is_not_a_duplicate` 里有正对照，`integrity.note` 就是这么写的（记为测量，不记为通过）。

## 7. §7 Reuse Candidates：三级分开

任务书 §6/§7 要求 duplicate、reusable、safe-to-reuse 是三句话，不是一句话。`reuse-candidates.json` 把 78 对全部列出，每行三个判决 + `reason`：

| 判决 | 对数 | 含义 |
|---|---|---|
| `reuse_candidate_unknown` | 42 | 是重复（A），且 §8 身份允许复用（B）；能不能安全复用（C）**未知** |
| `refused_different_block_identity` | 30 | 是重复，但 §23 的块规则直接判 `safe_to_reuse=false` |
| `not_a_candidate` | 6 | 块关系推不出来，连 B 都进不去 |

**`safe_to_reuse = 0`，且 0 的来源只有一个字段级事实**：五个条件在 42 个候选上的实测状态是

| 条件 | met | checkable-not-met | not checkable from a record |
|---|---|---|---|
| `state_semantics` | **42 / 42** | 0 | 0 |
| `same_block` | 21 | 21 | 0 |
| `block_identity` | 21 | 21 | 0 |
| `no_freshness_requirement` | 0 | 15 | **27** |
| `lifecycle_ownership` | 0 | 0 | **42** |

也就是说：**没有一个候选是卡在「数据不一样」上的**；42 个全部卡在 `lifecycle_ownership`（谁拥有这份答案）在记录里根本不是一个字段。`duplicate` 与 `reusable` 都成立，`safe_to_reuse` 无法成立——这正是三级必须分开的原因。若把它们混成「有没有重复」一栏，本轮就会被读成「42 次能省的 RPC」。

`state_semantics` 那 42 个 met 的含义要按它自己的 reason 读：「同一 method、同一批参数、同一端点摘要——节点被问的是同一件事」。它**不**声明两个调用者对这个答案的理解相同（§21 的 StateStore-vs-REVM 之争），只声明 ask 是一个 ask。

## 8. §8 Block Freshness：逐候选

42 个候选的块关系实测分布（`block_relation`）：

- 21 对：两边点名同一个高度 → `same_block` 成立，`block_identity` 成立。全是 `eth_getBlockByNumber` / `eth_maxPriorityFeePerGas` / `eth_chainId` 这类「头/费率轨道」上的读。
- 12 对：两边都不带 block 参数（`eth_chainId` 之类）→ 没有块可比，条件走「无块」分支，`same_block` 记 `checkable_not_met` 而非「相等所以能复用」。
- 9 对：两边都只给标签（`latest` / `pending`）→ 记录里没有标签解析成的高度，所以「同一块」无法证明，也无法否证。

被 §23 拒绝的 30 对：两边各点名一个不同高度，理由逐行写成 `"different block identity"`（§23 要求的原话）。这 30 对里 18 对是 `eth_call`（opportunity_detection → preflight），是全部 78 对里最大的一坨——**它们看着像重复（同池、同 calldata），但一个问的是发现时的块、一个问的是决策时的块**，按 §23 不可复用。这一坨也是本轮唯一一处「重复量大但明显不该省」的路径。

## 9. §9 Simulation Cache Interaction

三个量在这轮数据里是三条线，不能加：

| 量 | 每把 live run 的值 | 是否进 246 |
|---|---|---|
| cache hit（不产生请求） | 77 | **否** |
| logical read（一次 ask，无论命中与否） | 82 次 ask 中由 M8.3.1 缓存服务的那 77 次 lookup | 只数打出去的那 82 |
| physical RPC（真打给节点） | 82 | 是 |

`state_read_cache` 三把完全相同：`{hits: 77, misses: 38}`，分账户项为 balance 12/6、code 27/6、nonce 12/6、storage 26/20（hits/misses，四组相加正好 77/38），`simulations_with_reuse = 1`、`simulations_without_reuse = 0`。**77 次命中不在 246 里，也不在 78 对里**（§18「cache hit ≠ physical duplicate」）。这条区分是本轮数字可解释的关键：M8.3.1 已经在**一次 simulation 内部**省掉了 77 次请求；本轮量的是**跨 stage 那一层还没被省的部分**。两者不重叠，也不能相加。

## 10. §10 Correctness

## 13. §13 Limitations

本轮测到的边界，按「谁能推翻它」分类：

1. **`lifecycle_ownership` 不是记录字段**（42/42 不可判）。要推翻只能改代码——而 §2、§22 明令本轮不许改。这是本轮结论的主限。
2. **`no_freshness_requirement` 同样不是记录字段**：27 个不可判、15 个「可判但不满足」。「代码为什么又问一次」没有字段。
3. **`semantic_duplicate` 量不出来**：raw 存折叠后的 call，`latest` 与 `pending` 事后不可分。表里的 0 是对**记录**的测量，不是对**市场**的断言。
4. **6 对 `same_target_block_undetermined`**：一边给高度、一边给标签，标签解析后的高度没被记录，因此两边块关系不可判——它进不了候选（`not_a_candidate`），也没被算成「不可复用」。
5. **样本量**：live 只有 3 把，同 build 同路由模板。本轮所有量都是计数，不报百分位，所以 3 把足够；但「42 对候选」不是「平均每把 42 对」，也不是「每块 42 对」——它已经是三把合计。
6. **provider 边界**：记录点在「请求变成线上字节」那一处，节点侧的缓存、CDN、批量服务本轮不可见。若节点自己合并了请求，本轮数的是「发了多少」而不是「节点执行了多少」。
7. **未打标记的 stage**：3 + 3 = 6 对来自 `unstamped`（`eth_chainId`），以及固定块臂各 1 次。M8.4.1 已记过一次并发歧义，本轮不改打标机制，只在表里显式保留 `unstamped` 这个名字而不是猜一个。
8. **重试对照缺**：三把 live run `rows_with_more_than_one_physical_attempt = 0`，§25 的规则在 live 上没有对手；正对照只在 `canonicalization/tests.rs` 里。
9. **一处跨里程碑的连带改动**（必须报备）：本轮给 M8.3.2 的 `post-reuse/README.md` 加了一行「这次没开 M8.4.2 的开关所以看不到跨 stage 表」——与 M8.4.1 在 `12d3a9a` 加那行是同一个生成器列表、同一个刷新开关（`M832_POST_REUSE_REFRESH=1`）。该目录**只有这 1 行变化**，其余 11 个字节门禁测试仍绿。

## 14. §14 Conclusion（只说发现了什么）

1. **跨 stage 重复是大量存在的**：3 把 run、246 次 ask，78 对重复，其中 72 对跨 stage、6 对同 stage。最大单一来源是 `opportunity_detection → preflight` 的 18 对 `eth_call`（同池同 calldata、不同块），和 `preflight → build` 的 12 对 exact 重复。
2. **42 对进入 reusable 候选，0 对能判 safe-to-reuse**。0 的原因是单一的：`lifecycle_ownership` 不是这份记录里的字段（42/42）。数据相等这一条 42 对全部满足。
3. **块新鲜度这一刀切掉了 30 对**（§23，理由逐行点名 `"different block identity"`）；另有 6 对块关系不可判，连候选都不进。
4. **simulation 内部的复用已经在跑**（每把 77 次命中、不进本表）。本轮量的是它跨不出去的那一层。
5. 按任务书 §35，本轮落在**结果 C**：大量 duplicate，但 block/freshness/lifecycle 无法证明。因此下一步是 state ownership / lifecycle 的研究，**不是**直接加 cache。
6. 允许写的下一步（§30）：`preflight → build` 的 12 对（exact、同块、同身份）**该 candidate 可进入下一轮 controlled reuse experiment**；`Preflight → Simulation` 的反向 9 对与 `unstamped → build/preflight` 的 6 对值得先补打标，再判。
7. **本轮不写「因此应该实现 cache」，也没写。** 证据 README 里那句「Nothing here is a recommendation to build a cache」是生成器写的，不是事后补的。
