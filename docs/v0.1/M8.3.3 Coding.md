# M8.3.3 Coding Task

## Controlled RPC Parallelism Experiment

> 项目：`fenglufa/evm-mev-bot`
> 阶段：M8 Hardening
> 当前阶段：M8.3.3
> 前置完成：M8.3.1 State Read Reuse、M8.3.2 Post-Reuse State Acquisition Diagnosis
> 本任务性质：**实验 / 诊断，不是正式生产优化**

---

# 1. 背景

M8.3.1 已完成 simulation-local state read reuse。

M8.3.2 已重新测量 reuse 开启后的真实 state acquisition：

每次 simulation 当前稳定为：

```text
eth_getStorageAt       20
eth_getCode             6
eth_getBalance          6
eth_getTransactionCount 6
eth_getBlockByNumber    1
--------------------------
                        39 RPC
```

三把 live simulation 均验证：

```text
duplicate_state_reads = 0
max_concurrency = 1
overlap_duration = 0
rpc_union / rpc_span ≈ 996–997‰
simulation non-RPC ≈ 28–30 ms
```

因此目前 simulation 仍然基本由 RPC acquisition 构成，并且全部串行。

M8.3.3 的唯一核心问题：

> **在不改变 state、simulation、risk、execution 语义的前提下，受控提高 state RPC 并发度，是否可以显著降低 simulation latency？**

本轮必须保持实验性质。

---

# 2. 本轮目标

实现一个**可控 bounded concurrency 的 state acquisition 实验路径**。

至少支持：

```text
concurrency = 1
concurrency = 2
concurrency = 4
```

如果现有架构自然支持，可以增加：

```text
concurrency = 8
```

但 8 不是硬性要求。

必须回答：

1. concurrency=1 是否复现 M8.3.2 baseline？
2. concurrency=2 是否真的产生 RPC overlap？
3. concurrency=4 是否真的产生 RPC overlap？
4. simulation total duration 是否下降？
5. RPC wall duration 是否下降？
6. correctness 是否完全保持一致？
7. fixed-block 下 baseline/C2/C4 是否 field-by-field identical？
8. 并发是否仍然严格绑定同一个 historical block？
9. 是否存在新的 RPC、retry、failure、state inconsistency？
10. 并发收益是否足以支持下一阶段正式优化？

# 5. 首先建立 State Acquisition Dependency Map

在修改实现之前，必须从当前代码建立实际依赖关系。

不要根据“看起来可以并发”判断。

## 5.1 Block context

```text

```

确认它：

* 是否在 state reads 之前执行
* 是否决定 historical block context
* 是否可以与其他 reads 并发

# 6. Account reads

每个 address 有：

```text
eth_getCode
eth_getBalance
eth_getTransactionCount
```

当前为：

```text
6 addresses × 3 reads = 18 RPC
```

必须确认：

* 三个 read 的参数是否独立
* code 是否影响 balance/nonce 参数
* balance 是否影响 nonce 参数
* orchestration 是否依赖其中任何一个结果才能生成其他请求

如果代码证明独立，可以允许：

```text
code
balance
nonce
```

并发。

如果不能证明，必须保持依赖顺序，并在 evidence 中记录：

```text dependency = unknown
```

禁止猜测。

---

# 7. Storage reads

当前：

```text
20 × eth_getStorageAt
```

必须确认：

* address 是否提前确定
* slot 是否提前确定
* 一个 storage read 是否决定另一个 read 的参数
* 是否存在动态 slot generation
* 是否存在顺序依赖

如果全部 request descriptors 在 acquisition 开始前已经确定，则可以作为 independent read set。

否则必须保守处理。

---

# 8. State consistency 是最高优先级

所有 reads 必须继续使用：

```text
chain_id
block_number
block_tag
```

并保持与 M8.3.1/M8.3.2 相同的 historical block semantics。

禁止任何并发路径偷偷使用：

```text
latest
pending
unsafe latest
```

不得因为并发 scheduler 重构 provider API 而改变 block semantics。

---

# 9. 推荐实现方式

优先实现一个 simulation-local bounded scheduler。

概念上：

```text
State Acquisition Plan
        │
        ├── Block Context
        │
        ├── Account Reads
        │
        └── Storage Reads
```

每个 request 应当先成为明确的 request descriptor，例如：

```text
StateReadRequest
```

或者等价结构。

scheduler 根据：

```text
concurrency_limit
```

控制同时执行的 RPC 数量。

不要直接对整个 simulation 使用：

```rust
join_all(...)
```

也不要创建无限任务。
