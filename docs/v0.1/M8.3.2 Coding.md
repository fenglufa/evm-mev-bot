
# M8.3.2 — Post-Reuse State Acquisition Diagnosis

## 1. 目标

建立新的优化后基线，回答：

1. 剩余 39 次 RPC 各自是什么？
2. 哪类 RPC 占据最多 wall time？
3. `getStorageAt` 现在是不是第一瓶颈？
4. `getCode / Balance / Nonce` 的 18 次减少后，剩余 6+6+6 是否已经成为次要成本？
5. 39 次 RPC 是否仍然完全串行？
6. 剩余 RPC 中是否存在可以进一步复用的数据？
7. 哪些 RPC 是 simulation 必需，哪些来自外围/重复的 orchestration？
8. simulation 之外是否还有大量 preflight / detection RPC，需要单独处理？
9. 下一步应该进入：

   * same-account consolidation
   * batch
   * controlled concurrency
   * provider latency
   * 或暂时停止 simulation 优化

# 7. Storage slot 语义

如果现有代码已经知道某些 slot 的语义：

```text

...
```

可以记录：

```text

```

但必须遵守：

> **只有代码已有明确语义映射才能标注。**

不能根据 slot 数字猜。

如果无法确定：

```text
semantic = unknown
```

# 8. 一个非常重要的诊断：Storage 是否其实是“可合并”的

我们需要检查：

```text
getStorageAt(address, slot1)
getStorageAt(address, slot2)
getStorageAt(address, slot3)
```

是否来自同一个 RPC/provider endpoint。

如果全部是：

```text
same endpoint
same block
same simulation
```

那么 M8.3.2 可以提出一个候选：

> batch JSON-RPC

但**不能实现**。

# 10. 检查这 18 次是不是 simulation 真正需要

这里尤其重要。

需要沿着调用链确认：

```text
simulation
 ↓
REVM
 ↓
state acquisition
 ↓
account(address)
 ↓
code/balance/nonce
```

还是：

```text
simulation
 ↓
orchestration
 ↓
preflight-ish helper
 ↓
account()
```

如果某些 account state 是 simulation 本身必需的：

```text
required_by = simulation
```

如果来自外围编排：

```text
required_by = orchestration
```

如果无法区分：

```text
required_by = unknown
```

**不要猜。**

---

# 11. 第四层：重新检查 serial / overlap

M8.3.1 没有做 concurrency，所以大概率还是：

```text
max concurrency = 1
overlap = 0
```

但 M8.3.2 必须重新测。

输出：

```text
rpc_sum_duration
rpc_wall_duration
overlap_duration
serial_wait_duration
```

这是必要的，因为经过 cache 后：

```text
RPC 数量下降
```

但：

```text
single-request latency
```

可能已经成为新的主要限制。

---

# 12. 特别检查“空隙”

M8.2 发现：

```text
RPC 之间有 43–58ms 空隙
```

M8.3.2 必须重新测：

```text
gap_total
gap_count
gap_min
gap_median
gap_max
```

如果：

```text
39 RPC
每个 RPC 之间仍然 ~50ms
```

那么即使 RPC 本身非常快，orchestration 也可能产生明显成本。

如果 gap 已经接近 0：

> 可以排除这个方向。

---

# 13. 第五层：Local vs RPC 重新划分

M8.3.1 之后必须重新计算：

```text
simulation_total_duration
rpc_wall_duration
non_rpc_duration
```

仍然必须使用：

> **RPC interval union**

不能：

```text
simulation_total - rpc_sum
```

最终回答：

```text
M8.3.1 后
RPC %
Local %
```

因为之前：

```text
RPC ≈ 99.9%
```

现在很可能变成：

```text
RPC ≈ 99.x%
```

但我们不能提前假设。

---

# 14. 第六层：检查是否还有隐藏 RPC

这一步很重要。

M8.3.1 的 cache 只覆盖：

```text
code
balance
nonce
storage
```

所以 M8.3.2 要把整个 simulation 生命周期的 RPC trace 看一遍。

分类：

```text
simulation-state
simulation-context
orchestration
preflight
detection
unknown
```

尤其寻找：

```text
eth_call
eth_getBlockByNumber
eth_getLogs
eth_getCode
...
```

如果存在 simulation 外围 RPC：

**不要混进 39 的核心 state-read baseline。**

但要单独报告：

```text
outside_simulation_rpc
```

这样我们不会把：

```text
simulation optimization
```

和：

```text
preflight optimization
```

混在一起。

---

# 15. 第七层：Provider latency 仍然要保持独立

不要因为 M8.3.1 成功就默认：

> 剩余 RPC 慢就是 provider 慢。

要计算：

```text
method median
method max
```

特别：

```text
getStorageAt
```

如果：

```text
20 次 storage
≈ 200–300ms each
```

那么它自然可能成为第一瓶颈。

但如果：

```text
storage ≈ 30ms
code ≈ 400ms
```

那方向就完全不同。

---

# 16. 三个 real live runs 就够第一轮

继续遵守：

```text
0 ETH
0 signing
0 broadcast
```

建议：

```text
3 live simulations
```

不要求 20 个 opportunity。

每次：

```text
state_read_reuse = true
```

因为我们诊断的是：

> **优化后的实际系统。**

M8.2 的答案是：

```text

```

M8.3.1 已经把它消掉。

现在我们**不知道**答案是什么。

可能是：

```text
B — RPC latency
```

也可能是：

```text
C — serial dependency
```

也可能是：

```text
StorageAt × 20
```

甚至可能发现：

```text

preflight 才是下一阶段真正的大头
```

所以 M8.3.2 的价值就在这里：

> **重新测量，而不是继续沿着旧结论优化。**
