## 0. 一句话（白话版）

任务书假设 Flashblocks 是一条**推送流**：每个「亚块」自带一个递增序号，我们收到帧、按序号排好、
拼出还没封块的状态。**真实端点不是这样**：它没有推送（WS 升级不回包、`eth_subscribe` 在 HTTP 上
直接报 -32603），也没有序号（pending 块头里根本没有 `index` 字段，只有交易自己的 `transactionIndex`）。
它给的是**同一个「下一个块」被反复重读、每次都长得更大一点的同一份 HTTP 视图**——好比邮差不上门，
但你每三十秒去门口看一次，包裹就在你眼皮底下一点点变大。

因此 M9.4 能做的和必须重写的边界是：**「Early Radar（早雷达）」这件事依然成立且可举证**，
因为「比 canonical 早看到同一笔交易」是真实现象（p50 早 203 ms，实测 733 笔）；
但**它必须建在「轮询同一 pending 视图、自己给帧编号」之上**，而不是建在任务书 §8/§9 字面
假定的「provider 给 index 的推送流」之上。按 §62 的裁决句：**以真实协议为准**，
本文第 3 节把被证伪的假设逐条登记，一条都不偷偷改目标。

还有一个必须前置说的实测结论：**这个端点上「早」不等于「比 canonical RPC 更有权威」**。
flashblocks 专用宿主的 pending 块头 `stateRoot` 是**全零占位**（29/29、52/52、50/50 三个窗口一致），
也就是它压根不提供「可以在这个高度取状态」的凭据；它的真实增值是**同一个块还没封就能看见里面
越来越长的交易表和 receipts**（17/19 个高度出现多次状态；pending receipts 一个高度内 9→101 张）。
 canonical 宿主的 `pending` 本身也是一个早期视图（到 latest 的 p50 只差 1332 ms）。

## 2. 实测协议（§5/§6 的取证结论；未确认字段一律 Unknown，不猜）

### 2.1 传输面：只有 HTTP JSON-RPC，没有任何推送

| 探针 | 两宿主的逐字答复 |
|---|---|
| `eth_subscribe(["flashblocks"])` | HTTP 200，`{"code":-32603,"message":"Internal error"}` |
| `eth_subscribe(["newPendingTransactions"])` | 同上，逐字一致 |
| `engine_getBlobsV1` | HTTP 403，`{"code":-32601,"message":"rpc method is not whitelisted"}` |
| `rpc_methods` | HTTP 403，同上 |
| WS 升级请求（`/`、`/rpc`、`/websocket`） | **405 Method Not Allowed**，`Upgrade` / `Sec-WebSocket-Accept` 头均无 |
| WS 升级请求（`/ws`） | TLS 连接建立后 **7 s 内一个字节都不回**（自设 watchdog，非 HTTP 错误码） |
| Node `WebSocket` 真实握手（`/ws`） | 2.5 s 内 `NOT_OPEN`；6 种订阅 + 1 个控制请求全部 `InvalidStateError: Sent before connected.`；**总帧数 0，通知帧 0** |
| `eth_getBlockByHash(pendingHash)` | `result: null`（两宿主一致） |
| `eth_getLogs({blockHash: pendingHash})` | `{"code":-32001,"message":"block not found: hash 0x02fd0036…"}` |

**诚实边界（必须与结论同处书写）**：本机出口走本地 TLS 终止代理，WS 升级被代理阻断与被端点策略
阻断，靠 L3 窗口本身分不开。因此「无推送」这个结论的**权威证据是端点侧、与代理无关的那两条**：
`eth_subscribe` 在**已经能正常工作的 HTTP JSON-RPC 通道**上答 -32603，`engine_*` 答「not whitelisted」。
WS 探针只作为「本机路径下也无法建立第二传输」的记录，不作为独立结论。

### 2.2 预确认产品 = 被反复重读的 `pending` 视图，且它在一个高度内生长

| 指标（窗口 C，19 个高度） | flashblocks 宿主 | canonical 宿主 |
|---|---|---|
| pending 样本数 / 去重后 pending 块哈希数 | 52 / **46** | 56 / 19 |
| **同一高度出现多种状态**的高度数 | **17/19** | 0/19 |
| 同高度内交易数「变大」的次数 / 「变小」的次数 | 27 / 0 | 0 / 0 |
| `stateRoot` 为全零占位的样本数 | **52/52** | 0/56 |

窗口 G 复算（22 / 21 个高度）给出同方向结论：flashblocks 12/22 多状态，canonical 0/21。
窗口 K 用 `eth_getBlockReceipts("pending")` 再独立复算一次：flashblocks **8/14 高度多状态**，
单高度 receipts 数区间 **9..101**，canonical 0/14，errors 0。

⇒ 真实语义是「**一个 pending 块的部分状态，随轮询单调增长**」，不是「一段有序号的帧序列」。
`stateRoot` 全零 ⇒ 该视图**没有任何状态凭据**，这正是任务书 §3.1/§27 禁止它进 canonical StateStore
的物理理由，不只是架构偏好。

### 2.3 身份面：线上传输里**没有**帧序号字段

pending 块头的实测字段集合（窗口 H，26 项）：

```
baseFeePerGas blobGasUsed difficulty excessBlobGas extraData gasLimit gasUsed hash logsBloom
miner mixHash nonce number parentBeaconBlockRoot parentHash receiptsRoot requestsHash
sha3Uncles size stateRoot timestamp transactions transactionsRoot uncles withdrawals withdrawalsRoot
```

**没有 `index` / `sequence` / `slot` / `payloadId` 任何一项。** 带 `index` 语义的字段只存在于
条目级：交易有 `transactionIndex`，receipt 有 `transactionIndex`/`cumulativeGasUsed`/`status`/`l1Fee`，
log 有 `logIndex`/`transactionIndex`/`removed`/`blockHash`/`blockNumber`。

⇒ 任务书 §8 的身份式 `chain_id + block_number + index + parent_identity` 里，
`index` **只能由本地分配**（读序），不能声称来自 provider。本次实现据此建模，并在
完成报告与证据表里把「index 非 provider 字段」写死；同时 pending 块哈希**每次读都可能换**
（52 次读 46 个哈希）⇒ 帧身份绝不能只用哈希。

### 2.4 消息面：一个「块」= 一段增长序列，长度不固定（§48 按实测报，不伪造）

一帧 = 同一高度上被读到的一份**互不相同**的 pending 视图。实测（`target/m94_facts.json` 的
`c7_frame_counts`，逐窗口计算）：

| 窗口 / 臂 | 高度数 | 每高度读次 | 每高度不同视图数 | **≥3 次读**的高度 | **≥3 个不同视图**的高度 |
|---|---|---|---|---|---|
| C · flashblocks pending | 19 | 1..4 | 1..4 | **12** | **9** |
| C · canonical pending | 19 | 1..5 | **恒为 1** | 15 | **0** |
| G · flashblocks pending | 22 | 1..5 | 1..4 | 9 | 5 |
| G · canonical pending | 21 | 2..4 | **恒为 1** | 17 | 0 |

⇒ §48 的「N ≥ 3 连续 flashblocks」在 flashblocks 宿主上**可满足但不足额**：窗口 C 19 个高度里
9 个有 ≥3 个不同视图，另外 10 个只有 1–2 个（块封得太快）。canonical 宿主的同高度多视图数
**恒为 0**——这是两个宿主最干净的结构性区分。
证据表里必须逐高度报真实 N 并标注未达标的高度，**不得只挑 9 个达标的高度当分母**。

### 2.6 候选态 vs 已封块：哈希永不相同，内容常相同

对 48 个「其高度后来真的封了」的 pending 样本做对账（窗口 G）：

| | 实测 |
|---|---|
| tx 列表 + `gasUsed` + `parentHash` 与封块**完全相同** | **23/48** |
| 块**哈希**相同 | **0/48** |

⇒ **M5 现有的 hash 相等式 reconciliation 在本端点上结构上永不触发**
（`crates/live/src/flashblocks.rs:414` 的 `record.hashes.contains(&block.hash)`）。
M9.4 的对账必须是**内容式**（交易集合 / gasUsed / parentHash），且 §17「不一致时 canonical 胜出、
不合并」在内容式下依然可判定。既有 `matched_hash` 字段语义**保持不变**（它记录的就是「哈希是否相同」
这个事实），新的内容一致性判定另起字段，不改旧语义——这是本次生产码 diff 最小化的决定之一。

### 2.7 canonical 视图是共享的

同一高度的**已封块**哈希跨宿主比对：**7/7 相同，0 个不同**（窗口 E，latest 口径）。
⇒ 不存在「第二个 canonical 真相」；flashblocks 宿主只是把同一个链的**未来视图**露出来。
这条是 §15「canonical 验证」与 §3.1「不得写 canonical」能同时成立的前提。

### 2.8 A/B 延迟的诚实分布（§26/§27）

窗口 G 的同一秒表、同一窗口内并发采到 733 笔**两臂都见过**的交易：

| 派生量 | min | p50 | p90 | max | 非正值 |
|---|---|---|---|---|---|
| `canonical_first_sight − flashblocks_first_sight`（§27 的 `flashblocks_lead`） | **−692 ms** | **+203 ms** | +834 ms | +1240 ms | **187/733 = 25.5%** |
| flashblocks 臂 pending→latest | +632 | 1699 | 2082 | 2731 | 0/726 |
| canonical 臂 pending→latest | +769 | 1332 | 1727 | 1837 | 0/755 |

其他可见性口径：unique txs（fl pending 801 / ca pending 792 / 任一 latest 862），
**75 笔在 flashblocks 的 pending 里见过、但在两臂的 latest 里都没出现过**（它们所在块在窗口内未封）。

⇒ 三条必须写进完成报告的结论：
1. lead 是**有符号、有 25.5% 非正样本**的分布，**不是**「Flashblocks 更快」的证明；
   §28「不能通过选择性窗口证明 Flashblocks 有优势」在这里的字面落实就是这 187 笔。
2. flashblocks 宿主的 pending→latest 反而**更慢**（p50 1699 vs 1332 ms）⇒
   它的差异点**不是**「更早给出完整块」，而是 §2.2 的**同高度部分块可见性**。
3. canonical 宿主自己的 `pending` 已经是一个早期视图 ⇒ 「早雷达」的对照臂必须包含它，
   否则拿 A 臂比一个不存在的 B 臂。

### 2.9 机会面（AMM）在真实流量上的约束（§48 的「不伪造」）

| | 实测 |
|---|---|
| 14 s 窗口内 V2 Swap log | **1 条** |
| M9.2 已举证的池数（`graph-integration.json` 的边表） | 80 |
| pending log 发射者集合 ∩ 这 80 个池 | **0** |

⇒ 本里程碑**无法**在真实流量上攒出「预确认状态命中已注册池」的样本。这不是实现缺陷，

## 5. 类型隔离面（§4 / §58）现状与要补的门

§58 要求「本里程碑最重要的单个负向架构测试」。两把一起立：

1. **类型面**：`PreconfirmationState` 定义在 `crates/live`，**不实现**任何指向 canonical 状态的
   转换（无 `Into`/`From` 到 `evm_state` 的类型，也不实现 `is_canonical()==true` 的 `SourceKind`）。
   门测：以 trait 边界断言「不存在从 `PreconfirmationState` 到 StateStore 写入 API 的可达构造」，
   并加源码面扫描（新文件里不得出现 `InMemoryStateStore`/`on_canonical`/`StateUpdate` 的构造调用）。
2. **运行面**：把真实捕获的 pending 增长序列喂进 pipeline 的事件入口，断言
   `engine.blocks`（推进计数）为 0，且 evidence 行数 > 0——即「事件被看见、状态没被推进」。

`SourceKind::is_canonical()`（`event.rs:46-48`）已经是编译期的唯一分支点，
这一点在本文档里记为**审计结论**，不是新发明。
